Question 57 / 361

Your team wants to make sure Compute Engine instances running in your production project do not have public IP addresses. The frontend application Compute Engine instances will require public IPs. The product engineers have the Editor role to modify resources. Your team wants to enforce this requirement. How should your team meet these requirements?

  • A. Enable Private Access on the VPC network in the production project.
  • B. Remove the Editor role and grant the Compute Admin IAM role to the engineers.
  • C. Set up an organization policy to only permit public IPs for the front-end Compute Engine instances.
  • D. Set up a VPC network with two subnets: one with public IPs and one without public IPs.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C

Wyjaśnienie:
Ograniczenie polityki organizacji (Organization Policy) o nazwie `constraints/compute.restrictExternalIp` jest najskuteczniejszym sposobem na wymuszenie zakazu posiadania publicznych adresów IP w projekcie. Pozwala ono na zdefiniowanie "listy dopuszczonych" (whitelist) instancji maszyn wirtualnych, które jako jedyne mogą mieć przypisany zewnętrzny adres IP. Jest to mechanizm nadrzędny wobec IAM – nawet jeśli użytkownik posiada rolę Editor lub Compute Admin, polityka organizacji fizycznie zablokuje mu możliwość przypisania publicznego IP do instancji, która nie znajduje się na liście.

Dlaczego pozostałe opcje są niepoprawne:
- A: `Private Google Access` (Prywatny dostęp do Google) umożliwia instancjom posiadającym wyłącznie prywatne adresy IP na łączenie się z publicznymi API Google (np. Cloud Storage, BigQuery). Sama w sobie ta funkcja nie zabrania jednak przypisywania publicznych adresów IP do maszyn.
- B: Zmiana roli z Editor na `Compute Admin` nie rozwiąże problemu. Rola Compute Admin nadal daje pełne uprawnienia do zarządzania interfejsami sieciowymi maszyn, w tym do przypisywania im zewnętrznych adresów IP.
- D: W Google Cloud publiczny adres IP jest atrybutem interfejsu konkretnej instancji, a nie całej podsieci. Choć można zaprojektować architekturę z podziałem na podsieci "publiczne" i "prywatne", bez dodatkowych ograniczeń (jak Organization Policy) nic nie stoi na przeszkodzie, aby inżynier przypisał publiczny IP do maszyny w dowolnej podsieci.

Tips & Tricks:
- Słowo kluczowe "Enforce" (wymusić) w kontekście infrastruktury GCP bardzo często wskazuje na Organization Policy.
- Pamiętaj, że polityka `compute.restrictExternalIp` może być skonfigurowana tak, aby dopuszczać tylko konkretne nazwy instancji lub grupy instancji.
- Zawsze wybieraj Organization Policy, gdy musisz ograniczyć możliwości użytkowników o wysokich uprawnieniach (Administratorów/Edytorów).

Zagadnienia:
- Organization Policy Service (Więzy/Constraints)
- Compute Engine Networking (Adresacja IP)
- External IP restrictions (Ograniczanie zewnętrznych IP)

Kluczowe wnioski

Potwierdzona odpowiedź: C

Bezpieczeństwo sieciowe zaczyna się od minimalizacji powierzchni ataku. Wyłączenie publicznych adresów IP dla większości maszyn jest jedną z najważniejszych rekomendacji Google Cloud. W tym scenariuszu Organization Policy działa jako "bariera ochronna" (guardrail), zapobiegająca przypadkowym lub celowym błędnym konfiguracjom.

Praktyczne wskazówki

  • Warto wiedzieć, że maszyny bez publicznego IP mogą potrzebować Cloud NAT, aby móc pobierać aktualizacje z internetu.
  • Polityki organizacji są dziedziczone w dół hierarchii (Organizacja -> Folder -> Projekt), co pozwala na globalne narzucenie standardów bezpieczeństwa w całej firmie.
