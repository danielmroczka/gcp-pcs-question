Question 135 / 361

You need to implement an encryption-at-rest strategy that protects sensitive data and reduces key management complexity for non-sensitive data. Your solution has the following requirements: Schedule key rotation for sensitive data. Control which region the encryption keys for sensitive data are stored in. Minimize the latency to access encryption keys for both sensitive and non-sensitive data. What should you do?

  • A. Encrypt non-sensitive data and sensitive data with Cloud External Key Manager.
  • B. Encrypt non-sensitive data and sensitive data with Cloud Key Management Service.
  • C. Encrypt non-sensitive data with Google default encryption, and encrypt sensitive data with Cloud External Key Manager.
  • D. Encrypt non-sensitive data with Google default encryption, and encrypt sensitive data with Cloud Key Management Service.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

Potwierdzona odpowiedź: D (Encrypt non-sensitive data with Google default encryption, and encrypt sensitive data with Cloud Key Management Service).

Wyjaśnienie:
- Google Default Encryption: Google automatycznie szyfruje wszystkie dane w spoczynku bez dodatkowych kosztów i bez konieczności zarządzania kluczami. Jest to idealne rozwiązanie dla danych "non-sensitive", ponieważ minimalizuje złożoność zarządzania kluczami (Key Management Complexity) oraz zapewnia najniższe opóźnienia (latency), gdyż klucze są blisko danych.
- Cloud Key Management Service (Cloud KMS): Pozwala na tworzenie kluczy zarządzanych przez klienta (CMEK). Umożliwia planowanie rotacji kluczy (Schedule key rotation) oraz wybór regionu przechowywania kluczy (Control which region encryption keys are stored), co spełnia wymagania dla danych wrażliwych (sensitive data). KMS zapewnia również niskie opóźnienia w porównaniu do systemów zewnętrznych.

Dlaczego pozostałe są błędne:
- A. Cloud External Key Manager (EKM): Korzystanie z EKM dla wszystkich danych (w tym niejawnych) drastycznie zwiększa złożoność i opóźnienia (latency), ponieważ każde żądanie szyfrowania/odszyfrowania musi opuścić infrastrukturę Google Cloud do zewnętrznego dostawcy kluczy.
- B. Cloud KMS dla wszystkich danych: Chociaż możliwe, zwiększa to niepotrzebnie złożoność zarządzania kluczami dla danych niejawnych, dla których Google Default Encryption jest wystarczające i prostsze.
- C. Cloud EKM dla danych wrażliwych: Chociaż zapewnia kontrolę, wprowadza znacznie wyższe opóźnienia niż Cloud KMS, co narusza wymaganie "Minimize the latency". EKM jest zazwyczaj używany tylko wtedy, gdy wymagana jest suwerenność kluczy poza chmurą.

Wskazówki egzaminacyjne (Tips & Tricks):
- "Reduce key management complexity" + "non-sensitive data" = Default Encryption.
- "Schedule rotation" + "Control region" = Cloud KMS (CMEK).
- "Minimize latency" = Wybieraj rozwiązania natywne Google (Default lub KMS), unikaj zewnętrznych (EKM), chyba że suwerenność jest priorytetem.

Kluczowe zagadnienia do powtórzenia:
- Hierarchia szyfrowania w GCP (Default vs CMEK vs CSEK vs EKM).
- Cloud KMS i jego możliwości (rotacja, rezydencja danych).
- Latency w dostępie do kluczy szyfrujących.
