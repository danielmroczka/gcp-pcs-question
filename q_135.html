Question 135 / 361

You need to implement an encryption-at-rest strategy that protects sensitive data and reduces key management complexity for non-sensitive data. Your solution has the following requirements: Schedule key rotation for sensitive data. Control which region the encryption keys for sensitive data are stored in. Minimize the latency to access encryption keys for both sensitive and non-sensitive data. What should you do?

  • A. Encrypt non-sensitive data and sensitive data with Cloud External Key Manager.
  • B. Encrypt non-sensitive data and sensitive data with Cloud Key Management Service.
  • C. Encrypt non-sensitive data with Google default encryption, and encrypt sensitive data with Cloud External Key Manager.
  • D. Encrypt non-sensitive data with Google default encryption, and encrypt sensitive data with Cloud Key Management Service.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
D. Encrypt non-sensitive data with Google default encryption, and encrypt sensitive data with Cloud Key Management Service.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Wymagania dla szyfrowania danych w spoczynku: 1) ochrona danych wrażliwych z możliwością kontroli lokalizacji (residency) i harmonogramu rotacji, 2) niska złożoność dla danych zwykłych, 3) minimalizacja opóźnień (latency) w dostępie do kluczy dla obu typów danych:
- Szyfrowanie domyślne Google (Google default encryption) nie wymaga żadnej konfiguracji ani zarządzania (zerowa złożoność) i zapewnia najniższe możliwe opóźnienia, ponieważ klucze są zarządzane bezpośrednio przy systemach przechowywania danych. Jest to idealny wybór dla danych niewrażliwych.
- Szyfrowanie Cloud KMS (CMEK) dla danych wrażliwych pozwala na pełną kontrolę nad rotacją kluczy oraz regionem ich przechowywania. Ponieważ Cloud KMS to usługa wbudowana w sieć Google Cloud, opóźnienia dostępu do kluczy są minimalne (w przeciwieństwie do zewnętrznych systemów zarządzania kluczami).

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
- A i C. Użycie Cloud External Key Manager (EKM): EKM przechowuje klucze na zewnętrznych systemach HSM poza chmurą Google (on-premises lub u innego dostawcy). Każda operacja szyfrowania/deszyfrowania wymaga wywołania sieciowego poza GCP, co wprowadza znaczne opóźnienia (latency) i łamie wymóg ich minimalizacji.
- B. Szyfrowanie wszystkich danych za pomocą Cloud KMS: Wprowadza niepotrzebną złożoność operacyjną (management complexity) związaną z tworzeniem, autoryzacją i rotowaniem kluczy dla danych, które nie są wrażliwe.

4. Wskazówki, hinty, tips and tricks:
- Zewnętrzny menedżer kluczy (EKM) zawsze wiąże się z narzutem opóźnień sieciowych (network latency), ponieważ klucz fizycznie opuszcza infrastrukturę Google. W przypadku wymogu niskich opóźnień, klucze muszą znajdować się wewnątrz GCP (KMS/HSM).
- Domyślne szyfrowanie (default encryption) w GCP jest bezpłatne, automatyczne i nie generuje żadnego narzutu zarządzania.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
- Zwykłe dane + niskie opóźnienia i brak narzutu -> Google default encryption.
- Dane wrażliwe + kontrola rotacji i rezydencji w chmurze -> Cloud KMS.

6. Dodatkowe źródła i dokumentacja:
- Cloud KMS latency considerations: https://cloud.google.com/kms/docs/ekm#latency
