Question 287 / 361

You work for a banking organization. You are migrating sensitive customer data to Google Cloud that is currently encrypted at rest while on-premises. There are strict regulatory requirements when moving sensitive data to the cloud. Independent of the cloud service provider, you must be able to audit key usage and be able to deny certain types of decrypt requests. You must choose an encryption strategy that will ensure robust security and compliance with the regulations. What should you do?

  • A. Utilize Google default encryption and Cloud IAM to keep the keys within your organization's control.
  • B. Implement Cloud External Key Manager (Cloud EKM) with Access Approval, to integrate with your existing on-premises key management solution.
  • C. Implement Cloud External Key Manager (Cloud EKM) with Key Access Justifications to integrate with your existing on-premises key management solution.
  • D. Utilize customer-managed encryption keys (CMEK) created in a dedicated Google Compute Engine instance with Confidential Compute encryption, under your organization's control.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Implement Cloud External Key Manager (Cloud EKM) with Key Access Justifications to integrate with your existing on-premises key management solution.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź C jest prawidłowa, ponieważ połączenie Cloud External Key Manager (Cloud EKM) z funkcją Key Access Justifications (KAJ) w pełni spełnia rygorystyczne wymagania suwerenności danych oraz pełnej kontroli klienta nad operacjami odszyfrowywania w bankowości.

Kluczowe zalety rozwiązania:
a. **Klucze poza chmurą:** Klucze szyfrujące (KEK) są generowane i przechowywane w lokalnym systemie zarządzania kluczami (on-premises HSM) banku, niezależnie od Google.
b. **Decyzyjność o odszyfrowaniu (KAJ):** Przy każdej próbie odszyfrowania danych w GCP (np. odczyt bazy przez aplikację lub wsparcie Google), GCP wysyła żądanie do lokalnego HSM wraz z kodem uzasadnienia (Key Access Justification). Bank może zdefiniować zasady, które automatycznie odrzucą (deny) żądania z nieprawidłowym uzasadnieniem (np. brak zgody klienta, nieautoryzowana próba wsparcia technicznego).
c. **Pełen audyt:** Każde żądanie użycia klucza jest rejestrowane w lokalnym systemie banku, dając 100% pewność audytową niezależną od logów chmurowych.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Utilize Google default encryption and Cloud IAM...
   * Dlaczego nieprawidłowa: Domyślne szyfrowanie Google nie daje klientowi kontroli nad materiałem klucza (klucze są w pełni kontrolowane przez Google). Ponadto IAM nie pozwala na odrzucanie żądań na podstawie uzasadnień biznesowych (KAJ) i nie integruje się z lokalnym HSM banku.
B. Implement Cloud External Key Manager (Cloud EKM) with Access Approval...
   * Dlaczego nieprawidłowa: Access Approval służy do zatwierdzania dostępu inżynierów Google do zasobów w celach wsparcia. Nie jest to usługa zintegrowana bezpośrednio z procesem kryptograficznego odszyfrowywania danych przez aplikacje systemowe w locie za pomocą kluczy zewnętrznych w taki sposób jak KAJ.
D. Utilize customer-managed encryption keys (CMEK) created in a dedicated Google Compute Engine instance...
   * Dlaczego nieprawidłowa: Przechowywanie kluczy na maszynie wirtualnej wewnątrz GCP (nawet z Confidential Compute) oznacza, że klucze nadal fizycznie znajdują się w chmurze Google. Nie realizuje to wymogu pełnego wyodrębnienia i kontroli kluczy "niezależnie od dostawcy chmury" (independent of the cloud provider) w lokalnej infrastrukturze banku.

4. Wskazówki, hinty, tips and tricks:
* Pełna kontrola nad kluczami poza GCP + auditowanie i prawo do odrzucania żądań odszyfrowania (deny decrypt requests) -> Złoty standard suwerenności: **Cloud EKM** + **Key Access Justifications (KAJ)**.
* KAJ dostarcza powód (rationale) żądania klucza przy każdej operacji kryptograficznej.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Independent of cloud provider + audit key usage + deny decrypt requests -> Cloud EKM + Key Access Justifications (KAJ).
