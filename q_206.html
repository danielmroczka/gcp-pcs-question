Question 206 / 361

You manage a BigQuery analytical data warehouse in your organization. You want to keep data for all your customers in a common table while you also restrict query access based on rows and columns permissions. Non-query operations should not be supported.

  • A. Create row-level access policies to restrict the result data when you run queries with the filter expression set to TRUE.
  • B. Configure column-level encryption by using Authenticated Encryption with Associated Data (AEAD) functions with Cloud Key Management Service (KMS) to control access to columns at query runtime.
  • C. Create row-level access policies to restrict the result data when you run queries with the filter expression set to FALSE.
  • D. Configure dynamic data masking rules to control access to columns at query runtime.
  • E. Create column-level policy tags to control access to columns at query runtime.
Show Suggested Answer Hide Answer
Suggested Answer: CE

Wyjaśnienie

Potwierdzona odpowiedź: CE (C. Create row-level access policies, E. Create column-level policy tags).

Wyjaśnienie:
- Row-Level Security (RLS - C): BigQuery pozwala na ograniczanie dostępu do danych na poziomie poszczególnych wierszy w tabeli za pomocą tzw. "Row-level access policies". Każda polityka zawiera wyrażenie filtrujące (np. `customer_id = 'ABC'`). BigQuery automatycznie odfiltrowuje wiersze, dla których wyrażenie to jest FAŁSZYWE (FALSE). Dzięki temu w jednej tabeli możesz trzymać dane wielu klientów, a każdy z nich zobaczy tylko swoje rekordy.
- Column-Level Security (CLS - E): Do ograniczania dostępu do całych kolumn (np. PII) służą "Policy Tags" zarządzane w usłudze Data Catalog. Możesz oznaczyć konkretne kolumny tagami i nadać uprawnienia do odczytu tych tagów tylko wybranym osobom. Użytkownik bez odpowiedniej roli IAM nie będzie mógł wybrać tych kolumn w zapytaniu SELECT.

Dlaczego pozostałe odpowiedzi są niepoprawne:
- A. Filter expression set to TRUE: Gdybyś stworzył politykę z filtrem `TRUE`, użytkownik widziałby WSZYSTKIE wiersze (ponieważ dla każdego wiersza warunek byłby spełniony). Nie stanowiłoby to żadnej restrykcji.
- B. AEAD Encryption: Szyfrowanie AEAD z użyciem KMS jest potężną techniką, ale jest znacznie trudniejsze w implementacji i zarządzaniu niż natywne funkcje RLS/CLS BigQuery. Wymagałoby modyfikacji zapytań SQL przez użytkowników (użycie funkcji deszyfrujących w kodzie SQL).
- D. Dynamic data masking: Służy do ukrywania części danych (np. pokazanie tylko gwiazdek zamiast numeru karty), ale dane wciąż są widoczne w sformatowanej formie. CLS (opcja E) jest silniejszym mechanizmem, ponieważ całkowicie blokuje dostęp do kolumny na poziomie metadanych.

Wskazówki egzaminacyjne (Tips & Tricks):
- "Restrict access based on rows" = Row-level access policies.
- "Restrict access based on columns" = Policy tags (Data Catalog).
- Pamiętaj: Jeśli do tabeli zostanie przypisana chociaż jedna polityka RLS, wszyscy użytkownicy NIE ujęci w żadnej polityce tracą dostęp do WSZYSTKICH wierszy (bezpieczne domyślne zachowanie).

Kluczowe zagadnienia do powtórzenia:
- BigQuery Row-level security (RLS).
- BigQuery Column-level security (CLS) i Policy Tags.
- Data Catalog w ekosystemie Google Cloud.

Analiza i Wyjaśnienie

Sugerowana odpowiedź: CE

Głęboka analiza: To pytanie dotyczy budowy nowoczesnych platform analitycznych w architekturze "Multi-tenant". Najważniejszym trendem w GCP jest odchodzenie od fizycznej separacji danych (osobne tabele) na rzecz separacji logicznej (RLS/CLS). Pozwala to na znacznie łatwiejsze zarządzanie jednym, centralnym "Data Lake" przy zachowaniu rygorystycznych wymogów prywatności i zasady "need-to-know".
