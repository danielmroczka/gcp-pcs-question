Question 206 / 361

You manage a BigQuery analytical data warehouse in your organization. You want to keep data for all your customers in a common table while you also restrict query access based on rows and columns permissions. Non-query operations should not be supported.
What should you do? (Choose two.)

  • A. Create row-level access policies to restrict the result data when you run queries with the filter expression set to TRUE.
  • B. Configure column-level encryption by using Authenticated Encryption with Associated Data (AEAD) functions with Cloud Key Management Service (KMS) to control access to columns at query runtime.
  • C. Create row-level access policies to restrict the result data when you run queries with the filter expression set to FALSE.
  • D. Configure dynamic data masking rules to control access to columns at query runtime.
  • E. Create column-level policy tags to control access to columns at query runtime.
Show Suggested Answer Hide Answer
Suggested Answer: CE

Wyjaśnienie

Poprawna odpowiedź: CE (C: Create row-level access policies, E: Create column-level policy tags)

Dlaczego te odpowiedzi są poprawne:
- Row-Level Security (RLS - C): BigQuery pozwala na ograniczanie dostępu do danych na poziomie poszczególnych wierszy w tabeli. Robi się to za pomocą tzw. "Row-level access policies". Każda polityka zawiera wyrażenie filtrujące (np. `customer_id = 'ABC'`). Gdy użytkownik objęty taką polityką wykonuje zapytanie, BigQuery automatycznie odfiltrowuje (ukrywa) wiersze, dla których wyrażenie to jest FAŁSZYWE (FALSE). Dzięki temu w jednej tabeli możesz trzymać dane wielu klientów, a każdy z nich zobaczy tylko swoje rekordy.
- Column-Level Security (CLS - E): Do ograniczania dostępu do całych kolumn (np. PII, dane finansowe) służą "Policy Tags" zarządzane w usłudze Data Catalog. Możesz oznaczyć konkretne kolumny tagami (np. "Sensitive") i nadać uprawnienia do odczytu tych tagów tylko wybranym osobom. Użytkownik bez odpowiedniej roli IAM nie będzie mógł wybrać tych kolumn w zapytaniu SELECT, nawet jeśli ma dostęp do reszty tabeli.

Analiza niepoprawnych odpowiedzi:
- A. Filter expression set to TRUE: Gdybyś stworzył politykę z filtrem ustawionym na `TRUE`, użytkownik widziałby WSZYSTKIE wiersze (ponieważ dla każdego wiersza warunek byłby spełniony). Nie stanowiłoby to żadnej restrykcji, o którą prosi pytanie.
- B. AEAD Encryption: Szyfrowanie AEAD z użyciem KMS jest potężną techniką ochrony danych "at rest" i pozwala na granularną kontrolę, ale jest znacznie trudniejsze w implementacji i zarządzaniu niż natywne funkcje RLS/CLS BigQuery. Wymagałoby modyfikacji zapytań SQL przez użytkowników (użycie funkcji deszyfrujących).
- D. Dynamic data masking: Służy do ukrywania części danych (np. pokazanie tylko ostatnich 4 cyfr karty) dla osób bez uprawnień, ale dane wciąż są widoczne w sformatowanej formie. CLS (opcja E) jest silniejszym mechanizmem, ponieważ całkowicie blokuje dostęp do kolumny na poziomie metadanych.

Wskazówki i triki (Tips & Tricks):
- "Restrict access based on rows" = Row-level access policies.
- "Restrict access based on columns" = Policy tags (Data Catalog).
- Pamiętaj: RLS jest addytywne. Jeśli należysz do dwóch polityk, widzisz sumę wierszy z obu.
- Pamiętaj: Jeśli do tabeli zostanie przypisana chociaż jedna polityka RLS, wszyscy użytkownicy NIE ujęci w żadnej polityce tracą dostęp do WSZYSTKICH wierszy (bezpieczne domyślne zachowanie).

Praktyczne informacje na egzamin:
- Zrozum hierarchię: Dostęp do tabeli (Dataset/Table IAM) -> CLS (Policy Tags) -> RLS (Filter expressions).
- Aby używać CLS, musisz mieć włączone API Data Catalog i odpowiednie uprawnienia `Data Catalog Fine-Grained Reader`.

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: CE

Analiza strategiczna: To pytanie dotyczy budowy nowoczesnych platform analitycznych w architekturze "Multi-tenant". Najważniejszym trendem w GCP jest odchodzenie od fizycznej separacji danych (osobne tabele/datasety) na rzecz separacji logicznej (RLS/CLS). Pozwala to na znacznie łatwiejsze zarządzanie jednym, centralnym "Data Lake" przy zachowaniu rygorystycznych wymogów prywatności.

Dodatkowe wskazówki

  • Zwróć uwagę na wymóg "Non-query operations should not be supported". Oznacza to, że użytkownicy powinni mieć rolę `BigQuery Data Viewer`, a nie `Data Editor`.
  • RLS może wpłynąć na wydajność zapytań (Query performance) przy bardzo skomplikowanych filtrach, ponieważ filtry te są dołączane do każdego zapytania "pod maską".
