Question 235 / 361

You are setting up a new Cloud Storage bucket in your environment that is encrypted with a customer managed encryption key (CMEK). The CMEK is stored in Cloud Key Management Service (KMS), in project "prj-a", and the Cloud Storage bucket will use project "prj-b". The key is backed by a Cloud Hardware Security Module (HSM) and resides in the region europe-west3. Your storage bucket will be located in the region europe-west1. When you create the bucket, you cannot access the key, and you need to troubleshoot why. What has caused the access issue?

  • A. A firewall rule prevents the key from being accessible.
  • B. Cloud HSM does not support Cloud Storage.
  • C. The CMEK is in a different project than the Cloud Storage bucket.
  • D. The CMEK is in a different region than the Cloud Storage bucket.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
D. The CMEK is in a different region than the Cloud Storage bucket.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź D jest prawidłowa, ponieważ Google Cloud nakłada rygorystyczne wymagania dotyczące dopasowania lokalizacji (location matching) dla kluczy szyfrujących zarządzanych przez klienta (CMEK) używanych z usługą Cloud Storage.

Dlaczego lokalizacja ma kluczowe znaczenie:
a. Zgodnie z architekturą bezpieczeństwa GCP, kubełek Cloud Storage (w tym przypadku zlokalizowany w regionie `europe-west1` - Belgia) musi używać klucza KMS znajdującego się w tym samym regionie geograficznym.
b. Klucz CMEK podany w scenariuszu znajduje się w regionie `europe-west3` (Frankfurt).
c. Ze względu na niedopasowanie regionów (`europe-west1` vs `europe-west3`), usługa Cloud Storage nie jest w stanie powiązać kubełka z kluczem, co skutkuje brakiem możliwości autoryzacji i utworzenia zabezpieczonego kubełka.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. A firewall rule prevents the key from being accessible.
   * Dlaczego nieprawidłowa: Reguły zapory sieciowej (firewall rules) w GCP filtrują ruch sieciowy IP na poziomie maszyn wirtualnych Compute Engine i kontenerów. Dostęp do interfejsów API GCP (takich jak Cloud KMS czy Cloud Storage) odbywa się przez globalną sieć Google i nie jest blokowany przez standardowe reguły zapory sieciowej VPC.
B. Cloud HSM does not support Cloud Storage.
   * Dlaczego nieprawidłowa: Jest to nieprawda. Klucze KMS generowane i przechowywane w Cloud HSM są w pełni kompatybilne i wspierane jako klucze CMEK dla wszystkich operacji w Cloud Storage.
C. The CMEK is in a different project than the Cloud Storage bucket.
   * Dlaczego nieprawidłowa: GCP w pełni wspiera konfiguracje międzyprojektowe (cross-project CMEK). Klucz KMS może znajdować się w projekcie A (`prj-a`), a kubełek w projekcie B (`prj-b`), pod warunkiem, że nadano odpowiednie uprawnienia IAM dla konta serwisowego Cloud Storage z projektu B na kluczu w projekcie A. Sam fakt bycia w innym projekcie nie uniemożliwia dostępu.

4. Wskazówki, hinty, tips and tricks:
* Dla Cloud Storage: Klucz CMEK **musi** znajdować się w tej samej lokalizacji (regionie) co kubełek. Wyjątkiem są lokalizacje wieloregionowe (multi-region), gdzie lokalizacja klucza musi odpowiadać strukturze multi-regionu.
* Pamiętaj, że dostęp cross-project dla CMEK jest dozwolony i jest powszechną praktyką bezpieczeństwa (centralny projekt KMS).

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Storage bucket in region X, key in region Y -> Access issue is caused by different regions (different locations).

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
Jeśli scenariusz dotyczy zabezpieczania zasobów chmurowych (GCP), zawsze wybieraj rozwiązanie typu Managed (SCC, Secret Manager, Cloud KMS), a unikaj rozwiązań self-managed, chyba że pytanie wyraźnie wymaga dostosowania niskopoziomowego.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka IAM: Pytania o uprawnienia często sugerują 'Project Owner' – zawsze szukaj 'Least Privilege' (np. 'Role: Secret Manager Secret Accessor').
- Pułapka Sieciowa: Często mylone są VPC Peering (wydajność) oraz VPN (szyfrowanie/on-premise).

Głębokie wyjaśnienie techniczne:
Rozwiązanie bazuje na GCP Shared Responsibility Model. Google zarządza bezpieczeństwem infrastruktury (Physical, Network, Host), podczas gdy administrator zarządza tożsamością (IAM), danymi (Encryption, Cloud KMS) i regułami dostępu (VPC Firewall).

Kluczowe zagadnienia

Sugerowana odpowiedź: A
