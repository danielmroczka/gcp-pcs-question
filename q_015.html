Question 15 / 361

An application running on a Compute Engine instance needs to read data from a Cloud Storage bucket. Your team does not allow Cloud Storage buckets to be globally readable and wants to ensure the principle of least privilege. Which option meets the requirement of your team?

  • A. Create a Cloud Storage ACL that allows read-only access from the Compute Engine instance's IP address and allows the application to read from the bucket without credentials.
  • B. Use a service account with read-only access to the Cloud Storage bucket, and store the credentials to the service account in the config of the application on the Compute Engine instance.
  • D. Encrypt the data in the Cloud Storage bucket using Cloud KMS, and allow the application to decrypt the data with the KMS key.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C (Use a service account with read-only access to the Cloud Storage bucket to retrieve the credentials from the instance metadata.)

Wyjaśnienie: 
Rekomendowaną i najbezpieczniejszą metodą uwierzytelniania aplikacji działających na maszynach wirtualnych (Compute Engine) jest użycie kont serwisowych (Service Accounts) podpiętych bezpośrednio do instancji:
- Tożsamość: Instancja "staje się" kontem serwisowym.
- Metadata Server: Aplikacja pobiera tymczasowe tokeny dostępu (access tokens) bezpośrednio z serwera metadanych instancji (`metadata.google.internal`).
- Bezpieczeństwo: Nie trzeba przechowywać żadnych kluczy (JSON keys) ani haseł na dysku instancji ani w kodzie źródłowym. Jest to zgodne z zasadą najniższych uprawnień (Least Privilege).

Dlaczego pozostałe są błędne:
A. Cloud Storage ACL: ACL nie wspierają filtrowania po adresach IP. Ponadto dostęp bez poświadczeń (credentials) jest sprzeczny z wymogiem braku globalnej czytelności bucketu.
B. Przechowywanie poświadczeń (JSON key) w plikach konfiguracyjnych instancji jest niebezpieczną praktyką. Jeśli maszyna zostanie skompromitowana lub klucze trafią do systemu kontroli wersji, każdy może ich użyć poza tą instancją.
D. Szyfrowanie KMS: To dodatkowa warstwa ochrony danych, ale nie rozwiązuje problemu uwierzytelniania instancji do usługi Cloud Storage. Aplikacja nadal potrzebowałaby tożsamości, aby uzyskać dostęp do klucza KMS.

Wskazówki egzaminacyjne (Tips & Tricks):
- "Compute Engine access to GCP Service" = Zawsze szukaj opcji z "Service Account" i "Metadata Server".
- Unikaj opcji sugerujących przechowywanie kluczy (service account keys) na maszynach wirtualnych.
- Pamiętaj o różnicy między uprawnieniami (IAM) a dostępem (Access Scopes) – obecnie zaleca się ustawianie pełnego dostępu (Cloud-platform scope) i zarządzanie uprawnieniami wyłącznie przez IAM.

Kluczowe zagadnienia do powtórzenia:
- Compute Engine Service Accounts
- Instance Metadata Server
- Principle of Least Privilege in GCP

**Reguła Egzaminacyjna (Exam Rule):**
Zawsze identyfikuj warstwę modelu OSI, na której operuje atak oraz rozwiązanie. DNSSEC działa na poziomie warstwy aplikacji dla DNS, zapobiegając zatruwaniu pamięci podręcznej (Cache Poisoning).

**Haczyki egzaminacyjne (Exam Traps):**
- Mylenie Cloud Armor (WAF - L7) z zabezpieczeniami DNS (DNSSEC - integralność danych DNS).
- Zakładanie, że TLS/SSL wystarczy do ochrony przed przekierowaniem całego ruchu DNS (DNSSEC zabezpiecza sam proces rezolucji, zanim nawiążesz bezpieczne połączenie TLS).

**Głębokie wyjaśnienie techniczne:**
DNSSEC wykorzystuje kryptografię klucza publicznego (RRSIG, DNSKEY, DS) do cyfrowego podpisywania rekordów DNS w strefach (Zone Signing). Dzięki temu resolver DNS może zweryfikować łańcuch zaufania aż do punktu głównego (root zone) bez konieczności polegania wyłącznie na adresie IP serwera autorytatywnego, co drastycznie ogranicza skuteczność ataków typu MITM i cache poisoning.
