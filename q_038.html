Question 38 / 361

A customer's internal security team must manage its own encryption keys for encrypting data on Cloud Storage and decides to use customer-supplied encryption keys (CSEK).
How should the team complete this task?

  • A. Upload the encryption key to a Cloud Storage bucket, and then upload the object to the same bucket.
  • B. Use the gsutil command line tool to upload the object to Cloud Storage, and specify the location of the encryption key.
  • C. Generate an encryption key in the Google Cloud Platform Console, and upload an object to Cloud Storage using the specified key.
  • D. Encrypt the object, then use the gsutil command line tool or the Google Cloud Platform Console to upload the object to Cloud Storage.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

**Poprawna odpowiedź: B**

**1. Kompleksowe wyjaśnienie poprawnej odpowiedzi:**
Klient zdecydował się na użycie kluczy szyfrujących dostarczanych przez użytkownika (Customer-Supplied Encryption Keys - CSEK) w Cloud Storage:
- **Użycie narzędzia gsutil do przesłania obiektu z określeniem lokalizacji klucza szyfrującego na maszynie lokalnej (B):** W przypadku CSEK, Google Cloud nie przechowuje klucza. Klient musi przekazać 256-bitowy klucz AES w nagłówkach żądania przy każdej operacji zapisu i odczytu. Narzędzie `gsutil` obsługuje to poprzez plik konfiguracyjny `.boto` (sekcja `encryption_key`), w którym definiuje się klucz, lub przez odpowiednie flagi w linii poleceń. Dane są szyfrowane po stronie Google przy użyciu dostarczonego w locie klucza.

**2. Wyjaśnienie niepoprawnych odpowiedzi:**
- **A. Upload klucza do tego samego kubła GCS:** Przechowywanie klucza szyfrującego w tym samym miejscu co zaszyfrowane dane (w tym samym kubełku) całkowicie niweczy cel bezpieczeństwa szyfrowania.
- **C. Generowanie klucza w Konsoli GCP i upload:** Konsola GCP nie pozwala na generowanie kluczy CSEK do pobrania. Klucz CSEK musi zostać wygenerowany przez klienta lokalnie i nie może być przechowywany w infrastrukturze Google.
- **D. Ręczne szyfrowanie przed wysłaniem:** Szyfrowanie po stronie klienta (Client-side encryption) to inna technika. Pytanie dotyczy technologii CSEK, w której to Google Cloud wykonuje operację szyfrowania/odszyfrowywania w locie, korzystając z klucza przekazanego przez klienta w żądaniu API.

**3. Wskazówki i pułapki egzaminacyjne (Tips & Tricks):**
- Zapamiętaj: W **CSEK** klucze są przechowywane przez klienta (on-premises) i przekazywane w żądaniu API. Narzędzie `gsutil` konfiguruje się do tego za pomocą pliku `.boto`.
- Konsola GCP (GUI) **nie wspiera** wgrywania ani pobierania plików za pomocą CSEK (wspiera tylko CMEK w KMS).

**4. Reguły wyboru odpowiedzi:**
- CSEK dla Cloud Storage -> Użycie `gsutil` + lokalna konfiguracja klucza (np. w pliku `.boto`).

**5. Dodatkowe źródła:**
- Customer-supplied encryption keys in Cloud Storage: https://cloud.google.com/storage/docs/encryption/customer-supplied-keys

Wyjaśnienie Audytowe

Reguła Egzaminacyjna (Exam Rule):
Pamiętaj, że w egzaminie Professional Cloud Security Engineer kluczowe jest wybieranie rozwiązań najmniej uprzywilejowanych (Principle of Least Privilege), zoptymalizowanych kosztowo i spełniających wymogi compliancy (np. CMEK, Data Loss Prevention).

Haczyki egzaminacyjne (Exam Traps):
- Wybór rozwiązań, które wydają się wygodne, ale nie spełniają wymogów bezpieczeństwa (np. zbyt szerokie uprawnienia IAM).
- Mylenie usług: np. Cloud Armor (WAF) z Cloud IAP (Identity-Aware Proxy).

Głębokie wyjaśnienie techniczne (GCP Professional Cloud Security Engineer):
W każdym pytaniu analizuj warstwy: IAM (dostęp), Encryption (at rest/in transit), Logging/Monitoring (Audit Logs, Cloud Logging, Security Command Center) oraz Networking (VPC Service Controls, Firewall Rules). GCP kładzie duży nacisk na współdzieloną odpowiedzialność (Shared Responsibility Model) - klient odpowiada za konfigurację zabezpieczeń wewnątrz usług chmurowych.
