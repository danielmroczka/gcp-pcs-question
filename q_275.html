Question 275 / 361

Your organization is migrating business critical applications to Google Cloud across multiple projects. You only have the required IAM permission at the Google Cloud organization level. You want to grant project access to support engineers from two partner organizations using their existing identity provider (IdP) credentials. What should you do?

  • A. Create two single sign-on (SSO) profiles for the internal and partner IdPs by using SSO for Cloud Identity.
  • B. Create users manually by using the Google Cloud console. Assign the users to groups.
  • C. Create two workforce identity pools for the partner IdPs.
  • D. Sync user identities from their existing IdPs to Cloud Identity by using Google Cloud Directory Sync (GCDS).
Show Suggested Answer
Suggested Answer: C

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Create two workforce identity pools for the partner IdPs.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź C jest prawidłowa, ponieważ Workforce Identity Federation (Federacja Tożsamości Pracowników) jest najnowocześniejszym i zalecanym przez Google sposobem na nadawanie dostępu do konsoli i API Google Cloud dla użytkowników zewnętrznych (np. inżynierów wsparcia partnerów) przy użyciu ich własnych, istniejących systemów tożsamości (SAML/OIDC), bez konieczności tworzenia dla nich kont w chmurze klienta.

Zalety tego rozwiązania:
a. **Brak synchronizacji tożsamości:** Nie musimy tworzyć kont gości ani synchronizować tożsamości do naszego Cloud Identity (brak narzutu na administrację).
b. **Logowanie federacyjne:** Inżynierowie partnera logują się swoimi firmowymi kontami (np. z Azure AD partnera).
c. **Zarządzanie cyklem życia:** Jeśli pracownik partnera odejdzie z pracy, jego konto zostanie zablokowane w jego lokalnym systemie IdP, co automatycznie odetnie mu dostęp do Twojego GCP, zapewniając wysokie bezpieczeństwo.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Create two single sign-on (SSO) profiles... by using SSO for Cloud Identity.
   * Dlaczego nieprawidłowa: Tradycyjne logowanie jednokrotne (SSO) w Cloud Identity pozwala na skonfigurowanie tylko jednego aktywnego profilu SSO (dostawcy tożsamości) dla całej domeny organizacji. Nie pozwala na jednoczesną federację z wieloma zewnętrznymi IdP partnerów biznesowych w ten sposób bez migracji kont.
B. Create users manually by using the Google Cloud console. Assign the users to groups.
   * Dlaczego nieprawidłowa: Ręczne tworzenie setek kont dla zewnętrznych inżynierów i zarządzanie ich hasłami generuje olbrzymi narzut administracyjny i zwiększa ryzyko pozostawienia aktywnych "kont widmo" (stale aktywne konta byłych pracowników partnera), co narusza zasady bezpieczeństwa.
D. Sync user identities from their existing IdPs to Cloud Identity by using Google Cloud Directory Sync (GCDS).
   * Dlaczego nieprawidłowa: GCDS wymaga bezpośredniego połączenia LDAP (np. Active Directory) i służy do synchronizacji wewnątrz jednej firmy. Synchronizacja tożsamości z zewnętrznych systemów AD partnerów handlowych do Twojej domeny jest technicznie trudna, narusza granice bezpieczeństwa i wymaga tworzenia kont w Twoim systemie Cloud Identity.

4. Wskazówki, hinty, tips and tricks:
* Dostęp do GCP dla zewnętrznych pracowników (partnerzy/kontrahenci) przy użyciu ich własnych IdP -> Zawsze wybieraj **Workforce Identity Federation**.
* Workforce Identity Federation eliminuje potrzebę tworzenia i licencjonowania kont w Twoim Cloud Identity.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Grant project access to partner organizations using their existing IdP -> Create workforce identity pools.
