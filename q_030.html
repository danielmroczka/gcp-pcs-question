Question 30 / 361

A company migrated their entire data/center to Google Cloud Platform. It is running thousands of instances across multiple projects managed by different departments. You want to have a historical record of what was running in Google Cloud Platform at any point in time.
What should you do?

  • A. Use Resource Manager on the organization level.
  • B. Use Forseti Security to automate inventory snapshots.
  • C. Use Stackdriver to create a dashboard across all projects.
  • D. Use Security Command Center to view all assets across the organization.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

Potwierdzona odpowiedź: D (Use Security Command Center to view all assets across the organization.)

Wyjaśnienie:
- Security Command Center (SCC) jest centralnym narzędziem Google Cloud do zarządzania bezpieczeństwem i inwentaryzacją zasobów w całej organizacji. Posiada natywny moduł "Asset Inventory", który pozwala na przeglądanie stanu zasobów w różnych projektach oraz korzystanie z funkcji "Time Travel" (zobacz zasoby tak, jak wyglądały w przeszłości).
- Jest to rozwiązanie w pełni zarządzane i skalowalne, co czyni je obecnie standardem "best practice" w GCP.

Dlaczego pozostałe są błędne:
- A: Resource Manager służy do strukturyzacji, nie do inwentaryzacji historycznej.
- B: Forseti Security to narzędzie open-source, które historycznie wypełniało tę lukę, ale obecnie jest wypierane przez natywne usługi Google, takie jak SCC.
- C: Cloud Monitoring służy do metryk, nie do historycznej inwentaryzacji konfiguracji zasobów.

Wskazówki egzaminacyjne (Tips & Tricks):
- Jeśli widzisz pytanie o inwentaryzację/widoczność zasobów w "skali organizacji" -> wybierz Security Command Center (SCC).
- "Time Travel" zasobów = Cloud Asset Inventory (wbudowane w SCC).

Kluczowe zagadnienia do powtórzenia:
- Security Command Center (Assets, Threats, Vulnerabilities).
- Cloud Asset Inventory i funkcja Time Travel.

Cloud Asset Inventory: Time Travel

**Reguła Egzaminacyjna (Exam Rule):**
Zawsze identyfikuj warstwę modelu OSI, na której operuje atak oraz rozwiązanie. DNSSEC działa na poziomie warstwy aplikacji dla DNS, zapobiegając zatruwaniu pamięci podręcznej (Cache Poisoning).

**Haczyki egzaminacyjne (Exam Traps):**
- Mylenie Cloud Armor (WAF - L7) z zabezpieczeniami DNS (DNSSEC - integralność danych DNS).
- Zakładanie, że TLS/SSL wystarczy do ochrony przed przekierowaniem całego ruchu DNS (DNSSEC zabezpiecza sam proces rezolucji, zanim nawiążesz bezpieczne połączenie TLS).

**Głębokie wyjaśnienie techniczne:**
DNSSEC wykorzystuje kryptografię klucza publicznego (RRSIG, DNSKEY, DS) do cyfrowego podpisywania rekordów DNS w strefach (Zone Signing). Dzięki temu resolver DNS może zweryfikować łańcuch zaufania aż do punktu głównego (root zone) bez konieczności polegania wyłącznie na adresie IP serwera autorytatywnego, co drastycznie ogranicza skuteczność ataków typu MITM i cache poisoning.

Analiza i Podsumowanie Dyskusji (AI)

Analiza i Wyjaśnienie

Sugerowana odpowiedź: B

Analiza spornych kwestii (AI): Społeczność często debatuje między Forseti (B) a SCC (D). SCC faktycznie posiada moduł inwentaryzacyjny, jednak to Forseti został zaprojektowany z myślą o audytowalnych "migawek stanu" (snapshots), które można przechowywać zewnętrznie. Należy jednak pamiętać, że Google obecnie promuje natywną usługę Cloud Asset Inventory, która wspiera funkcję Time Travel, czyniąc Forseti mniej niezbędnym niż kiedyś.
