Question 43 / 361

While migrating your organization's infrastructure to GCP, a large number of users will need to access GCP Console. The Identity Management team already has a well-established way to manage your users and want to keep using your existing Active Directory or LDAP server along with the existing SSO password. What should you do?

  • A. Manually synchronize the data in Google domain with your existing Active Directory or LDAP server.
  • B. Use Google Cloud Directory Sync to synchronize the data in Google domain with your existing Active Directory or LDAP server.
  • C. Users sign in directly to the GCP Console using the credentials from your on-premises Kerberos compliant identity provider.
  • D. Users sign in using OpenID (OIDC) compatible IdP, receive an authentication token, then use that token to log in to the GCP Console.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

Potwierdzona odpowiedź: B (Google Cloud Directory Sync - GCDS)

Wyjaśnienie:
Gdy organizacja posiada już własne źródło tożsamości (Active Directory lub LDAP) i chce zachować istniejące procesy zarządzania użytkownikami podczas migracji do GCP, standardowym rozwiązaniem jest Google Cloud Directory Sync (GCDS).
1. Synchronizacja (Provisioning): GCDS to narzędzie działające lokalnie (on-premises), które jednostronnie synchronizuje dane z AD/LDAP do Cloud Identity lub Google Workspace. Synchronizuje użytkowników, grupy i aliasy.
2. SSO (Single Sign-On): Choć GCDS dba o to, by konta istniały w chmurze, federacja (np. przez SAML 2.0) pozwala użytkownikom na logowanie się przy użyciu ich obecnego hasła z AD.
3. Automatyzacja: GCDS eliminuje konieczność ręcznego tworzenia kont w GCP i zapewnia, że gdy pracownik odejdzie z firmy (zostanie usunięty z AD), jego dostęp do GCP również zostanie automatycznie zablokowany.

Dlaczego pozostałe są błędne:
A. Manualna synchronizacja: Przy "dużej liczbie użytkowników" jest to niewykonalne, podatne na błędy i niebezpieczne (brak automatycznego deprovisioningu).
C. Kerberos: GCP Console nie wspiera bezpośredniego logowania za pomocą biletów Kerberos on-premises bez dodatkowej warstwy federacyjnej.
D. OpenID Connect (OIDC): Choć OIDC jest wspierane, to samo otrzymanie tokena nie wystarczy do zalogowania się do Konsoli GCP bez wcześniejszego istnienia (provisioningu) tożsamości użytkownika w Cloud Identity. Opcja B jest kompletnym rozwiązaniem adresującym potrzebę "zarządzania użytkownikami" (management).

Wskazówki egzaminacyjne (Tips & Tricks):
- "Active Directory/LDAP" + "GCP Identity" = zawsze najpierw myśl o "GCDS".
- GCDS synchronizuje tożsamość, ale NIE synchronizuje haseł (do haseł służy SSO/Federacja lub Google Password Sync).
- Pamiętaj, że GCDS jest procesem jednokierunkowym (AD -> Google).

Kluczowe zagadnienia do powtórzenia:
- Google Cloud Directory Sync (GCDS) architertura.
- SAML 2.0 Federation vs. GCDS.
- Managed vs. Unmanaged users.

Analiza i Podsumowanie Dyskusji (AI)

Analiza i Wyjaśnienie

Sugerowana odpowiedź: B

Analiza spornych kwestii (AI): Kluczowe w pytaniu jest zachowanie "dobrze ustalonego sposobu zarządzania użytkownikami". GCDS pozwala na zachowanie AD jako "Single Source of Truth". Użytkownicy nadal są tworzeni w AD, a GCDS po prostu odzwierciedla te zmiany w Google Cloud. Jest to najmniej inwazyjna metoda migracji tożsamości.

Wyjaśnienie Audytowe

Reguła Egzaminacyjna (Exam Rule):
Pamiętaj, że w egzaminie Professional Cloud Security Engineer kluczowe jest wybieranie rozwiązań najmniej uprzywilejowanych (Principle of Least Privilege), zoptymalizowanych kosztowo i spełniających wymogi compliancy (np. CMEK, Data Loss Prevention).

Haczyki egzaminacyjne (Exam Traps):
- Wybór rozwiązań, które wydają się wygodne, ale nie spełniają wymogów bezpieczeństwa (np. zbyt szerokie uprawnienia IAM).
- Mylenie usług: np. Cloud Armor (WAF) z Cloud IAP (Identity-Aware Proxy).

Głębokie wyjaśnienie techniczne (GCP Professional Cloud Security Engineer):
W każdym pytaniu analizuj warstwy: IAM (dostęp), Encryption (at rest/in transit), Logging/Monitoring (Audit Logs, Cloud Logging, Security Command Center) oraz Networking (VPC Service Controls, Firewall Rules). GCP kładzie duży nacisk na współdzieloną odpowiedzialność (Shared Responsibility Model) - klient odpowiada za konfigurację zabezpieczeń wewnątrz usług chmurowych.
