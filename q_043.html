Question 43 / 361

While migrating your organization's infrastructure to GCP, a large number of users will need to access GCP Console. The Identity Management team already has a well-established way to manage your users and want to keep using your existing Active Directory or LDAP server along with the existing SSO password. What should you do?

  • A. Manually synchronize the data in Google domain with your existing Active Directory or LDAP server.
  • B. Use Google Cloud Directory Sync to synchronize the data in Google domain with your existing Active Directory or LDAP server.
  • C. Users sign in directly to the GCP Console using the credentials from your on-premises Kerberos compliant identity provider.
  • D. Users sign in using OpenID (OIDC) compatible IdP, receive an authentication token, then use that token to log in to the GCP Console.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

**Poprawna odpowiedź: B**

**1. Kompleksowe wyjaśnienie poprawnej odpowiedzi:**
Organizacja migruje użytkowników do GCP i chce zachować istniejący lokalny serwer Active Directory / LDAP jako jedyne źródło prawdy (Single Source of Truth) oraz zachować te same hasła SSO:
- **Użycie Google Cloud Directory Sync (GCDS) do synchronizacji tożsamości z Active Directory/LDAP (B):** GCDS jest darmowym, zalecanym i bezpiecznym narzędziem Google, które instaluje się lokalnie. Łączy się ono z AD/LDAP przez bezpieczne połączenie, odczytuje użytkowników oraz grupy i automatycznie synchronizuje ich konta do Google Cloud Identity/Workspace. GCDS nie synchronizuje haseł bezpośrednio, co pozwala organizacji na wdrożenie SAML SSO (logowania jednokrotnego), dzięki czemu użytkownicy logują się swoimi firmowymi hasłami.

**2. Wyjaśnienie niepoprawnych odpowiedzi:**
- **A. Ręczna synchronizacja:** Przy dużej liczbie użytkowników ("large number of users") ręczne dodawanie i usuwanie kont jest nieefektywne, powolne i podatne na błędy ludzkie (np. nieusunięcie konta zwolnionego pracownika).
- **C. Logowanie bezpośrednio za pomocą Kerberos:** GCP Console nie wspiera bezpośredniego uwierzytelniania protokołem Kerberos z lokalnej domeny bez integracji z dostawcą tożsamości SAML/OIDC.
- **D. Logowanie za pomocą OpenID (OIDC) IdP bez synchronizacji kont:** Nawet przy wdrożonym SSO, użytkownicy wciąż muszą posiadać zsynchronizowane konta tożsamości (szkielety kont) w Cloud Identity, by móc przypisywać im role IAM. OIDC samo z siebie nie tworzy kont w GCP bez wcześniejszej synchronizacji.

**3. Wskazówki i pułapki egzaminacyjne (Tips & Tricks):**
- AD/LDAP jako źródło prawdy -> **Google Cloud Directory Sync (GCDS)** do synchronizacji kont.
- Zapamiętaj: GCDS działa w jedną stronę (ze środowiska lokalnego do chmury Google). Nigdy nie modyfikuje lokalnego Active Directory.

**4. Reguły wyboru odpowiedzi:**
- Synchronizacja kont AD/LDAP do GCP -> GCDS.

**5. Dodatkowe źródła:**
- Google Cloud Directory Sync: https://cloud.google.com/directory-sync/docs

Wyjaśnienie Audytowe

Reguła Egzaminacyjna (Exam Rule):
Pamiętaj, że w egzaminie Professional Cloud Security Engineer kluczowe jest wybieranie rozwiązań najmniej uprzywilejowanych (Principle of Least Privilege), zoptymalizowanych kosztowo i spełniających wymogi compliancy (np. CMEK, Data Loss Prevention).

Haczyki egzaminacyjne (Exam Traps):
- Wybór rozwiązań, które wydają się wygodne, ale nie spełniają wymogów bezpieczeństwa (np. zbyt szerokie uprawnienia IAM).
- Mylenie usług: np. Cloud Armor (WAF) z Cloud IAP (Identity-Aware Proxy).

Głębokie wyjaśnienie techniczne (GCP Professional Cloud Security Engineer):
W każdym pytaniu analizuj warstwy: IAM (dostęp), Encryption (at rest/in transit), Logging/Monitoring (Audit Logs, Cloud Logging, Security Command Center) oraz Networking (VPC Service Controls, Firewall Rules).
