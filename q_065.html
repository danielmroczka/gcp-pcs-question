Question 65 / 361

A customer has an analytics workload running on Compute Engine. Your team created an egress firewall rule to deny (priority 1000) all traffic to the internet. The instances now need to reach out to a public repository for updates. What should you do?

  • A. Create an egress rule to allow traffic to the repository CIDR with priority > 1000.
  • B. Create an egress rule to allow traffic to the repository CIDR with priority < 1000.
  • C. Create an egress rule to allow traffic to the hostname with priority > 1000.
  • D. Create an egress rule to allow traffic to the hostname with priority < 1000.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

PRAWIDŁOWA ODPOWIEDŹ LUB ODPOWIEDZI:

B. Create an egress rule to allow traffic to the repository CIDR with priority < 1000.

KOMPLEKSOWE WYJAŚNIENIE DLACZEGO DANA ODPOWIEDŹ JEST PRAWIDŁOWA (ANALIZA):

W Google Cloud Platform (GCP) mechanizm Google Cloud VPC Firewall Rules jest fundamentalnym narzędziem do kontroli ruchu sieciowego dla instancji Compute Engine oraz innych zasobów w wirtualnych sieciach prywatnych (VPC). Reguły te działają na warstwach 3 i 4 modelu OSI, co oznacza, że filtrują ruch na podstawie adresów IP źródłowych i docelowych (w tym zakresów CIDR), protokołów i numerów portów. Nie operują one na nazwach domenowych (FQDN) ani nazwach hostów, ponieważ są to mechanizmy działające na wyższych warstwach (DNS, warstwa aplikacji).

Kluczowym elementem mechanizmu VPC Firewall Rules jest ich priorytet (priority). W GCP priorytety są reprezentowane przez liczby całkowite z zakresu od 0 do 65535. Bardzo ważne jest, aby zrozumieć, że niższa liczba oznacza wyższy priorytet. Reguły są oceniane w kolejności od najniższego priorytetu (najwyższej ważności) do najwyższego priorytetu (najniższej ważności). Jeśli ruch pasuje do reguły, która ma wyższy priorytet, ta reguła jest stosowana, a dalsze przetwarzanie dla tego konkretnego pakietu zostaje zatrzymane.

W scenariuszu egzaminacyjnym istnieje już reguła typu egress (ruch wychodzący) o priorytecie 1000, która blokuje cały ruch do internetu (deny all traffic to the internet). Aby zezwolić na specyficzny ruch wychodzący do publicznego repozytorium na potrzeby aktualizacji, musimy stworzyć nową regułę zezwalającą (allow) z wyższym priorytetem niż istniejąca reguła blokująca. Oznacza to, że nowa reguła zezwalająca musi mieć priorytet liczbowo mniejszy niż 1000 (np. 999, 500, 100, 0). Dzięki temu, gdy instancja spróbuje nawiązać połączenie z repozytorium, pakiet zostanie najpierw oceniony przez nowo utworzoną regułę "allow" (o niższym numerze priorytetu). Jeśli pakiet pasuje do tej reguły (czyli jego adres docelowy znajduje się w zakresie CIDR repozytorium), zostanie on zezwolony i ruch zostanie przepuszczony, zanim pakiet dotrze do reguły "deny all" o priorytecie 1000.

Ponadto, reguła ta musi precyzować docelowy zakres CIDR (CIDR block) repozytorium. Jest to zgodne z zasadą najmniejszych uprawnień (least privilege), która jest fundamentalną zasadą bezpieczeństwa. Zamiast otwierać ruch do całego internetu, otwieramy go tylko do niezbędnego zakresu adresów IP. To minimalizuje powierzchnię ataku i zwiększa bezpieczeństwo środowiska. Instancje Compute Engine, które potrzebują dostępu do zewnętrznych repozytoriów, typowo łączą się z nimi za pomocą publicznych adresów IP, które można zidentyfikować i ująć w zakresie CIDR.

Podsumowując, opcja B jest prawidłowa, ponieważ:
1.  Określa regułę typu egress (ruch wychodzący), co jest zgodne z potrzebą aktualizacji, czyli pobierania danych z zewnętrznego repozytorium.
2.  Używa zakresu CIDR (CIDR block) do identyfikacji docelowego repozytorium, co jest poprawnym sposobem adresowania w VPC Firewall Rules (warstwa 3).
3.  Ustawia priorytet reguły na wartość mniejszą niż 1000 (priority < 1000), co zapewnia, że reguła zezwalająca zostanie zastosowana przed istniejącą regułą blokującą (deny) o priorytecie 1000.

WYJAŚNIENIE Z OSOBNA KAŻDEJ NIEPOPRAWNEJ ODPOWIEDZI:

A. Create an egress rule to allow traffic to the repository CIDR with priority > 1000.
   Ta opcja jest błędna ze względu na priorytet. Chociaż poprawnie identyfikuje potrzebę reguły typu egress i używa CIDR do określenia celu, to ustawienie priorytetu większego niż 1000 (np. 1001, 2000) oznaczałoby, że nowa reguła zezwalająca ma niższy priorytet (mniejszą ważność) niż istniejąca reguła blokująca (deny) o priorytecie 1000. W efekcie, gdy pakiet trafiłby do firewalla, najpierw zostałaby zastosowana reguła o priorytecie 1000 (deny all), która zablokowałaby ruch, zanim reguła o priorytecie > 1000 (allow) miałaby szansę zostać oceniona. Ruch do repozytorium nadal byłby blokowany.

C. Create an egress rule to allow traffic to the hostname with priority > 1000.
   Ta opcja jest błędna z dwóch głównych powodów:
   1.  Filtrowanie po nazwach hostów (hostname): Google Cloud VPC Firewall Rules działają na poziomie warstw 3 i 4, co oznacza, że operują na adresach IP (zakresach CIDR) i portach. Nie mają wbudowanej funkcji rozumienia i filtrowania ruchu na podstawie nazw domenowych (FQDN) lub nazw hostów. Firewall nie jest serwerem DNS ani proxy aplikacyjnym. Aby filtrować ruch do konkretnego hosta, musiałbyś znać i podać jego adres IP lub zakres CIDR.
   2.  Priorytet: Podobnie jak w opcji A, ustawienie priorytetu większego niż 1000 jest nieprawidłowe. Reguła zezwalająca z niższym priorytetem (wyższą liczbą) niż reguła blokująca o priorytecie 1000 nigdy nie zostanie zastosowana dla blokowanego ruchu.

D. Create an egress rule to allow traffic to the hostname with priority < 1000.
   Ta opcja jest błędna z tego samego powodu co opcja C w odniesieniu do filtrowania. Google Cloud VPC Firewall Rules nie obsługują filtrowania po nazwach hostów (hostname). Nawet jeśli priorytet (priority < 1000) byłby poprawny dla reguły zezwalającej w kontekście kolidujących reguł, to podstawowa mechanika filtrowania po nazwie hosta jest niekompatybilna z funkcjonalnością VPC Firewall.

WSKAZÓWKI, HINTY, TIPS AND TRICKS:

1.  Zawsze zwracaj uwagę na priorytety: To jedna z najczęstszych pułapek w pytaniach dotyczących VPC Firewall Rules. Zapamiętaj: Niższa liczba priorytetu = Wyższy priorytet (reguła jest oceniana i stosowana wcześniej). Jeśli masz regułę "deny all" o priorytecie X i chcesz stworzyć regułę "allow" dla specyficznego ruchu, musi ona mieć priorytet Y, gdzie Y < X.
2.  VPC Firewall to Layer 3/4: Firewall działa na adresach IP (CIDR) i portach, nie na nazwach domenowych (FQDN) ani nazwach hostów. To kolejna bardzo częsta pułapka egzaminacyjna. Jeśli pytanie mówi o "hostname" lub "domain name" w kontekście celu reguły firewall, niemal zawsze jest to odpowiedź błędna, chyba że istnieje dodatkowy mechanizm (np. Cloud DNS Firewall, ale to inny produkt).
3.  Zrozum kierunek ruchu (Egress vs. Ingress): Pamiętaj, że egress dotyczy ruchu wychodzącego z instancji/sieci, a ingress dotyczy ruchu przychodzącego do instancji/sieci. W tym pytaniu potrzeba aktualizacji oznacza ruch wychodzący, więc reguła egress jest prawidłowa.
4.  Zasada Least Privilege: Zawsze, gdy to możliwe, szukaj odpowiedzi, która ogranicza dostęp do absolutnego minimum. Zezwolenie na ruch do konkretnego zakresu CIDR jest znacznie bezpieczniejsze niż zezwolenie na ruch do "całego internetu".
5.  Domyślne reguły: Pamiętaj o domyślnych regułach w każdej sieci VPC, takich jak default-allow-internal, default-allow-ssh, default-allow-rdp, oraz default-deny-all-egress. Chociaż w tym przypadku mamy niestandardową regułę "deny all egress", świadomość domyślnych zachowań jest kluczowa.

REGUŁY WYBORU ODPOWIEDZI (SŁOWA KLUCZOWE):

1.  Jeśli pytanie wspomina o "deny all traffic" lub "deny all egress" z określonym priorytetem, a celem jest "allow specific traffic", szukaj odpowiedzi zawierającej:
    *   "allow" w typie reguły.
    *   "priority < [priorytet_reguły_deny]".
    *   "CIDR" lub "IP address range" jako docelową specyfikację.

2.  Gdy celem jest kontrola ruchu "to the internet" lub "to a public repository" z instancji Compute Engine, zawsze wybieraj reguły typu "egress".

3.  Jeśli w opcjach odpowiedzi pojawiają się terminy takie jak "hostname", "FQDN" lub "domain name" jako cel reguły firewall, a nie ma mowy o specyficznym produkcie GCP filtrującym na warstwie 7 (np. Cloud Load Balancing z URL maps, Cloud DNS Firewall), prawie zawsze jest to pułapka i opcja jest błędna w kontekście standardowych VPC Firewall Rules.

4.  W przypadku pytania o "firewall rule priority", kluczowym elementem do zapamiętania jest "niższa liczba = wyższy priorytet". Opcje, które sugerują wyższą liczbę priorytetu dla reguły "allow" w celu nadpisania reguły "deny", są błędne.
