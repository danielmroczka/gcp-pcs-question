Question 184 / 361

You have a highly sensitive BigQuery workload that contains personally identifiable information (PII) that you want to ensure is not accessible from the internet. To prevent data exfiltration, only requests from authorized IP addresses are allowed to query your BigQuery tables.
What should you do?

  • A. Use service perimeter and create an access level based on the authorized source IP address as the condition.
  • B. Use Google Cloud Armor security policies defining an allowlist of authorized IP addresses at the global HTTPS load balancer.
  • C. Use the Restrict Resource Service Usage organization policy constraint along with Cloud Data Loss Prevention (DLP).
  • D. Use the Restrict allowed Google Cloud APIs and services organization policy constraint along with Cloud Data Loss Prevention (DLP).
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

Poprawna odpowiedź: A (Use service perimeter and create an access level based on the authorized source IP address as the condition)

Dlaczego ta odpowiedź jest poprawna:
- VPC Service Controls (VPC SC): Jest to najsilniejszy mechanizm ochrony przed eksfiltracją danych w Google Cloud. Pozwala on na stworzenie perymetru wokół usług takich jak BigQuery.
- Service Perimeter (Perymetr serwisowy): Gdy BigQuery zostanie dodane do perymetru, dostęp do jego API jest domyślnie blokowany dla wszystkich żądań spoza perymetru (w tym z internetu).
- Access Level (Poziom dostępu): Aby pozwolić na dostęp z konkretnych, autoryzowanych adresów IP, należy stworzyć Poziom Dostępu w Access Context Manager. Warunkiem w tym poziomie dostępu będzie lista dozwolonych adresów IP.
- Wynik: Połączenie perymetru z poziomem dostępu sprawia, że BigQuery jest "niewidoczne" dla całego internetu, z wyjątkiem ruchu pochodzącego z dokładnie zdefiniowanych przez Ciebie adresów IP, co idealnie spełnia wymagania bezpieczeństwa.

Analiza niepoprawnych odpowiedzi:
- B. Google Cloud Armor: Cloud Armor służy do ochrony aplikacji webowych znajdujących się za External HTTP(S) Load Balancerem. Nie służy on do bezpośredniego filtrowania ruchu do natywnego API BigQuery. Cloud Armor nie zapobiega eksfiltracji danych z BigQuery w taki sposób jak VPC SC.
- C. Restrict Resource Service Usage policy: Ta polityka organizacji pozwala na zablokowanie użycia konkretnych usług w projekcie (np. "nikt nie może używać Cloud SQL"), ale nie oferuje filtrowania dostępu na podstawie adresów IP dla dozwolonej już usługi BigQuery.
- D. Restrict allowed Google Cloud APIs: Podobnie jak w opcji C, ta polityka ogranicza listę API, które mogą być włączone/używane, ale nie zapewnia granularnej kontroli dostępu opartej na sieciowej tożsamości klienta (IP).

Wskazówki i triki (Tips & Tricks):
- "Prevent data exfiltration" + "BigQuery" = VPC Service Controls.
- "Context-aware access" / "IP-based restriction for Google APIs" = VPC SC + Access Levels.
- Pamiętaj: IAM mówi "kto", VPC SC mówi "skąd" i "dokąd" mogą płynąć dane.

Praktyczne informacje na egzamin:
- VPC SC chroni przed sytuacją, w której pracownik (nawet z uprawnieniami Admina) próbuje skopiować dane do prywatnego projektu spoza firmy.
- Access Levels są częścią "BeyondCorp Enterprise" i pozwalają na weryfikację nie tylko IP, ale także stanu urządzenia (np. czy ma włączone szyfrowanie dysku).

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: A

Analiza strategiczna: To pytanie testuje zrozumienie architektury bezpieczeństwa API Google Cloud. Większość usług Google jest dostępna pod publicznymi adresami URL (np. bigquery.googleapis.com). Same uprawnienia IAM to za mało dla danych wrażliwych. VPC SC to "ściana", która zamyka te publiczne endpointy i wpuszcza tylko autoryzowany ruch z zaufanych lokalizacji (Access Levels).

Dodatkowe wskazówki

  • VPC SC wymaga włączenia Private Google Access w sieciach VPC, które mają komunikować się z BigQuery wewnątrz perymetru.
  • Pamiętaj o trybie "Dry-run", który pozwala testować perymetr bez ryzyka przerwania działania aplikacji produkcyjnych.
