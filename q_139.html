Question 139 / 361

You are backing up application logs to a shared Cloud Storage bucket that is accessible to both the administrator and analysts. Analysts should not have access to logs that contain any personally identifiable information (PII). Log files containing PII should be stored in another bucket that is only accessible to the administrator. What should you do?

  • A. Upload the logs to both the shared bucket and the bucket with PII that is only accessible to the administrator. Use the Cloud Data Loss Prevention API to create a job trigger. Configure the trigger to delete any files that contain PII from the shared bucket.
  • B. On the shared bucket, configure Object Lifecycle Management to delete objects that contain PII.
  • C. On the shared bucket, configure a Cloud Storage trigger that is only triggered when PII is uploaded. Use Cloud Functions to capture the trigger and delete the files that contain PII.
  • D. Use Pub/Sub and Cloud Functions to trigger a Cloud Data Loss Prevention scan every time a file is uploaded to the administrator's bucket. If the scan does not detect PII, have the function move the objects into the shared Cloud Storage bucket.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
D. Use Pub/Sub and Cloud Functions to trigger a Cloud Data Loss Prevention scan every time a file is uploaded to the administrator's bucket. If the scan does not detect PII, have the function move the objects into the shared Cloud Storage bucket.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Wymagane jest archiwizowanie logów aplikacji w kubełku Cloud Storage. Analitycy nie mogą mieć dostępu do plików zawierających dane osobowe (PII), natomiast administrator musi mieć dostęp do wszystkich plików (w tym tych z PII):
- Prawidłowe podejście z punktu widzenia bezpieczeństwa zakłada zasadę "Secure Ingestion". Wszystkie surowe logi są najpierw wysyłane do bezpiecznego kubełka administratora (niedostępnego dla analityków).
- Powiadomienie o nowym pliku w kubełku administratora jest wysyłane przez Pub/Sub do Cloud Functions. Funkcja ta uruchamia skanowanie pliku za pomocą Cloud DLP API.
- Jeśli skanowanie wykaże, że plik jest czysty (brak PII), funkcja przenosi go do współdzielonego kubełka dla analityków. W ten sposób analitycy nigdy nie mają kontaktu z surowym plikiem przed weryfikacją, co eliminuje ryzyko przypadkowego wycieku danych.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
- A. Przesyłanie do obu kubełków i usuwanie z PII za pomocą DLP: Stwarza poważne ryzyko bezpieczeństwa (race condition). Plik z danymi PII pojawia się we współdzielonym kubełku i jest tam dostępny dla analityków, dopóki asynchroniczne skanowanie DLP go nie wykryje i nie usunie.
- B. Użycie Object Lifecycle Management na kubełku: Reguły cyklu życia obiektów w Cloud Storage służą do automatycznej zmiany klas przechowywania (np. na Archive) lub usuwania starych plików na podstawie wieku. Nie posiadają funkcji analizy zawartości plików pod kątem danych osobowych (PII).
- C. Wyzwalacz Cloud Storage reagujący na PII: Wyzwalacze Cloud Storage (GCS Triggers) reagują na zdarzenia obiektowe (np. utworzenie obiektu, usunięcie), ale nie potrafią badać zawartości plików pod kątem PII bez integracji z zewnętrznym silnikiem skanującym (DLP).

4. Wskazówki, hinty, tips and tricks:
- W projektowaniu przepływów danych (Data Pipeline Security): **nigdy nie wrzucaj potencjalnie wrażliwych danych bezpośrednio do strefy publicznej/współdzielonej** z zamiarem ich późniejszego usunięcia. Zawsze filtruj dane w strefie prywatnej przed ich udostępnieniem.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
- Blokowanie dostępu analityków do PII przed weryfikacją -> Zapis do bezpiecznego bucketu -> Skan DLP przez Cloud Function -> Przeniesienie czystych plików do shared bucketu.
