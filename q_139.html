Question 139 / 361

You are backing up application logs to a shared Cloud Storage bucket that is accessible to both the administrator and analysts. Analysts should not have access to logs that contain any personally identifiable information (PII). Log files containing PII should be stored in another bucket that is only accessible to the administrator. What should you do?

  • A. Upload the logs to both the shared bucket and the bucket with PII that is only accessible to the administrator. Use the Cloud Data Loss Prevention API to create a job trigger. Configure the trigger to delete any files that contain PII from the shared bucket.
  • B. On the shared bucket, configure Object Lifecycle Management to delete objects that contain PII.
  • C. On the shared bucket, configure a Cloud Storage trigger that is only triggered when PII is uploaded. Use Cloud Functions to capture the trigger and delete the files that contain PII.
  • D. Use Pub/Sub and Cloud Functions to trigger a Cloud Data Loss Prevention scan every time a file is uploaded to the administrator's bucket. If the scan does not detect PII, have the function move the objects into the shared Cloud Storage bucket.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

Potwierdzona odpowiedź: D (Use Pub/Sub and Cloud Functions to trigger a Cloud Data Loss Prevention scan every time a file is uploaded to the administrator's bucket. If the scan does not detect PII, have the function move the objects into the shared Cloud Storage bucket).

Wyjaśnienie:
- Bezpieczeństwo przede wszystkim (Security first): Najbezpieczniejszym podejściem jest przesyłanie logów najpierw do bezpiecznego, odizolowanego miejsca (bucket administratora), a dopiero po weryfikacji udostępnianie ich szerszemu gronu (analitykom).
- Proces automatyzacji:
  1. Logi trafiają do bucketu administratora.
  2. Powiadomienie o nowym pliku (Cloud Storage Notification) trafia do Pub/Sub.
  3. Pub/Sub wyzwala Cloud Function.
  4. Funkcja wywołuje DLP API w celu przeskanowania pliku pod kątem PII.
  5. Jeśli wynik skanowania jest negatywny (brak PII), funkcja przenosi plik do współdzielonego bucketu analityków.

Dlaczego pozostałe są błędne:
- A. Upload do obu + usuwanie: To podejście jest niebezpieczne (Race Condition). Istnieje okno czasowe, w którym analitycy mogą odczytać logi z PII zanim DLP zdąży je wykryć i usunąć.
- B. Object Lifecycle Management: Ta funkcja służy do zarządzania wiekiem obiektów lub ich wersjami (np. przenoszenie do Coldline lub usuwanie po 30 dniach). Nie potrafi ona skanować zawartości plików pod kątem PII.
- C. Cloud Storage trigger na PII upload: Triggery GCS reagują na zdarzenia techniczne (finalize, delete, metadata update), a nie na zawartość merytoryczną pliku. Trigger sam w sobie nie "wie", czy w pliku jest PII.

Wskazówki egzaminacyjne (Tips & Tricks):
- Jeśli musisz odfiltrować dane wrażliwe przed ich udostępnieniem, zawsze wybieraj schemat: [Miejsce Bezpieczne] -> [Skanowanie DLP] -> [Miejsce Współdzielone].
- Unikaj rozwiązań, które udostępniają dane "na chwilę" z zamiarem ich późniejszego usunięcia.

Kluczowe zagadnienia do powtórzenia:
- Cloud Data Loss Prevention (DLP) API.
- Integracja Cloud Storage z Cloud Functions i Pub/Sub.
- Zasada Least Privilege w dostępie do danych.
