Question 64 / 361

In an effort for your company messaging app to comply with FIPS 140-2, a decision was made to use GCP compute and network services. The messaging app architecture includes a Managed Instance Group (MIG) that controls a cluster of Compute Engine instances. The instances use Local SSDs for data caching and UDP for instance-to-instance communications. The app development team is willing to make any changes necessary to comply with the standard. Which options should you recommend to meet the requirements?

  • A. Encrypt all cache storage and VM-to-VM communication using the BoringCrypto module.
  • B. Set Disk Encryption on the Instance Template used by the MIG to customer-managed key and use BoringSSL for all data transit between instances.
  • C. Change the app instance-to-instance communications from UDP to TCP and enable BoringSSL on clients' TLS connections.
  • D. Set Disk Encryption on the Instance Template used by the MIG to Google-managed Key and use BoringSSL library on all instance-to-instance communications.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

Potwierdzona odpowiedź: A (Encrypt all cache storage and VM-to-VM communication using the BoringCrypto module.)

Wyjaśnienie:
FIPS 140-2 to amerykański standard federalny określający wymagania bezpieczeństwa dla modułów kryptograficznych. Google używa biblioteki `BoringSSL`, która zawiera moduł `BoringCrypto`, posiadający certyfikację FIPS 140-2.
1. BoringCrypto: Aby aplikacja działająca na infrastrukturze Google była w pełni zgodna z FIPS, musi używać certyfikowanych modułów do wszelkich operacji kryptograficznych – zarówno dla danych "at rest" (w tym przypadku cache na Local SSD), jak i danych "in transit" (komunikacja między instancjami).
2. Local SSD: Domyślne szyfrowanie GCP chroni dane na dyskach, ale w przypadku rygorystycznych wymogów FIPS na poziomie aplikacji, to aplikacja sama powinna zarządzać szyfrowaniem przy użyciu zatwierdzonego modułu (BoringCrypto).
3. UDP/TCP: Standard FIPS nie zabrania używania UDP, ale wymaga, aby sama kryptografia użyta do zabezpieczenia tego ruchu była zgodna ze standardem.

Dlaczego pozostałe są błędne:
B, D: Skupiają się na zarządzaniu kluczami (CMEK/GMEK), co jest istotne, ale samo zarządzanie kluczem nie gwarantuje, że *moduł użyty do szyfrowania* (biblioteka wewnątrz aplikacji) posiada certyfikat FIPS 140-2.
C: Zmiana protokołu z UDP na TCP nie jest wymagana przez FIPS. Kluczem jest biblioteka kryptograficzna, a nie protokół warstwy transportowej.

Tips & Tricks:
- Słowo "FIPS 140-2" w kontekście Google Cloud = "BoringCrypto" lub "BoringSSL".
- Google Cloud posiada certyfikację FIPS dla swojej infrastruktury, ale aplikacje klienta muszą same zadbać o użycie odpowiednich bibliotek, aby zachować zgodność na poziomie "Guest OS" i wyżej.
- Local SSD w GKE/GCE są szyfrowane domyślnie, ale certyfikacja FIPS na poziomie aplikacji wymaga jawnego użycia certyfikowanego modułu.

Zagadnienia:
- FIPS 140-2 Compliance in GCP.
- BoringCrypto module (Google's FIPS-validated library).
- Encryption at rest vs. Encryption in transit requirements.

Sugerowana odpowiedź: A

Głęboka analiza: Wybór BoringCrypto zapewnia, że operacje takie jak `AES-GCM` czy `SHA-256` są wykonywane przez kod, który przeszedł rygorystyczne testy NIST. Jest to niezbędne dla klientów z sektora publicznego i regulowanego.
