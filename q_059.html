Question 59 / 361

A patch for a vulnerability has been released, and a DevOps team needs to update their running containers in Google Kubernetes Engine (GKE). How should the DevOps team accomplish this?

  • A. Use Puppet or Chef to push out the patch to the running container.
  • B. Verify that auto upgrade is enabled; if so, Google will upgrade the nodes in a GKE cluster.
  • C. Update the application code or apply a patch, build a new image, and redeploy it.
  • D. Configure containers to automatically upgrade when the base image is available in Container Registry.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C (Update the application code or apply a patch, build a new image, and redeploy it.)

Wyjaśnienie:
Kontenery w ekosystemie Docker/Kubernetes są z założenia niemutowalne (immutable). Oznacza to, że nie powinno się ich patchować "na żywo" w trakcie działania. Prawidłowy proces aktualizacji (tzw. "Cloud-native way") polega na:
1. Naniesieniu poprawek w kodzie źródłowym lub pliku Dockerfile.
2. Zbudowaniu nowego obrazu kontenera z nowym tagiem (wersją).
3. Przesłaniu obrazu do rejestru (np. Artifact Registry).
4. Wykonaniu nowej instalacji (redeploy) w klastrze GKE (np. za pomocą `kubectl set image` lub aktualizacji manifestu Deployment), co spowoduje, że Kubernetes automatycznie zastąpi stare kontenery nowymi (Rolling Update).

Dlaczego pozostałe są błędne:
A. Puppet/Chef: Narzędzia do zarządzania konfiguracją są świetne dla systemów operacyjnych maszyn wirtualnych, ale nie dla kontenerów. Kontener powinien być traktowany jako "jednorazowy" – jeśli wymaga zmiany, tworzy się nowy.
B. Node Auto-upgrade: To ustawienie dotyczy aktualizacji systemu operacyjnego i oprogramowania samych węzłów (maszyn wirtualnych) klastra GKE, a nie aplikacji działających w kontenerach na tych węzłach.
D. Auto-upgrade kontenerów: W GKE nie ma wbudowanego mechanizmu, który automatycznie wykrywa nowy obraz w rejestrze i samoczynnie aktualizuje działające kontenery bez zewnętrznego wyzwalacza (np. CI/CD pipeline).

Tips & Tricks:
- "Immutability" (Niemutowalność) to słowo klucz w świecie kontenerów. Pamiętaj: nie naprawiaj kontenera, wymień go na nowy.
- Na egzaminie Google Cloud zawsze wybieraj odpowiedzi promujące standardowe cykle CI/CD (Build -> Image -> Deploy).

Analiza i Wyjaśnienie

Sugerowana odpowiedź: C

Praktyczne wnioski: Strategia "Build once, deploy anywhere" wymaga, aby obrazy były wersjonowane. Nigdy nie używaj tagu `:latest` w produkcji, ponieważ utrudnia to proces wycofywania zmian (rollback) i śledzenie, co faktycznie działa na klastrze.
