Question 220 / 361

You manage one of your organization's Google Cloud projects (Project A). A VPC Service Control (SC) perimeter is blocking API access requests to this project, including Pub/Sub. A resource running under a service account in another project (Project B) needs to collect messages from a Pub/Sub topic in your project. Project B is not included in a VPC SC perimeter. You need to provide access from Project B to the Pub/Sub topic in Project A using the principle of least privilege.
What should you do?

  • A. Configure an ingress policy for the perimeter in Project A, and allow access for the service account in Project B to collect messages.
  • B. Create an access level that allows a developer in Project B to subscribe to the Pub/Sub topic that is located in Project A.
  • C. Create a perimeter bridge between Project A and Project B to allow the required communication between both projects.
  • D. Remove the Pub/Sub API from the list of restricted services in the perimeter configuration for Project A.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

Poprawna odpowiedź: A (Configure an ingress policy for the perimeter in Project A, and allow access for the service account in Project B to collect messages)

Dlaczego ta odpowiedź jest poprawna:
- VPC Service Controls (VPC SC): Chroni zasoby (jak temat Pub/Sub w Projekcie A) przed eksfiltracją i nieautoryzowanym dostępem. Perymetr domyślnie blokuje dostęp z zewnątrz.
- Ingress Rule (Reguła przychodząca): Aby umożliwić dostęp z Projeku B (który jest poza perymetrem) do zasobu w Projekcie A (wewnątrz perymetru), należy skonfigurować regułę Ingress dla perymetru w Projekcie A.
- Zasada najniższych uprawnień: Reguła Ingress pozwala precyzyjnie wskazać "kto" (konto serwisowe z Projektu B) i "jaki zasób" (temat Pub/Sub w Projekcie A) mogą się komunikować, co jest zgodne z zasadą najniższych uprawnień.

Analiza niepoprawnych odpowiedzi:
- B. Access level: Poziomy dostępu (Access Levels) definiują kontekst (np. IP, certyfikat), ale same w sobie nie dają uprawnień do przełamania blokady perymetru. Muszą być powiązane z regułą Ingress, aby zadziałały w tym kontekście.
- C. Perimeter bridge: Most (bridge) łączy dwa perymetry. W tym przypadku Projekt B NIE jest w perymetrze, więc bridge nie ma zastosowania (nie ma czego łączyć).
- D. Remove Pub/Sub API: To podejście "wszystko albo nic". Usunięcie usługi z listy restricted wyłącza ochronę dla tej usługi w całym projekcie, co narusza zasady bezpieczeństwa (otwierasz dostęp dla każdego, zamiast precyzyjnie dla konta serwisowego).

Wskazówki i triki (Tips & Tricks):
- "Cross-perimeter access" / "Access from outside perimeter" = Ingress Rule.
- "Project B is outside" = Ingress rule on A's perimeter.
- Pamiętaj: Ingress rule definiuje, kto z zewnątrz może pukać do wnętrza perymetru.

Praktyczne informacje na egzamin:
- Reguły Ingress działają na poziomie API. Musisz podać `serviceName` (np. `pubsub.googleapis.com`) i konkretną metodę (jeśli potrzeba).
- Zawsze weryfikuj, czy konto serwisowe w Projekcie B ma też nadane uprawnienia IAM (np. `roles/pubsub.subscriber`), ponieważ VPC SC tylko "pozwala" na żądanie API, ale IAM wciąż decyduje, czy użytkownik ma uprawnienia do wykonania operacji.

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: A

Analiza strategiczna: VPC Service Controls to narzędzie typu "Zero Trust" dla usług Google Cloud. Ingress rules są "bezpiecznymi furtkami" w tym perymetrze. Zrozumienie, że musisz dopuścić tożsamość z zewnątrz (Ingress) do wnętrza, jest kluczową umiejętnością dla inżyniera bezpieczeństwa zarządzającego wieloma projektami.

Dodatkowe wskazówki

  • Możesz testować reguły za pomocą trybu "Dry-run", aby nie zepsuć komunikacji produkcyjnej.
  • Pamiętaj: jeśli konto serwisowe w Projekcie B zmienia się, musisz zaktualizować regułę Ingress w Projekcie A.
