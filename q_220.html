Question 220 / 361

You manage one of your organization's Google Cloud projects (Project A). A VPC Service Control (SC) perimeter is blocking API access requests to this project, including Pub/Sub. A resource running under a service account in another project (Project B) needs to collect messages from a Pub/Sub topic in your project. Project B is not included in a VPC SC perimeter. You need to provide access from Project B to the Pub/Sub topic in Project A using the principle of least privilege. What should you do?

  • A. Configure an ingress policy for the perimeter in Project A, and allow access for the service account in Project B to collect messages.
  • B. Create an access level that allows a developer in Project B to subscribe to the Pub/Sub topic that is located in Project A.
  • C. Create a perimeter bridge between Project A and Project B to allow the required communication between both projects.
  • D. Remove the Pub/Sub API from the list of restricted services in the perimeter configuration for Project A.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
A. Configure an ingress policy for the perimeter in Project A, and allow access for the service account in Project B to collect messages.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź A jest prawidłowa, ponieważ zasady wejściowe (Ingress Policies) w VPC Service Controls (VPC SC) pozwalają na bezpieczne dopuszczenie ruchu z zasobów znajdujących się poza perymetrem bezpieczeństwa (Project B) do zasobów chronionych wewnątrz perymetru (Project A) na podstawie tożsamości konta serwisowego, bez konieczności rozszerzania perymetru na cały zewnętrzny projekt.

Mechanizm ten działa w następujący sposób:
a. Projekt A jest chroniony przez perymetr, co oznacza, że wszelki nieautoryzowany ruch przychodzący do jego API (w tym Pub/Sub) z zewnątrz perymetru jest domyślnie blokowany.
b. Zamiast tworzyć most (perimeter bridge) łączący całe projekty, konfigurujemy regułę Ingress w perymetrze Projektu A.
c. Reguła Ingress definiuje tożsamość źródłową (konto serwisowe z Projektu B) oraz dozwoloną operację docelową (usługę Pub/Sub w Projekcie A). Spełnia to zasadę najmniejszych uprawnień (least privilege), ponieważ dopuszcza tylko jedno, konkretne konto serwisowe i tylko dla usługi Pub/Sub.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
B. Create an access level that allows a developer in Project B to subscribe...
   * Dlaczego nieprawidłowa: Poziomy dostępu (Access Levels) bazują głównie na atrybutach sieciowych (np. IP, geolokalizacja, stan urządzenia) i służą do uwierzytelniania użytkowników za pomocą Access Context Manager. Nie są one przeznaczone do precyzyjnej autoryzacji komunikacji między kontami serwisowymi w różnych projektach przez granicę perymetru.
C. Create a perimeter bridge between Project A and Project B...
   * Dlaczego nieprawidłowa: Perymetr mostu (Perimeter Bridge) łączy dwa projekty, które oba znajdują się wewnątrz jakichś perymetrów. Ponieważ Projekt B nie jest częścią żadnego perymetru, stworzenie mostu jest niemożliwe. Nawet gdyby było możliwe, dałoby to zbyt szeroki dostęp, naruszając zasadę least privilege.
D. Remove the Pub/Sub API from the list of restricted services...
   * Dlaczego nieprawidłowa: Usunięcie Pub/Sub z listy usług chronionych całkowicie pozbawiłoby ochrony całą usługę Pub/Sub w Projekcie A dla wszystkich zasobów, co jest poważnym osłabieniem profilu bezpieczeństwa organizacji.

4. Wskazówki, hinty, tips and tricks:
* Aby kontrolować ruch przez perymetr VPC SC:
  - Ruch przychodzący (spoza perymetru do środka) -> **Ingress Policy**.
  - Ruch wychodzący (ze środka perymetru na zewnątrz) -> **Egress Policy**.
* Unikaj wyłączania ochrony API (opcja D) w celach rozwiązywania problemów z dostępem dla pojedynczych klientów.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Dostęp spoza perymetru do chronionego projektu w perymetrze -> Ingress policy dla perymetru.
