Question 33 / 361

A customer wants to move their sensitive workloads to a Compute Engine-based cluster using Managed Instance Groups (MIGs). The jobs are bursty and must be completed quickly. They have a requirement to be able to control the key lifecycle.
Which boot disk encryption solution should you use on the cluster to meet this customer's requirements?

  • A. Customer-supplied encryption keys (CSEK)
  • B. Customer-managed encryption keys (CMEK) using Cloud Key Management Service (KMS)
  • C. Encryption by default
  • D. Pre-encrypting files before transferring to Google Cloud Platform (GCP) for analysis
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

Potwierdzona odpowiedź: B (Customer-managed encryption keys (CMEK) using Cloud Key Management Service (KMS))

Wyjaśnienie: 
Customer-Managed Encryption Keys (CMEK) to rozwiązanie w Google Cloud, które daje administratorowi pełną kontrolę nad cyklem życia kluczy szyfrujących (tworzenie, rotacja, wyłączanie, niszczenie) za pośrednictwem usługi Cloud KMS. CMEK jest w pełni zintegrowany z Managed Instance Groups (MIG). W Instance Template (szablonie instancji) można wskazać klucz KMS, a Google automatycznie użyje go do zaszyfrowania dysków systemowych (boot disks) każdej nowo powstającej instancji w ramach grupy. Jest to kluczowe przy obciążeniach typu "bursty", gdzie skalowanie (tworzenie nowych VM) musi odbywać się całkowicie automatycznie i bez opóźnień.

Dlaczego pozostałe są błędne:
A. Customer-supplied encryption keys (CSEK): Rozwiązanie to wymaga podania surowego klucza (raw key) w każdym żądaniu utworzenia dysku lub startu maszyny. Ponieważ MIG-i zarządzają instancjami automatycznie (Google samo tworzy VM w odpowiedzi na obciążenie), system nie miałby dostępu do Twojego klucza CSEK bez Twojej ręcznej interwencji przy każdym skalowaniu, co uniemożliwia automatyzację procesów.
C. Encryption by default: To szyfrowanie przy użyciu kluczy zarządzanych przez Google (GMEK). W tym modelu klient nie ma żadnej kontroli nad kluczem (nie może go rotować, unieważnić ani usunąć), co bezpośrednio narusza wymóg "control the key lifecycle".
D. Pre-encrypting files: Szyfrowanie plików przed ich wysłaniem chroni jedynie dane, a nie całe dyski systemowe maszyn wirtualnych. Nie rozwiązuje problemu bezpieczeństwa infrastruktury Compute Engine i jest trudne w zarządzaniu przy skalowaniu.

Wskazówki egzaminacyjne (Tips & Tricks):
- "MIG" / "Autoscaling" + "Control key lifecycle": To zawsze wskazuje na CMEK (KMS).
- "Control" = CMEK (Twoje klucze w KMS). "Supply" = CSEK (Twoje klucze poza chmurą). "Default" = GMEK (Klucze Google).
- Zapamiętaj: CSEK i automatyczne skalowanie (MIG/GKE) nie są ze sobą kompatybilne w pełni zautomatyzowany sposób.

Kluczowe zagadnienia do powtórzenia:
- Różnice między GMEK, CMEK i CSEK
- Integracja Cloud KMS z zasobami Compute Engine
- Działanie Instance Templates w grupach MIG

Sugerowana odpowiedź: B

Analiza spornych kwestii (AI): W przypadku CMEK, nadajesz specjalnemu kontu serwisowemu Google (Compute Service Agent) rolę 'CryptoKey Encrypter/Decrypter'. Dzięki temu Google może w Twoim imieniu automatycznie tworzyć zaszyfrowane dyski podczas skalowania MIG, zachowując jednocześnie Twoją władzę nad kluczem w KMS (np. możesz go w każdej chwili zniszczyć, uniemożliwiając odczyt danych).
