Question 327 / 361

Your organization is migrating its primary web application from on-premises to Google Kubernetes Engine (GKE). You must advise the development team on how to grant their applications access to Google Cloud services from within GKE according to security recommended practices. What should you advise the development team to do?

  • A. Configure the GKE nodes to use the default Compute Engine service account.
  • B. Enable Workload Identity for GKE. Assign a Kubernetes service account to the application and configure that Kubernetes service account to act as an Identity and Access Management (IAM) service account. Grant the required roles to the IAM service account.
  • C. Create a user-managed service account with only the roles required for the specific workload. Assign this service account to the GKE nodes.
  • D. Create an application-specific IAM service account and generate a user-managed service account key for it. Inject the key to the workload by storing it as a Kubernetes secret within the same namespace as the application.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

✅ PRAWIDŁOWA ODPOWIEDŹ: B

Prawidłowa odpowiedź: B – Enable Workload Identity for GKE. Assign a Kubernetes service account to the application and configure IAM to allow the Kubernetes service account to act as a Google service account with only the required permissions.

DLACZEGO B JEST PRAWIDŁOWE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Workload Identity to Google-recommended metoda dla aplikacji GKE do dostępu do Google Cloud APIs:
- Eliminuje potrzebę service account keys (klucze JSON = ryzyko wycieku).
- Kubernetes SA jest powiązany z Google SA przez IAM.
- Granularne uprawnienia (tylko wymagane role).
- Automatyczna rotacja tokenów.
- Nie wymaga przechowywania sekretów.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
DLACZEGO INNE OPCJE SĄ BŁĘDNE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
A. ❌ Default Compute Engine SA = zbyt szerokie domyślne uprawnienia (Editor). Naruszenie least privilege.
C. ❌ User-managed SA z przypisaniem do node pool = SA jest dla WSZYSTKICH podów na nodzie, nie dla konkretnej aplikacji. Brak izolacji.
D. ❌ SA key file = antywzorzec. Klucze JSON są długoterminowe, trudne do rotacji i mogą wyciec. Google rekomenduje Workload Identity zamiast kluczy.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WSKAZÓWKI EGZAMINACYJNE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• GKE + Google APIs = Workload Identity (zawsze, gdy pytanie mówi "recommended").
• Unikaj SA key files (JSON keys) – to antywzorzec bezpieczeństwa.
• Default SA = zbyt szerokie uprawnienia.
• Workload Identity = per-pod uprawnienia (nie per-node).

• GKE application → Google APIs = Workload Identity (Google recommended).
• Nigdy SA key files dla GKE workloads w produkcji.
