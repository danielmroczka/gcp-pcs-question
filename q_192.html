Question 192 / 361

Your organization is rolling out a new continuous integration and delivery (CI/CD) process to deploy infrastructure and applications in Google Cloud. Many teams will use their own instances of the CI/CD workflow. It will run on Google Kubernetes Engine (GKE). The CI/CD pipelines must be designed to securely access Google Cloud APIs. What should you do?

  • A. 1. Create two service accounts, one for the infrastructure and one for the application deployment. 2. Use workload identities to let the pods run the two pipelines and authenticate with the service accounts. 3. Run the infrastructure and application pipelines in separate namespaces.
  • B. 1. Create a dedicated service account for the CI/CD pipelines. 2. Run the deployment pipelines in a dedicated nodes pool in the GKE cluster. 3. Use the service account that you created as identity for the nodes in the pool to authenticate to the Google Cloud APIs.
  • C. 1. Create individual service accounts for each deployment pipeline. 2. Add an identifier for the pipeline in the service account naming convention. 3. Ensure each pipeline runs on dedicated pods. 4. Use workload identity to map a deployment pipeline pod with a service account.
  • D. 1. Create service accounts for each deployment pipeline. 2. Generate private keys for the service accounts. 3. Securely store the private keys as Kubernetes secrets accessible only by the pods that run the specific deploy pipeline.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

Potwierdzona odpowiedź: A (1. Create two service accounts, one for the infrastructure and one for the application deployment. 2. Use workload identities to let the pods run the two pipelines and authenticate with the service accounts. 3. Run the infrastructure and application pipelines in separate namespaces).

Wyjaśnienie:
- Workload Identity: Jest to najbezpieczniejszy i zalecany przez Google sposób uwierzytelniania aplikacji działających w GKE (w tym pipeline'ów CI/CD) do usług Google Cloud. Eliminuje potrzebę generowania, pobierania i przechowywania statycznych kluczy JSON (Service Account Keys), które są częstym źródłem wycieków danych.
- Mapowanie Tożsamości: Workload Identity wiąże konto serwisowe Kubernetes (KSA) z kontem serwisowym Google Cloud (GSA). Dzięki temu pod działający w klastrze automatycznie otrzymuje tokeny tożsamości GSA z serwera metadanych.
- Separacja Obowiązków (Separation of Duties): Użycie dwóch osobnych kont serwisowych (dla infrastruktury i dla aplikacji) oraz odrębnych przestrzeni nazw (namespaces) zapewnia silną izolację. Pipeline infrastrukturalny (wymagający wyższych uprawnień, np. Project Editor) jest odseparowany od pipeline'u aplikacyjnego (wymagającego zazwyczaj tylko uprawnień do deploymentu obrazu).

Dlaczego pozostałe odpowiedzi są niepoprawne:
- B. Node Pool Service Account: Nadanie wysokich uprawnień całemu węzłowi (node) sprawia, że KAŻDY pod działający na tym węźle ma te same uprawnienia. Jest to skrajnie niebezpieczne i narusza zasadę Least Privilege. Workload Identity nadaje uprawnienia konkretnym podom, a nie całym maszynom.
- C. Individual SA for each pipeline: Choć jest to technicznie poprawne i bardzo granularne, opcja A jest częściej spotykana na egzaminie jako standardowy model separacji "Infra vs App". W opcji C brakuje również wzmianki o separacji na poziomie Namespace, co jest kluczowe dla izolacji w GKE.
- D. Kubernetes Secrets: Przechowywanie kluczy JSON w sekretach Kubernetes jest lepsze niż trzymanie ich w kodzie, ale wciąż gorsze niż Workload Identity. Klucze wciąż muszą być rotowane i mogą zostać wykradzione przy kompromitacji klastra.

Wskazówki egzaminacyjne (Tips & Tricks):
- "GKE" + "Access Google Cloud APIs" + "Secure" = Workload Identity.
- Jeśli widzisz "Service Account Keys" lub "JSON keys" w opcjach dla GKE, zazwyczaj jest to błędna odpowiedź.
- Pamiętaj: Workload Identity wymaga włączenia na poziomie klastra ORAZ na poziomie puli węzłów.

Kluczowe zagadnienia do powtórzenia:
- Workload Identity w GKE.
- Zasada najniższych uprawnień (Least Privilege) w GKE.
- Uwierzytelnianie między GKE a Google Cloud APIs.

Analiza i Wyjaśnienie

Sugerowana odpowiedź: A

Głęboka analiza: To pytanie testuje znajomość nowoczesnych standardów bezpieczeństwa kontenerów. Przejście od uprawnień "maszyny" (Node SA) do uprawnień "procesu" (Workload Identity) jest fundamentalną zmianą w architekturze chmurowej. Separacja namespaces dodatkowo utrudnia ataki typu "lateral movement" wewnątrz klastra.
