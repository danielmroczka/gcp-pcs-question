Question 192 / 361

Your organization is rolling out a new continuous integration and delivery (CI/CD) process to deploy infrastructure and applications in Google Cloud. Many teams will use their own instances of the CI/CD workflow. It will run on Google Kubernetes Engine (GKE). The CI/CD pipelines must be designed to securely access Google Cloud APIs. What should you do?

  • A. 1. Create two service accounts, one for the infrastructure and one for the application deployment. 2. Use workload identities to let the pods run the two pipelines and authenticate with the service accounts. 3. Run the infrastructure and application pipelines in separate namespaces.
  • B. 1. Create a dedicated service account for the CI/CD pipelines. 2. Run the deployment pipelines in a dedicated nodes pool in the GKE cluster. 3. Use the service account that you created as identity for the nodes in the pool to authenticate to the Google Cloud APIs.
  • C. 1. Create individual service accounts for each deployment pipeline. 2. Add an identifier for the pipeline in the service account naming convention. 3. Ensure each pipeline runs on dedicated pods. 4. Use workload identity to map a deployment pipeline pod with a service account.
  • D. 1. Create service accounts for each deployment pipeline. 2. Generate private keys for the service accounts. 3. Securely store the private keys as Kubernetes secrets accessible only by the pods that run the specific deploy pipeline.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
A. 1. Create two service accounts, one for the infrastructure and one for the application deployment. 2. Use workload identities to let the pods run the two pipelines and authenticate with the service accounts. 3. Run the infrastructure and application pipelines in separate namespaces.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Zadaniem jest zaprojektowanie bezpiecznego uwierzytelniania dla procesów CI/CD wdrażających infrastrukturę oraz aplikacje w Google Cloud, uruchomionych na klastrze Google Kubernetes Engine (GKE).
Zgodnie z najlepszymi praktykami Google Cloud:
1. **Zasada najniższych uprawnień oraz separacja obowiązków (Separation of Duties):** Pipeline wdrożeniowy infrastruktury (który tworzy sieci, maszyny itp.) potrzebuje znacznie wyższych uprawnień (np. Editor/Owner lub dedykowane role administracyjne) niż pipeline aplikacyjny (który tylko aktualizuje wdrożenie kontenera). Tworzymy więc dwa oddzielne konta serwisowe (GCP Service Accounts).
2. **Bezpieczne uwierzytelnianie w GKE:** Do uwierzytelniania podów w GKE do API Google Cloud należy stosować **Workload Identity**. Eliminuje to konieczność generowania i przechowywania statycznych kluczy prywatnych (JSON keys) wewnątrz klastra, co chroni przed ich wyciekiem. Workload Identity wiąże konto serwisowe Kubernetes (KSA) z kontem serwisowym Google Cloud (GSA).
3. **Izolacja sieciowa i logiczna klastra:** Uruchomienie pipeline'ów w osobnych przestrzeniach nazw (namespaces) w Kubernetes zapewnia silną izolację ról RBAC oraz konfiguracji sekretów i zasobów między procesami wdrożenia infrastruktury i aplikacji.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
- B. Use the service account that you created as identity for the nodes in the pool...: Przypisanie konta serwisowego o wysokich uprawnieniach bezpośrednio do węzłów (Node Service Account) sprawia, że każdy pod uruchomiony w danej puli maszyn dziedziczy te same uprawnienia. Narusza to podstawowe zasady bezpieczeństwa (Least Privilege).
- C. Create individual service accounts for each deployment pipeline... Use workload identity...: Ta opcja proponuje tworzenie indywidualnych kont dla każdego pojedynczego pipeline'u oraz użycie identyfikatora w nazwie konta, co w dużej skali prowadzi do dużego narzutu administracyjnego. Przede wszystkim jednak opcja ta pomija kluczowy element bezpieczeństwa – izolację na poziomie przestrzeni nazw (namespaces) w GKE, co uniemożliwia pełne rozdzielenie uprawnień wewnątrz klastra Kubernetes.
- D. Generate private keys for the service accounts. Securely store the private keys as Kubernetes secrets...: Korzystanie ze statycznych kluczy prywatnych kont serwisowych (JSON service account keys) w klastrze GKE jest złą praktyką i niesie ryzyko kompromitacji. Zawsze należy dążyć do eliminacji statycznych kluczy na rzecz tożsamości dynamicznych (Workload Identity).

4. Wskazówki, hinty, tips and tricks:
- W pytaniach dotyczących bezpiecznego dostępu aplikacji/podów działających w **GKE** do zasobów/API Google Cloud (np. Cloud Storage, BigQuery), prawidłowa odpowiedź niemal zawsze wskazuje na **Workload Identity**.
- Zawsze unikaj odpowiedzi sugerujących pobieranie kluczy prywatnych kont serwisowych (JSON keys) lub nadawanie wysokich uprawnień do kont węzłów (Node Service Accounts).

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
- "GKE" + "securely access Google Cloud APIs" + "CI/CD pipelines" -> Workload Identity + separate namespaces.

6. Dodatkowe źródła i dokumentacja:
- GKE Workload Identity: https://cloud.google.com/kubernetes-engine/docs/how-to/workload-identity

Analiza i Wyjaśnienie

Sugerowana odpowiedź: A

Głęboka analiza: To pytanie testuje znajomość nowoczesnych standardów bezpieczeństwa kontenerów. Przejście od uprawnień "maszyny" (Node SA) do uprawnień "procesu" (Workload Identity) jest fundamentalną zmianą w architekturze chmurowej. Separacja namespaces dodatkowo utrudnia ataki typu "lateral movement" wewnątrz klastra.
