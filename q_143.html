Question 143 / 361

Your organization hosts a financial services application running on Compute Engine instances for a third-party company. The third-party company's servers that will consume the application also run on Compute Engine in a separate Google Cloud organization. You need to configure a secure network connection between the Compute Engine instances. You have the following requirements:
- The network connection must be encrypted.
- The communication between servers must be over private IP addresses.
What should you do?

  • A. Configure a Cloud VPN connection between your organization's VPC network and the third party's that is controlled by VPC firewall rules.
  • B. Configure a VPC peering connection between your organization's VPC network and the third party's that is controlled by VPC firewall rules.
  • C. Configure a VPC Service Controls perimeter around your Compute Engine instances, and provide access to the third party via an access level.
  • D. Configure an Apigee proxy that exposes your Compute Engine-hosted application as an API, and is encrypted with TLS which allows access only to the third party.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

Potwierdzona odpowiedź: A (Configure a Cloud VPN connection...)

Wyjaśnienie:
Cloud VPN umożliwia bezpieczne połączenie dwóch sieci VPC (nawet w różnych organizacjach) za pomocą tunelu IPsec. Spełnia oba kluczowe wymagania zadania: ruch jest szyfrowany (protokół IPsec gwarantuje szyfrowanie w warstwie sieciowej) oraz odbywa się za pomocą prywatnych adresów IP (RFC 1918). Jest to standardowe rozwiązanie w GCP do bezpiecznego łączenia odizolowanych środowisk różnych organizacji, gdzie wymagane jest dodatkowe szyfrowanie tunelu.

Dlaczego pozostałe są błędne:
B. VPC Peering: Chociaż pozwala na komunikację po prywatnych adresach IP, a Google domyślnie szyfruje ruch wewnątrz swojej sieci (encryption-in-transit), w kontekście egzaminacyjnym Cloud VPN jest wskazywany jako rozwiązanie spełniające wymóg "encrypted connection" w sposób jawny i konfigurowalny przez użytkownika. Peering jest częściej wybierany dla wydajności, ale VPN jest odpowiedzią na wymóg specyficznego "szyfrowanego połączenia" (IPsec).
C. VPC Service Controls: To rozwiązanie służy do tworzenia obwodów bezpieczeństwa (perimeters) wokół usług zarządzanych (API Google), a nie do nawiązywania bezpośredniej łączności L3 między instancjami Compute Engine.
D. Apigee proxy: Jest to rozwiązanie warstwy aplikacji (L7). Chociaż obsługuje TLS, nie spełnia wymogu bezpośredniej komunikacji między serwerami po prywatnych adresach IP w sposób natywny dla infrastruktury sieciowej VPC.

Wskazówki egzaminacyjne (Tips & Tricks):
- Jeśli widzisz wymagania: "Encrypted" + "Private IP" + "Separate Organizations/Networks" -> najsilniejszym kandydatem jest Cloud VPN.
- VPC Peering jest zazwyczaj odpowiedzią, gdy nacisk kładzie się na "Performance" lub "Low Latency" i "Private IP".

Kluczowe zagadnienia do powtórzenia:
- Różnice między VPC Peering a Cloud VPN.
- Scenariusze hybrydowe i między-organizacyjne.
- Szyfrowanie w tranzycie w GCP.

Analiza i Podsumowanie Dyskusji (AI)

Analiza i Wyjaśnienie

Sugerowana odpowiedź: A

Analiza spornych kwestii (AI): Głównym punktem debaty jest wybór między Cloud VPN (A) a VPC Peering (B). Google domyślnie szyfruje cały ruch między centrami danych (MACsec), więc Peering technicznie jest bezpieczny. Jednakże, jeśli wymaganie egzaminacyjne wyraźnie podkreśla potrzebę szyfrowanego połączenia ("network connection must be encrypted"), zazwyczaj oczekuje się wyboru Cloud VPN, który tworzy jawny tunel IPsec. Wersja B jest poprawna technicznie w wielu scenariuszach, ale A jest "bezpieczniejszą" odpowiedzią egzaminacyjną przy takim sformułowaniu wymagań.
