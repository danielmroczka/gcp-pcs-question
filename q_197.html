Question 197 / 361

You run applications on Cloud Run. You already enabled container analysis for vulnerability scanning. However, you are concerned about the lack of control on the applications that are deployed. You must ensure that only trusted container images are deployed on Cloud Run. What should you do? (Choose two.)

  • A. Enable Binary Authorization on the existing Cloud Run service.
  • B. Set the organization policy constraint constraints/run.allowedBinaryAuthorizationPolicies to the list or allowed Binary Authorization policy names.
  • C. Enable Binary Authorization on the existing Kubernetes cluster.
  • D. Use Cloud Run breakglass to deploy an image that meets the Binary Authorization policy by default.
  • E. Set the organization policy constraint constraints/compute.trustedImageProjects to the list of projects that contain the trusted container images.
Show Suggested Answer Hide Answer
Suggested Answer: AB

Wyjaśnienie

Potwierdzona odpowiedź: AB (A. Enable Binary Authorization on the existing Cloud Run service, B. Set the organization policy constraint constraints/run.allowedBinaryAuthorizationPolicies to the list or allowed Binary Authorization policy names).

Wyjaśnienie:
- Binary Authorization (BinAuthz): Jest to usługa bezpieczeństwa Google Cloud, która działa jako "strażnik" (gatekeeper) przy wdrażaniu kontenerów. Pozwala ona na zdefiniowanie polityk, które sprawdzają, czy obraz kontenera spełnia określone wymogi (np. czy został zbudowany w zaufanym pipeline, czy posiada atestację zespołu security).
- A. Włączenie BinAuthz na Cloud Run: Aby Cloud Run zaczął weryfikować obrazy przed uruchomieniem, musisz jawnie włączyć funkcję Binary Authorization dla danej usługi Cloud Run (można to zrobić w ustawieniach usługi lub przez gcloud).
- B. Polityka Organizacji: Aby zapewnić spójną kontrolę w całej firmie, należy użyć polityki organizacji `constraints/run.allowedBinaryAuthorizationPolicies`. Pozwala ona na wymuszenie, aby wszystkie usługi Cloud Run korzystały wyłącznie z zatwierdzonych i zdefiniowanych centralnie polityk Binary Authorization, co uniemożliwia deweloperom omijanie zabezpieczeń.

Dlaczego pozostałe odpowiedzi są niepoprawne:
- C. BinAuthz on Kubernetes cluster: To pytanie dotyczy Cloud Run (usługa serverless), a nie klastrów GKE. Choć BinAuthz działa na GKE, włączenie go tam nie zabezpieczy wdrożeń na Cloud Run – to osobne integracje.
- D. Breakglass: Funkcja "breakglass" służy do celowego OMINIĘCIA polityki w sytuacjach awaryjnych (incydenty). Użycie jej domyślnie przeczy celowi pytania, którym jest "zapewnienie, że tylko zaufane obrazy są wdrażane".
- E. trustedImageProjects: Ta polityka organizacji dotyczy obrazów maszyn wirtualnych (Compute Engine), a nie obrazów kontenerów (Docker/OCI) wdrażanych w Artifact Registry lub Cloud Run.

Wskazówki egzaminacyjne (Tips & Tricks):
- "Trusted container images" + "Cloud Run" / "GKE" = Binary Authorization.
- Szukaj słowa "Attestors" (osoby/systemy poświadczające) w podobnych pytaniach o podpisywanie obrazów.
- Pamiętaj: Binary Authorization sprawdza obraz w momencie wdrożenia (deployment), a nie w czasie budowania (build). To ostatnia linia obrony przed nieautoryzowanym kodem.

Kluczowe zagadnienia do powtórzenia:
- Binary Authorization dla Cloud Run i GKE.
- Atestacje (Attestations) i Atesorzy (Attestors).
- Polityki Organizacji dla usług serverless.

Analiza i Wyjaśnienie

Sugerowana odpowiedź: AB

Głęboka analiza: To pytanie testuje Twoją znajomość mechanizmów kontroli wdrożeń (Deployment Governance). W środowiskach mikroserwisowych łatwo o wdrożenie nieprzetestowanego lub złośliwego kodu. Binary Authorization w połączeniu z polityką organizacji daje zespołowi security gwarancję, że na produkcji (Cloud Run) działają tylko te bity, które zostały oficjalnie zatwierdzone przez CI/CD.
