Question 74 / 361

What are the steps to encrypt data using envelope encryption?

  • A. Generate a data encryption key (DEK) locally. Use a key encryption key (KEK) to wrap the DEK. Encrypt data with the KEK. Store the encrypted data and the wrapped DEK.
  • B. Generate a key encryption key (KEK) locally. Use the KEK to generate a data encryption key (DEK). Encrypt data with the DEK. Store the encrypted data and the wrapped DEK.
  • C. Generate a data encryption key (DEK) locally. Encrypt data with the DEK. Use a key encryption key (KEK) to wrap the DEK. Store the encrypted data and the wrapped DEK.
  • D. Generate a key encryption key (KEK) locally. Generate a data encryption key (DEK) locally. Encrypt data with the KEK. Store the encrypted data and the wrapped DEK.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C (Generate a data encryption key (DEK) locally. Encrypt data with the DEK. Use a key encryption key (KEK) to wrap the DEK. Store the encrypted data and the wrapped DEK.)

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Prawidłowa odpowiedź C precyzyjnie opisuje standardową sekwencję kroków w procesie szyfrowania kopertowego (envelope encryption), która jest szeroko stosowana w Google Cloud Platform (GCP), zwłaszcza z wykorzystaniem usługi Cloud Key Management Service (Cloud KMS). Szyfrowanie kopertowe to kluczowa technika zapewniająca zarówno bezpieczeństwo, jak i wydajność szyfrowania dużych ilości danych.

Mechanizmy leżące u podstaw tej opcji:
Szyfrowanie kopertowe opiera się na idei użycia dwóch rodzajów kluczy:
   Data Encryption Key (DEK): Jest to klucz używany do szyfrowania bezpośrednio samych danych (tzw. plaintext data). DEK jest zazwyczaj krótkotrwałym, losowo generowanym kluczem symetrycznym, który jest generowany przez aplikację kliencką (stąd "locally" w opisie). Szyfrowanie danych DEK-iem jest szybkie i efektywne dla dużych bloków danych.
   Key Encryption Key (KEK): Jest to klucz używany do szyfrowania (owijania, "wrapping") klucza DEK. KEK jest kluczem długoterminowym, o wyższej wartości bezpieczeństwa, który jest przechowywany i zarządzany w bezpiecznym środowisku, takim jak Hardware Security Module (HSM) lub usługa Key Management System (KMS), np. Google Cloud KMS. KEK nigdy nie opuszcza tego bezpiecznego środowiska i jest używany wyłącznie do ochrony innych kluczy, a nie bezpośrednio danych użytkownika.

Sekwencja kroków w szyfrowaniu kopertowym:
1.  Generowanie DEK lokalnie: Aplikacja kliencka, która chce zaszyfrować dane, generuje losowy DEK. Jest to klucz symetryczny.
2.  Szyfrowanie danych DEK-iem: Aplikacja używa wygenerowanego DEK do zaszyfrowania danych użytkownika. Wynikiem jest zaszyfrowana treść (ciphertext).
3.  Szyfrowanie (owijanie) DEK-a KEK-iem: Zamiast przechowywać DEK w postaci jawnej, co byłoby niebezpieczne, DEK jest szyfrowany (owijany) za pomocą KEK przechowywanego w KMS. Aplikacja wysyła DEK do KMS, który używa KEK do jego zaszyfrowania i zwraca zaszyfrowany DEK (tzw. wrapped DEK).
4.  Przechowywanie zaszyfrowanych danych i owiniętego DEK-a: Aplikacja przechowuje zaszyfrowane dane oraz odpowiadający im zaszyfrowany (wrapped) DEK. Ważne jest, aby KEK nigdy nie był przechowywany razem z danymi. KEK pozostaje bezpiecznie w KMS.

Dlaczego jest to zalecana praktyka w GCP i dlaczego jest lepsza, bezpieczniejsza i bardziej skalowalna:
Bezpieczeństwo:
   Separacja odpowiedzialności kluczy: KEK, jako master key, pozostaje zawsze w KMS. Tylko owinięty DEK opuszcza KMS. Zmniejsza to ryzyko kompromitacji klucza głównego.
   Klucze efemeryczne: DEK jest generowany "na żądanie" i używany tylko do konkretnej operacji szyfrowania danych. Może być szybko unieważniony lub po prostu zapomniany po użyciu, co minimalizuje czas ekspozycji klucza.
   Audyt i kontrola dostępu: Operacje związane z KEK (owijanie/rozwijanie DEK) są centralnie logowane i kontrolowane przez IAM w Cloud KMS, co pozwala na granularne zarządzanie uprawnieniami i audytowanie użycia kluczy.

Wydajność i skalowalność:
   Lokalne szyfrowanie danych: Szyfrowanie dużych ilości danych za pomocą lokalnie wygenerowanego DEK jest znacznie szybsze niż wysyłanie całych danych do KMS w celu zaszyfrowania ich KEK-iem. Komunikacja z KMS jest ograniczona do małego DEK-a, a nie do całej zawartości danych.
   Mniejsze obciążenie KMS: KMS służy tylko do operacji na kluczach (owijanie/rozwijanie), a nie do szyfrowania bulk data. To pozwala KMS na obsługę większej liczby operacji kluczowych i zapewnia jego wysoką dostępność i skalowalność.
   Elastyczność: Możliwość przechowywania zaszyfrowanych danych i owiniętych DEK-ów w dowolnym miejscu (np. Cloud Storage, baza danych) bez konieczności bezpośredniego dostępu KMS do miejsca przechowywania danych.

Podsumowując, opcja C przedstawia prawidłową, bezpieczną, wydajną i skalowalną metodę szyfrowania kopertowego, która jest fundamentalnym wzorcem bezpieczeństwa w chmurze.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
Opcja A. Generate a data encryption key (DEK) locally. Use a key encryption key (KEK) to wrap the DEK. Encrypt data with the KEK. Store the encrypted data and the wrapped DEK.
   Błąd w tej opcji polega na kroku "Encrypt data with the KEK". W szyfrowaniu kopertowym klucz KEK (Key Encryption Key) służy wyłącznie do szyfrowania innych kluczy (DEK), a nie bezpośrednio do szyfrowania danych użytkownika. Szyfrowanie dużych ilości danych bezpośrednio za pomocą KEK-a zarządzanego przez KMS byłoby nieefektywne (wymagałoby przesyłania wszystkich danych do KMS) i bardzo kosztowne, a także naruszałoby fundamentalną zasadę separacji odpowiedzialności kluczy. Celem szyfrowania kopertowego jest odciążenie KMS od operacji na dużych danych i zapewnienie, że KEK nigdy nie opuszcza bezpiecznego środowiska KMS.

Opcja B. Generate a key encryption key (KEK) locally. Use the KEK to generate a data encryption key (DEK). Encrypt data with the DEK. Store the encrypted data and the wrapped DEK.
   Ta opcja zawiera dwa główne błędy:
   1.  "Generate a key encryption key (KEK) locally": Klucze KEK, jako klucze nadrzędne i długoterminowe, zawsze powinny być generowane i zarządzane w bezpiecznym środowisku Key Management System (KMS) lub Hardware Security Module (HSM). Generowanie KEK-a "lokalnie" przez aplikację kliencką byłoby poważnym naruszeniem bezpieczeństwa, ponieważ taki klucz byłby narażony na kompromitację poza chronionym środowiskiem. KEK jest fundamentem łańcucha zaufania w szyfrowaniu kopertowym.
   2.  "Use the KEK to generate a data encryption key (DEK)": KEK nie jest używany do "generowania" DEK-a. DEK jest niezależnie generowany jako losowy ciąg bitów. KEK jest używany do "owijania" (szyfrowania) już istniejącego DEK-a. Chociaż KMS może oferować funkcje generowania kluczy, to w kontekście szyfrowania kopertowego, DEK jest zazwyczaj generowany przez klienta, a następnie wysyłany do KMS w celu owinięcia.

Opcja D. Generate a key encryption key (KEK) locally. Generate a data encryption key (DEK) locally. Encrypt data with the KEK. Store the encrypted data and the wrapped DEK.
   Ta opcja łączy błędy z opcji A i B:
   1.  "Generate a key encryption key (KEK) locally": Jak wyjaśniono dla opcji B, KEK nigdy nie powinien być generowany lokalnie przez aplikację kliencką. Musi być bezpiecznie zarządzany w KMS.
   2.  "Encrypt data with the KEK": Jak wyjaśniono dla opcji A, KEK służy do szyfrowania DEK-a, a nie bezpośrednio danych użytkownika. Ten krok jest niezgodny z zasadami szyfrowania kopertowego.

4. Wskazówki, hinty, tips and tricks:
   Zrozumienie ról DEK i KEK: Najważniejsze jest jasne rozróżnienie funkcji Data Encryption Key (DEK) i Key Encryption Key (KEK). DEK szyfruje DANE (Data), KEK szyfruje KLUCZE (Key, czyli DEK-a). Pamiętaj o tej hierarchii.
   Kolejność operacji: Zawsze zwracaj uwagę na kolejność kroków. Prawidłowa sekwencja to: generowanie DEK -> szyfrowanie DANYCH DEK-iem -> owijanie DEK-a KEK-iem -> przechowywanie zaszyfrowanych danych i owiniętego DEK-a.
   Lokalne generowanie a KMS: Klucze DEK są generowane "lokalnie" przez aplikację, ponieważ mają być krótkotrwałe i efemeryczne. Klucze KEK są zawsze zarządzane przez KMS i nigdy nie opuszczają jego bezpiecznej granicy; nie są generowane "lokalnie" przez aplikację kliencką.
   Cel szyfrowania kopertowego: Pamiętaj, że szyfrowanie kopertowe ma na celu oddzielenie klucza do szyfrowania danych od master keya, zwiększenie wydajności (nie wysyłasz wszystkich danych do KMS) i poprawę skalowalności. Każda opcja, która narusza te zasady, jest prawdopodobnie nieprawidłowa.
   Terminologia "wrap": Zwróć uwagę na termin "wrap" (owijać). Jest to standardowe określenie na szyfrowanie klucza przez inny klucz (DEK przez KEK).
   Pułapki językowe: Uważaj na subtelne różnice w sformułowaniach. Na przykład, "generate DEK using KEK" jest nieprawidłowe, podczas gdy "encrypt/wrap DEK using KEK" jest prawidłowe.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
   Jeśli pytanie wspomina o "envelope encryption" lub "szyfrowaniu kopertowym", zawsze szukaj odpowiedzi, która przedstawia następującą sekwencję:
      Klucz DEK jest generowany przez klienta.
      DEK jest używany do szyfrowania danych.
      Klucz KEK jest używany do szyfrowania (owijania, "wrapping") klucza DEK.
      Nigdy nie zaszyfrowano danych bezpośrednio za pomocą KEK.
      Klucz KEK jest zawsze zarządzany przez KMS, nie jest generowany "lokalnie" przez klienta.
   Gdy celem jest bezpieczne i wydajne szyfrowanie dużych zbiorów danych w chmurze przy użyciu usług KMS, prawidłowa odpowiedź będzie odzwierciedlać proces, w którym większość pracy szyfrującej odbywa się poza KMS (przez DEK), a KMS odpowiada za ochronę tylko kluczy (KEK chroni DEK).
   Jeśli opcja sugeruje, że KEK jest generowany "lokalnie" lub używany do bezpośredniego szyfrowania danych, zazwyczaj jest to pułapka i nieprawidłowa odpowiedź.
