Question 42 / 361

A DevOps team will create a new container to run on Google Kubernetes Engine. As the application will be internet-facing, they want to minimize the attack surface of the container. What should they do?

  • A. Use Cloud Build to build the container images.
  • B. Build small containers using small base images.
  • C. Delete non-used versions from Container Registry.
  • D. Use a Continuous Delivery tool to deploy the application.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

**Poprawna odpowiedź: B**

**1. Kompleksowe wyjaśnienie poprawnej odpowiedzi:**
Wymaganiem jest zminimalizowanie powierzchni ataku kontenera działającego w GKE, ponieważ będzie on wystawiony bezpośrednio na ruch z internetu:
- **Budowanie małych kontenerów przy użyciu minimalnych obrazów bazowych (B):** Im mniejszy obraz bazowy (np. `alpine`, `distroless` lub czysty `scratch`), tym mniej bibliotek, narzędzi pomocniczych (takich jak shell, curl, kompilatory) i kodu znajduje się wewnątrz kontenera. W przypadku wykrycia luki w aplikacji, napastnik nie będzie miał dostępu do tych narzędzi systemowych, co drastycznie ogranicza jego możliwości eskalacji uprawnień i poruszania się wewnątrz klastra.

**2. Wyjaśnienie niepoprawnych odpowiedzi:**
- **A. Użycie Cloud Build:** Cloud Build to narzędzie CI/CD do budowania obrazów. Samo użycie tego narzędzia nie gwarantuje, że powstały kontener będzie bezpieczny i będzie miał małą powierzchnię ataku (zależy to od definicji Dockerfile).
- **C. Usuwanie nieużywanych wersji z Container Registry:** Pomaga oszczędzać miejsce na dysku w rejestrze obrazów, ale nie ma żadnego wpływu na bezpieczeństwo i powierzchnię ataku kontenera, który jest już uruchomiony w klastrze GKE.
- **D. Użycie narzędzia Continuous Delivery:** Automatyzuje proces wdrożenia aplikacji, ale nie wpływa na bezpieczeństwo wewnętrzne obrazu kontenerowego.

**3. Wskazówki i pułapki egzaminacyjne (Tips & Tricks):**
- Złota zasada bezpieczeństwa kontenerów: **"Czego nie ma w obrazie kontenera, tego nie da się wykorzystać do ataku"**. Dlatego standardem w produkcji są obrazy typu **distroless** (nie zawierają nawet basha).
- Mniejszy rozmiar obrazu to również szybsze pobieranie (lepsze skalowanie podów w GKE) oraz szybsze skanowanie podatności.

**4. Reguły wyboru odpowiedzi:**
- Minimalizacja powierzchni ataku kontenera -> Małe, dedykowane obrazy bazowe (minimal base images/distroless).

**5. Dodatkowe źródła:**
- Best practices for building containers: https://cloud.google.com/architecture/best-practices-for-building-containers

Wyjaśnienie Audytowe

Reguła Egzaminacyjna (Exam Rule):
Pamiętaj, że w egzaminie Professional Cloud Security Engineer kluczowe jest wybieranie rozwiązań najmniej uprzywilejowanych (Principle of Least Privilege), zoptymalizowanych kosztowo i spełniających wymogi compliancy (np. CMEK, Data Loss Prevention).

Haczyki egzaminacyjne (Exam Traps):
- Wybór rozwiązań, które wydają się wygodne, ale nie spełniają wymogów bezpieczeństwa (np. zbyt szerokie uprawnienia IAM).
- Mylenie usług: np. Cloud Armor (WAF) z Cloud IAP (Identity-Aware Proxy).

Głębokie wyjaśnienie techniczne (GCP Professional Cloud Security Engineer):
W każdym pytaniu analizuj warstwy: IAM (dostęp), Encryption (at rest/in transit), Logging/Monitoring (Audit Logs, Cloud Logging, Security Command Center) oraz Networking (VPC Service Controls, Firewall Rules). GCP kładzie duży nacisk na współdzieloną odpowiedzialność (Shared Responsibility Model) - klient odpowiada za konfigurację zabezpieczeń wewnątrz usług chmurowych.
