Question 42 / 361

A DevOps team will create a new container to run on Google Kubernetes Engine. As the application will be internet-facing, they want to minimize the attack surface of the container. What should they do?

  • A. Use Cloud Build to build the container images.
  • B. Build small containers using small base images.
  • C. Delete non-used versions from Container Registry.
  • D. Use a Continuous Delivery tool to deploy the application.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

Potwierdzona odpowiedź: B (Build small containers using small base images)

Wyjaśnienie:
Minimalizacja powierzchni ataku (attack surface) w kontenerach polega na usunięciu wszystkiego, co nie jest niezbędne do działania aplikacji.
1. Małe obrazy bazowe (Small base images): Używanie minimalistycznych obrazów (np. Alpine Linux, Distroless) zamiast pełnych dystrybucji (np. Ubuntu, Debian) znacząco redukuje liczbę zainstalowanych pakietów, powłok (shells) i narzędzi systemowych.
2. Korzyści: Mniej zainstalowanego oprogramowania oznacza mniej potencjalnych podatności (CVE), które haker może wykorzystać po przejęciu kontenera. Obrazy "Distroless" nie zawierają nawet managera pakietów ani powłoki sh/bash, co dramatycznie utrudnia życie napastnikowi.

Dlaczego pozostałe są błędne:
A. Cloud Build: To usługa do budowania obrazów (CI). Sam wybór narzędzia do budowania nie wpływa bezpośrednio na zawartość obrazu i jego powierzchnię ataku. Można zbudować "ciężki" i niebezpieczny obraz za pomocą Cloud Build.
C. Usuwanie starych wersji: To dobra praktyka porządkowa i oszczędność miejsca, ale nie minimalizuje powierzchni ataku kontenera, który jest aktualnie uruchomiony w GKE.
D. Continuous Delivery: Narzędzia CD służą do automatyzacji wdrożeń. Podobnie jak w przypadku Cloud Build, samo zautomatyzowanie wdrożenia nie zmienia struktury bezpieczeństwa wnętrza kontenera.

Wskazówki egzaminacyjne (Tips & Tricks):
- "Minimize attack surface" w kontekście kontenerów = "Lean images", "Small base images", "Distroless".
- Pamiętaj o "Multi-stage builds" w Dockerze – to technika pozwalająca na użycie ciężkich narzędzi w fazie budowania i skopiowanie tylko binarnego pliku do finalnego, małego obrazu.
- Szukaj odpowiedzi, które promują usunięcie zbędnych narzędzi (np. SSH, curl, ping) z obrazu produkcyjnego.

Kluczowe zagadnienia do powtórzenia:
- Container security best practices.
- Distroless images.
- Multi-stage Docker builds.

Analiza i Wyjaśnienie

Sugerowana odpowiedź: B

Analiza spornych kwestii (AI): Spośród wszystkich opcji, tylko B bezpośrednio odnosi się do "wnętrza" kontenera. Pozostałe opcje dotyczą procesu (A, D) lub cyklu życia (C). W bezpieczeństwie kontenerów panuje zasada: "Czego nie ma w obrazie, tego nie da się zhakować".

Wyjaśnienie Audytowe

Reguła Egzaminacyjna (Exam Rule):
Pamiętaj, że w egzaminie Professional Cloud Security Engineer kluczowe jest wybieranie rozwiązań najmniej uprzywilejowanych (Principle of Least Privilege), zoptymalizowanych kosztowo i spełniających wymogi compliancy (np. CMEK, Data Loss Prevention).

Haczyki egzaminacyjne (Exam Traps):
- Wybór rozwiązań, które wydają się wygodne, ale nie spełniają wymogów bezpieczeństwa (np. zbyt szerokie uprawnienia IAM).
- Mylenie usług: np. Cloud Armor (WAF) z Cloud IAP (Identity-Aware Proxy).

Głębokie wyjaśnienie techniczne (GCP Professional Cloud Security Engineer):
W każdym pytaniu analizuj warstwy: IAM (dostęp), Encryption (at rest/in transit), Logging/Monitoring (Audit Logs, Cloud Logging, Security Command Center) oraz Networking (VPC Service Controls, Firewall Rules). GCP kładzie duży nacisk na współdzieloną odpowiedzialność (Shared Responsibility Model) - klient odpowiada za konfigurację zabezpieczeń wewnątrz usług chmurowych.
