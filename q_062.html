Question 62 / 361

A manager wants to start retaining security event logs for 2 years while minimizing costs. You write a filter to select the appropriate log entries. Where should you export the logs?

  • A. BigQuery datasets
  • B. Cloud Storage buckets
  • C. StackDriver logging
  • D. Cloud Pub/Sub topics
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
B. Cloud Storage buckets

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Prawidłową odpowiedzią jest Cloud Storage buckets, ponieważ doskonale odpowiada na oba kluczowe wymagania zawarte w pytaniu: długoterminową retencję logów bezpieczeństwa (2 lata) oraz minimalizację kosztów.

Analiza techniczna i architektoniczna:
Cloud Storage to skalowalna i wysoce dostępna usługa do przechowywania danych obiektowych w Google Cloud Platform. Jest to idealne rozwiązanie do archiwizacji danych, w tym logów, z kilku powodów:

  Klasy przechowywania (Storage Classes): Cloud Storage oferuje różne klasy przechowywania, które są zoptymalizowane pod kątem różnych wzorców dostępu i kosztów:
    Standard: Do często używanych danych.
    Nearline: Do danych dostępnych raz w miesiącu, z niższymi kosztami przechowywania i wyższymi kosztami dostępu niż Standard.
    Coldline: Do danych dostępnych raz na kwartał, z jeszcze niższymi kosztami przechowywania i wyższymi kosztami dostępu.
    Archive: Do danych archiwizowanych długoterminowo, dostępnych rzadko (raz w roku lub rzadziej), z najniższymi kosztami przechowywania i najwyższymi kosztami dostępu/pobierania danych.

  Dla logów bezpieczeństwa, które muszą być przechowywane przez 2 lata, ale prawdopodobnie będą rzadko dostępne (chyba że w przypadku audytu lub incydentu bezpieczeństwa), klasy Coldline lub Archive są najbardziej opłacalne. Pozwalają one znacząco obniżyć koszty przechowywania w porównaniu do BigQuery czy domyślnej retencji w Cloud Logging.

  Zarządzanie cyklem życia obiektów (Object Lifecycle Management): To niezwykle ważna funkcja dla tego scenariusza. Pozwala ona zdefiniować automatyczne reguły, które zarządzają obiektami w bucketach Cloud Storage. W tym przypadku można skonfigurować:
    Automatyczne przenoszenie logów do tańszych klas przechowywania (np. z Standard do Coldline, a następnie do Archive) po określonym czasie, co dodatkowo obniża koszty.
    Automatyczne usuwanie logów po upływie dokładnie 2 lat, co jest kluczowe dla zgodności z wymogami retencji i dalszej optymalizacji kosztów poprzez unikanie przechowywania zbędnych danych.

  Eksport logów (Log Sinks): Google Cloud Logging (dawniej Stackdriver Logging) umożliwia eksportowanie logów do różnych miejsc docelowych za pomocą tak zwanych "sinków" (Log Sinks). Możesz utworzyć sink, który filtruje odpowiednie wpisy logów bezpieczeństwa i eksportuje je do wskazanego bucketa Cloud Storage. Logi są eksportowane w formacie JSON, zazwyczaj skompresowane, co dodatkowo oszczędza miejsce.

  Bezpieczeństwo: Cloud Storage integruje się z Google Cloud IAM (Identity and Access Management) do precyzyjnego zarządzania dostępem do bucketów i obiektów. Można zastosować zasadę najmniejszych uprawnień (Principle of Least Privilege), aby tylko autoryzowani użytkownicy lub Service Accounts mieli dostęp do logów. Dane są szyfrowane w spoczynku (encryption at rest) domyślnie, z opcjami użycia kluczy zarządzanych przez Google lub kluczy zarządzanych przez klienta (Customer-Managed Encryption Keys - CMEK lub Customer-Supplied Encryption Keys - CSEK), co jest kluczowe dla wymagań bezpieczeństwa logów.

Dlaczego jest to zalecana praktyka (best practice):
Dla długoterminowej, koszt-efektywnej archiwizacji logów, Cloud Storage jest powszechnie uznawaną najlepszą praktyką w GCP. Spełnia wymogi zgodności (compliance) dotyczące retencji danych, jednocześnie minimalizując koszty operacyjne. Zapewnia to audytowalność i integralność logów przez wymagany okres.

Lepsze, bezpieczniejsze i bardziej skalowalne niż inne rozwiązania:
  Lepsze pod względem kosztów: Żadna inna usługa w GCP nie oferuje tak niskich kosztów przechowywania danych w spoczynku dla rzadko używanych danych, jak Cloud Storage (szczególnie klasy Archive).
  Bezpieczniejsze: Dzięki integracji z IAM, szyfrowaniu w spoczynku i opcjom zarządzania kluczami, Cloud Storage zapewnia wysoki poziom bezpieczeństwa dla przechowywanych logów. Możliwość niezmienności obiektów (Object Lock) pozwala chronić logi przed przypadkowym lub celowym usunięciem czy modyfikacją, co jest kluczowe dla integralności dowodów cyfrowych.
  Bardziej skalowalne: Cloud Storage jest usługą bezserwerową (serverless), co oznacza, że automatycznie skaluje się, aby sprostać dowolnym wymaganiom dotyczącym objętości danych, bez konieczności zarządzania infrastrukturą. Możesz przechowywać petabajty danych bez żadnych operacyjnych obciążeń.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:

  A. BigQuery datasets
    BigQuery jest usługą hurtowni danych bezserwerową, przeznaczoną do szybkiej analizy ogromnych zbiorów danych przy użyciu SQL. Jest doskonałym wyborem do wykonywania złożonych zapytań analitycznych na logach, budowania pulpitów nawigacyjnych czy używania narzędzi do uczenia maszynowego.
    DLACZEGO JEST NIEPRAWIDŁOWA W TYM SCENARIUSZU: Głównym celem pytania jest "minimizing costs" dla "retaining security event logs for 2 years". Chociaż BigQuery oferuje przechowywanie danych, jego model kosztowy jest wyższy niż Cloud Storage dla czystego przechowywania danych, zwłaszcza jeśli dane mają być rzadko dostępne. Opłaty za przechowywanie w BigQuery są naliczane za gigabajt, ale nie ma tak zróżnicowanych klas dostępu jak w Cloud Storage (z wyjątkiem rozróżnienia na aktywne i długoterminowe przechowywanie, które jest mniej agresywne cenowo niż klasy Cloud Storage Archive). Ponadto, korzystanie z BigQuery do samego przechowywania logów bez aktywnej analizy byłoby nieefektywnym wykorzystaniem zasobów i droższym rozwiązaniem niż Cloud Storage.

  C. StackDriver logging
    StackDriver logging, obecnie nazywane Cloud Logging, to główna usługa Google Cloud do zbierania, przechowywania, wyszukiwania i monitorowania logów. Domyślnie Cloud Logging przechowuje logi w "log buckets" (segmenty logów) przez określony czas:
      Logi administracyjne (Admin Activity logs) są przechowywane przez 90 dni.
      Logi dostępu do danych (Data Access logs) są przechowywane przez 30 dni.
      Logi zdarzeń systemowych (System Event logs) są przechowywane przez 30 dni.
      Logi z platformy (Platform logs) i logi użytkownika (User logs) mogą mieć domyślną retencję od 30 do 400 dni, w zależności od konfiguracji log bucketu i regionu.
    Istnieje możliwość konfiguracji niestandardowej retencji dla log buckets do 10 lat, jednakże koszty przechowywania w Cloud Logging dla tak długiego okresu i dużej objętości logów są zazwyczaj wyższe niż w przypadku eksportu do Cloud Storage, szczególnie jeśli logi mają być rzadko dostępne.
    DLACZEGO JEST NIEPRAWIDŁOWA W TYM SCENARIUSZU: Chociaż Cloud Logging pozwala na niestandardową retencję, nie jest to najbardziej kosztowo efektywne rozwiązanie dla DŁUGOTERMINOWEGO przechowywania logów z MINIMALIZACJĄ KOSZTÓW, zwłaszcza w porównaniu do opcji Archive w Cloud Storage. Celem jest archiwizacja, a nie codzienne monitorowanie czy wyszukiwanie w Cloud Logging UI.

  D. Cloud Pub/Sub topics
    Cloud Pub/Sub to w pełni zarządzana usługa asynchronicznego przesyłania wiadomości, służąca do tworzenia skalowalnych i elastycznych architektur. Jest używana do rozprzęgania usług, strumieniowego przetwarzania danych, dystrybucji wydarzeń w czasie rzeczywistym.
    DLACZEGO JEST NIEPRAWIDŁOWA W TYM SCENARIUSZU: Cloud Pub/Sub NIE jest usługą do przechowywania danych (storage service) dla długoterminowej retencji. Jego podstawową funkcją jest przekazywanie wiadomości od wydawców do subskrybentów. Wiadomości są przechowywane w temacie tylko przez bardzo krótki czas (domyślnie 7 dni, maksymalnie 7 dni), aby umożliwić subskrybentom ich pobranie. Nie jest to rozwiązanie do archiwizacji logów na 2 lata. Może być używane jako pośrednik do strumieniowego przesyłania logów w czasie rzeczywistym do innych systemów (np. SIEM on-premises lub do BigQuery w celu analizy), ale nie jako docelowe miejsce przechowywania.

4. Wskazówki, hinty, tips and tricks:

  Kluczowe słowa w pytaniu: Zawsze zwracaj szczególną uwagę na słowa kluczowe w pytaniu. W tym przypadku "retaining security event logs for 2 years" (długoterminowa retencja) i "minimizing costs" (minimalizacja kosztów) są absolutnie decydujące.
  Długoterminowa retencja i minimalne koszty: Jeśli te dwa warunki pojawiają się razem, 90% czasu odpowiedź będzie wskazywała na Cloud Storage, często z sugestią użycia klas przechowywania (Nearline, Coldline, Archive) i Object Lifecycle Management.
  Rodzaj dostępu do danych: Pomyśl, jak często te dane będą dostępne. Logi do audytu często nie są dostępne na co dzień, co sugeruje tańsze klasy przechowywania.
  Pułapki językowe: Uważaj na opcje, które są "technicznie możliwe" do przechowywania logów, ale nie są optymalne pod kątem kosztów lub podstawowego przeznaczenia. Na przykład, możesz technicznie eksportować logi do BigQuery i je tam trzymać, ale to nie jest najbardziej koszt-efektywne rozwiązanie dla długoterminowej retencji bez aktywnej analizy.
  Rozróżnij "przetwarzanie w czasie rzeczywistym" od "przechowywania": Cloud Pub/Sub to usługa przetwarzania w czasie rzeczywistym/przesyłania strumieniowego, a nie przechowywania.
  Domyślne vs. niestandardowe retencje: Pamiętaj o domyślnych limitach retencji w Cloud Logging. Choć można je zwiększyć, często wiąże się to z wyższymi kosztami niż dedykowana usługa archiwizacji, jaką jest Cloud Storage.
  Pamiętaj o zgodności: Logi bezpieczeństwa często podlegają rygorystycznym wymogom zgodności (np. GDPR, HIPAA, PCI DSS). Cloud Storage z Object Lock i IAM doskonale wspiera te wymogi.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):

  Jeśli pytanie wspomina o "długoterminowej retencji" (long-term retention) oraz "minimalizacji kosztów" (minimizing costs) dla logów lub dużych zbiorów danych, szukaj odpowiedzi zawierającej "Cloud Storage buckets" i w myślach rozważ klasy przechowywania takie jak Nearline, Coldline lub Archive, a także Object Lifecycle Management.
  Gdy celem jest "analiza w czasie rzeczywistym" (real-time analysis), "zapytania SQL" (SQL queries), "hurtownia danych" (data warehouse) lub "uczenie maszynowe na danych" (machine learning on data), wybierz "BigQuery".
  Jeśli scenariusz wymaga "przesyłania strumieniowego" (streaming), "przekazywania wiadomości" (messaging), "rozprzęgania usług" (decoupling services) lub "integracji z systemami SIEM/SOAR" (SIEM/SOAR integration) dla logów w czasie rzeczywistym, odpowiedź będzie dotyczyła "Cloud Pub/Sub topics".
  Gdy pytanie dotyczy "domyślnego przechowywania logów", "monitorowania logów", "alertowania na podstawie logów" lub "szybkiego wyszukiwania logów operacyjnych" (troubleshooting) w perspektywie krótkoterminowej (do 400 dni), rozważ "Cloud Logging" (dawniej Stackdriver logging).
