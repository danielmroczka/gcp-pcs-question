Question 188 / 361

A company is using Google Kubernetes Engine (GKE) with container images of a mission-critical application. The company wants to scan the images for known security issues and securely share the report with the security team without exposing them outside Google Cloud.
What should you do?

  • A. 1. Enable Container Threat Detection in the Security Command Center Premium tier. 2. Upgrade all clusters that are not on a supported version of GKE to the latest possible GKE version. 3. View and share the results from the Security Command Center.
  • B. 1. Use an open source tool in Cloud Build to scan the images. 2. Upload reports to publicly accessible buckets in Cloud Storage by using gsutil. 3. Share the scan report link with your security department.
  • C. 1. Enable vulnerability scanning in the Artifact Registry settings. 2. Use Cloud Build to build the images. 3. Push the images to the Artifact Registry for automatic scanning. 4. View the reports in the Artifact Registry.
  • D. 1. Get a GitHub subscription. 2. Build the images in Cloud Build and store them in GitHub for automatic scanning. 3. Download the report from GitHub and share with the Security Team.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Poprawna odpowiedź: C (1. Enable vulnerability scanning in the Artifact Registry settings. 2. Use Cloud Build to build the images. 3. Push the images to the Artifact Registry for automatic scanning. 4. View the reports in the Artifact Registry)

Dlaczego ta odpowiedź jest poprawna:
- Artifact Registry: Jest to następca Google Container Registry (GCR) i natywne miejsce do przechowywania obrazów kontenerów w GCP.
- Vulnerability Scanning: Artifact Registry posiada wbudowaną usługę skanowania podatności (część Container Analysis). Po jej włączeniu, każdy obraz wypchnięty (push) do rejestru jest automatycznie analizowany pod kątem znanych luk (CVE) w paczkach systemowych.
- Bezpieczeństwo i Integracja: Ten proces odbywa się w całości wewnątrz infrastruktury Google Cloud. Raporty są dostępne bezpośrednio w konsoli dla osób z odpowiednimi uprawnieniami IAM (np. zespół security), co spełnia wymóg "without exposing them outside Google Cloud".
- Automatyzacja: Użycie Cloud Build do budowania i automatycznego wypychania obrazów do rejestru tworzy spójny i bezpieczny potok CI/CD (DevSecOps).

Analiza niepoprawnych odpowiedzi:
- A. Container Threat Detection (SCC Premium): Ta usługa SCC służy do wykrywania zagrożeń w CZASIE RZECZYWISTYM na uruchomionych klastrach (np. podejrzane procesy, reverse shells). Nie jest to narzędzie do statycznego skanowania obrazów w rejestrze pod kątem luk przed wdrożeniem.
- B. Open source tool + Public buckets: Wysyłanie raportów bezpieczeństwa do PUBLICZNYCH bucketów jest rażącym błędem i narusza wymóg "without exposing them outside Google Cloud".
- D. GitHub scanning: Choć GitHub posiada dobre skanery, wymóg pytania wyraźnie sugeruje wykorzystanie ekosystemu Google Cloud ("without exposing them outside") oraz natywną integrację z GKE/Cloud Build.

Wskazówki i triki (Tips & Tricks):
- "Scan container images" + "Google Cloud native" = Artifact Registry Vulnerability Scanning.
- Pamiętaj: Container Analysis to usługa "podkładowa", która przechowuje metadane skanów, a Artifact Registry to interfejs użytkownika.
- Skanowanie w Artifact Registry dzieli się na "On-push scanning" (automatyczne) oraz "Continuous scanning" (monitorowanie nowych luk dla już istniejących obrazów).

Praktyczne informacje na egzamin:
- Zwróć uwagę na koszty: Skanowanie "On-push" jest płatne za każdy obraz, natomiast "Continuous scanning" ma model subskrypcyjny lub oparty na liczbie obrazów.
- Skanowanie wykrywa podatności głównie w paczkach zarządzanych przez menedżery (np. apt, yum, apk). Nie wykrywa błędów w samym kodzie aplikacji (do tego służy SAST).

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: C

Analiza strategiczna: To pytanie sprawdza znajomość cyklu życia bezpiecznego oprogramowania (Secure SDLC) w chmurze. Google stawia na podejście "Shift Left" – wykrywanie błędów jak najwcześniej. Skanowanie w rejestrze (Artifact Registry) pozwala zatrzymać niebezpieczny obraz jeszcze przed jego wdrożeniem na produkcję (GKE), co jest znacznie tańsze i bezpieczniejsze niż reagowanie na incydenty po fakcie.

Dodatkowe wskazówki

  • W połączeniu z Binary Authorization, możesz skonfigurować GKE tak, aby odrzucał obrazy, które posiadają luki o poziomie "High" lub "Critical".
  • Raporty skanowania zawierają nie tylko listę CVE, ale także informacje o tym, która wersja paczki naprawia dany błąd (fix version).
