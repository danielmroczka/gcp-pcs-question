Question 188 / 361

A company is using Google Kubernetes Engine (GKE) with container images of a mission-critical application. The company wants to scan the images for known security issues and securely share the report with the security team without exposing them outside Google Cloud.
What should you do?

  • A. 1. Enable Container Threat Detection in the Security Command Center Premium tier. 2. Upgrade all clusters that are not on a supported version of GKE to the latest possible GKE version. 3. View and share the results from the Security Command Center.
  • B. 1. Use an open source tool in Cloud Build to scan the images. 2. Upload reports to publicly accessible buckets in Cloud Storage by using gsutil. 3. Share the scan report link with your security department.
  • C. 1. Enable vulnerability scanning in the Artifact Registry settings. 2. Use Cloud Build to build the images. 3. Push the images to the Artifact Registry for automatic scanning. 4. View the reports in the Artifact Registry.
  • D. 1. Get a GitHub subscription. 2. Build the images in Cloud Build and store them in GitHub for automatic scanning. 3. Download the report from GitHub and share with the Security Team.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C (1. Enable vulnerability scanning in the Artifact Registry settings. 2. Use Cloud Build to build the images. 3. Push the images to the Artifact Registry for automatic scanning. 4. View the reports in the Artifact Registry).

Wyjaśnienie:
Artifact Registry to nowoczesny, natywny rejestr obrazów kontenerów w Google Cloud. Posiada on wbudowaną funkcję "Vulnerability Scanning" (część usługi Container Analysis). Po jej włączeniu każde wypchnięcie (push) obrazu do rejestru automatycznie uruchamia skanowanie pod kątem znanych podatności (CVE) w paczkach systemowych. Cały proces odbywa się wewnątrz bezpiecznej infrastruktury Google Cloud, a raporty są dostępne bezpośrednio w konsoli dla uprawnionych osób (np. zespołu security), co spełnia wymóg poufności i braku ekspozycji raportów na zewnątrz.

Dlaczego pozostałe są błędne:
- A. Container Threat Detection (SCC Premium): Ta usługa służy do wykrywania zagrożeń w czasie rzeczywistym na już URUCHOMIONYCH kontenerach (np. wykrywanie reverse shell). Nie służy do statycznego skanowania obrazów w rejestrze przed ich wdrożeniem.
- B. Open source tool + Public buckets: Publikowanie raportów bezpieczeństwa w PUBLICZNYCH bucketach Cloud Storage jest rażącym naruszeniem zasad bezpieczeństwa i wprost przeczy wymogowi "without exposing them outside Google Cloud".
- D. GitHub scanning: Przechowywanie obrazów i raportów w zewnętrznym serwisie (GitHub) wykracza poza infrastrukturę Google Cloud, co narusza wymóg zachowania danych wewnątrz chmury Google.

Wskazówki egzaminacyjne (Tips & Tricks):
- "Scan container images" + "GCP native" = Artifact Registry Vulnerability Scanning.
- Pamiętaj o podejściu "Shift Left" – skanujemy obrazy ZANIM trafią na produkcję.

Kluczowe zagadnienia do powtórzenia:
- Integracja Cloud Build z Artifact Registry.
- Container Analysis API i automatyczne skanowanie.
- Binary Authorization (blokowanie wdrożeń obrazów z krytycznymi podatnościami).

Sugerowana odpowiedź: C

Głęboka analiza: Zadanie wymaga bezpiecznego i natywnego procesu skanowania. Artifact Registry w połączeniu z Container Analysis oferuje w pełni zautomatyzowane rozwiązanie, które nie wymaga przesyłania danych do zewnętrznych dostawców. To standardowa metoda budowania bezpiecznego łańcucha dostaw oprogramowania (Secure Software Supply Chain) w Google Cloud.
