Question 87 / 361

You have an application where the frontend is deployed on a managed instance group in subnet A and the data layer is stored on a mysql Compute Engine virtual machine (VM) in subnet B on the same VPC. Subnet A and Subnet B hold several other Compute Engine VMs. You only want to allow the application frontend to access the data in the application's mysql instance on port 3306.
What should you do?

  • A. Configure an ingress firewall rule that allows communication from the src IP range of subnet A to the tag "data-tag" that is applied to the mysql Compute Engine VM on port 3306.
  • B. Configure an ingress firewall rule that allows communication from the frontend's unique service account to the unique service account of the mysql Compute Engine VM on port 3306.
  • C. Configure a network tag "fe-tag" to be applied to all instances in subnet A and a network tag "data-tag" to be applied to all instances in subnet B. Then configure an egress firewall rule that allows communication from Compute Engine VMs tagged with data-tag to destination Compute Engine VMs tagged fe-tag.
  • D. Configure a network tag "fe-tag" to be applied to all instances in subnet A and a network tag "data-tag" to be applied to all instances in subnet B. Then configure an ingress firewall rule that allows communication from Compute Engine VMs tagged with fe-tag to destination Compute Engine VMs tagged with data-tag.

Suggested Answer: B

Wyjaśnienie

**Poprawna odpowiedź: B**

**1. Kompleksowe wyjaśnienie poprawnej odpowiedzi:**
Wymagane jest zezwolenie na dostęp do bazy danych MySQL (port 3306) wyłącznie dla maszyn z warstwy frontendowej (Subnet A), bez zezwalania innym maszynom w tej samej podsieci na dostęp, co stanowi implementację mikrosegmentacji sieciowej:
- **Skonfigurowanie reguły zapory sieciowej opartej na kontach usług (Service Accounts) (B):** W Google Cloud reguły firewall mogą być definiowane nie tylko za pomocą zakresów IP czy tagów sieciowych, ale także na podstawie tożsamości maszyn (konta usługi powiązanego z maszyną wirtualną). Konfiguracja reguły zezwalającej na ruch z konta usługi frontendu do konta usługi bazy danych jest najbezpieczniejszym rozwiązaniem. Działa niezależnie od adresacji IP oraz uniemożliwia innym maszynom w Subnet A (które mają inne konta usługi) na dostęp do bazy danych.

**2. Wyjaśnienie niepoprawnych odpowiedzi:**
- **A. Reguła oparta na zakresie IP podsieci A:** Zezwoliłaby na ruch z *każdej* maszyny znajdującej się w podsieci A, co narusza zasadę najmniejszych uprawnień (inne aplikacje w tej podsieci również zyskałyby dostęp).
- **C. Reguła egress z bazy do frontendu:** Reguły typu egress kontrolują ruch wychodzący. Zezwolenie na ruch wychodzący z bazy do frontendu nie jest właściwym sposobem na autoryzowanie połączeń inicjowanych przez frontend w kierunku bazy (potrzebna jest reguła ingress na bazie).
- **D. Reguła oparta na tagach sieciowych ("fe-tag" i "data-tag"):** Tagi sieciowe nie są powiązane z tożsamością maszyn i mogą być łatwo zmieniane przez osoby z uprawnieniami do edycji VM. Ponadto, reguły oparte na kontach usług (Service Accounts) są rekomendowaną praktyką bezpieczeństwa w GCP, ponieważ IAM ściśle kontroluje, kto może uruchomić maszynę z danym kontem usługi.

**3. Wskazówki i pułapki egzaminacyjne (Tips & Tricks):**
- Definiowanie reguł firewall na podstawie **konta usługi (Service Account)** jest bezpieczniejsze niż na podstawie **tagów sieciowych (network tags)**, ponieważ uprawnienie do przypisania konta usługi (`iam.serviceAccounts.actAs`) jest ściślej kontrolowane niż uprawnienie do edycji tagów sieciowych.
- Reguły firewall oparte na kontach usług umożliwiają prawdziwą mikrosegmentację w GCP.

**4. Reguły wyboru odpowiedzi:**
- Ścisłe ograniczenie ruchu między warstwami aplikacji (frontend -> backend/database) -> Użycie kont usług (Service Accounts) jako źródła i celu w regułach firewall.

**5. Dodatkowe źródła:**
