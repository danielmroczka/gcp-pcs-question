Question 63 / 361

For compliance reasons, an organization needs to ensure that in-scope PCI Kubernetes Pods reside on `in-scope` Nodes only. These Nodes can only contain the `in-scope` Pods. How should the organization achieve this objective?

  • A. Add a nodeSelector field to the pod configuration to only use the Nodes labeled inscope: true.
  • B. Create a node pool with the label inscope: true and a Pod Security Policy that only allows the Pods to run on Nodes with that label.
  • C. Place a taint on the Nodes with the label inscope: true and effect NoSchedule and a toleration to match in the Pod configuration.
  • D. Run all in-scope Pods in the namespace in-scope-pci.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Place a taint on the Nodes with the label inscope: true and effect NoSchedule and a toleration to match in the Pod configuration.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Prawidłowa odpowiedź opiera się na mechanizmach Taints i Tolerations dostępnych w Kubernetes, a tym samym w Google Kubernetes Engine (GKE), które są kluczowe do realizacji zaawansowanych strategii planowania Podów i izolacji obciążeń. W kontekście zgodności z PCI DSS (Payment Card Industry Data Security Standard), izolacja zasobów jest krytyczna i często wymaga gwarancji, że wrażliwe obciążenia nie współdzielą infrastruktury fizycznej (węzłów) z obciążeniami, które nie są objęte zakresem PCI lub są mniej zaufane.

Analiza techniczna i architektoniczna:
Mechanizm Taints i Tolerations działa na zasadzie "odpychania" i "przyciągania".
Taint (Skażenie): Nakładany jest na węzeł (Node). Oznacza on, że węzeł "nie chce" uruchamiać Podów, chyba że posiadają one odpowiednią Tolerancję. Taint składa się z klucza (key), wartości (value) i efektu (effect). W tym scenariuszu klucz i wartość mogą być ustawione na inscope: true, a efekt na NoSchedule.
 Efekt NoSchedule oznacza, że żaden nowy Pod nie zostanie zaplanowany na tym węźle, chyba że posiada odpowiednią Tolerancję. To bezpośrednio odpowiada na drugą część pytania: "These Nodes can only contain the in-scope Pods". Wszystkie Pody, które nie mają tolerancji dla tainty inscope: true:NoSchedule, zostaną przez scheduler Kubernetes'a zignorowane i nie zostaną umieszczone na tych węzłach.
Toleration (Tolerancja): Dodawana jest do konfiguracji Podu. Określa ona, że dany Pod "toleruje" konkretny Taint i może zostać na nim zaplanowany. Pody PCI, które mają zostać uruchomione na węzłach oznaczonych jako inscope: true, muszą posiadać tolerancję dopasowaną do Taintu na tych węzłach. Taka tolerancja umożliwi schedulerowi umieszczenie tych Podów na skażonych węzłach, spełniając wymóg "in-scope PCI Kubernetes Pods reside on in-scope Nodes only".

Zalety i zgodność z najlepszymi praktykami GCP:
1.  Silna izolacja: Taints i Tolerations zapewniają dwukierunkową izolację. Z jednej strony, tylko autoryzowane Pody (z Tolerancją) mogą trafić na wyznaczone węzły. Z drugiej strony, wyznaczone węzły mogą zawierać tylko te autoryzowane Pody, ponieważ wszystkie inne Pody są "odpychane". To jest kluczowe dla wymogów compliance, takich jak PCI DSS, które często wymagają ścisłej separacji środowisk.
2.  Elastyczność planowania: Pozwala to na precyzyjne sterowanie planowaniem Podów, co jest niezbędne w złożonych środowiskach korporacyjnych. Można tworzyć dedykowane pule węzłów dla różnych typów obciążeń, np. produkcyjnych, testowych, PCI, wrażliwych danych, itd.
3.  Zgodność z Kubernetes Native: Jest to natywny mechanizm Kubernetes, co oznacza jego pełne wsparcie w GKE, dobrą integrację z ekosystemem i stabilność.
4.  Bezpieczeństwo: Zapobiega przypadkowemu lub nieautoryzowanemu umieszczaniu Podów z mniej restrykcyjnymi wymaganiami bezpieczeństwa na węzłach przeznaczonych dla obciążeń o wysokiej wrażliwości. Zmniejsza to powierzchnię ataku i ryzyko naruszenia danych.
5.  Skalowalność i zarządzanie: Chociaż ręczne dodawanie Taintów i Toleracji może wydawać się pracochłonne, w GKE można tworzyć Node Pools z predefiniowanymi Taintami, co ułatwia zarządzanie i skalowanie. Pody mogą być automatycznie konfigurowane z odpowiednimi Toleracjami za pomocą narzędzi do zarządzania konfiguracją lub mechanizmów CD/CI.

Podsumowując, połączenie Taintów na węzłach z efektem NoSchedule i odpowiadających im Toleracji w konfiguracji Podów jest jedynym spośród przedstawionych rozwiązań, które w pełni spełnia oba wymagania pytania: zapewnia, że Pody PCI trafiają wyłącznie na węzły PCI ORAZ że na węzłach PCI mogą być uruchamiane wyłącznie Pody PCI.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:

A. Add a nodeSelector field to the pod configuration to only use the Nodes labeled inscope: true.
Dlaczego jest niepoprawna: Opcja ta jest błędna, ponieważ rozwiązuje tylko jeden z dwóch postawionych warunków. nodeSelector to mechanizm "przyciągania" (affinity). Oznacza to, że Pod z nodeSelector: inscope: true zostanie zaplanowany *tylko* na węzłach, które posiadają etykietę inscope: true. Spełnia to wymóg "in-scope PCI Kubernetes Pods reside on in-scope Nodes only". Jednakże, nodeSelector *nie zapobiega* sytuacji, w której inne Pody, które *nie* mają określonego nodeSelector (lub mają inny), zostaną również zaplanowane na tych samych węzłach. Scheduler Kubernetes domyślnie będzie próbował umieścić Pody na dowolnym dostępnym węźle. W rezultacie, węzły z etykietą inscope: true mogłyby nadal zawierać Pody, które nie są objęte zakresem PCI, co naruszałoby wymóg "These Nodes can only contain the in-scope Pods". Brak jest więc gwarancji ekskluzywności.

B. Create a node pool with the label inscope: true and a Pod Security Policy that only allows the Pods to run on Nodes with that label.
Dlaczego jest niepoprawna: Ta opcja jest błędna z kilku powodów:
1.  Pod Security Policy (PSP) jest mechanizmem kontroli dostępu do zasobów Podu i kontroli jego uprawnień (np. czy może uruchamiać kontenery jako root, czy ma dostęp do hostPath, czy może używać uprzywilejowanych kontenerów), a nie do sterowania tym, na których węzłach fizycznych Pod ma się znaleźć. PSP nie ma wbudowanej funkcjonalności do narzucania ograniczeń planowania Podów na podstawie etykiet węzłów.
2.  Pod Security Policy (PSP) został oznaczony jako przestarzały (deprecated) w Kubernetes v1.21 i usunięty w v1.25. Został zastąpiony przez Pod Security Admission (PSA). Chociaż PSA jest nowszym i zalecanym mechanizmem, podobnie jak PSP, jego głównym celem jest egzekwowanie standardów bezpieczeństwa Podów poprzez kontrolę kontekstu bezpieczeństwa Podów, a nie ich fizycznego umiejscowienia na węzłach.
3.  Nawet jeśli stworzona zostanie pula węzłów z etykietą inscope: true, to samo w sobie nie zapobiegnie umieszczeniu na nich Podów spoza zakresu PCI, jeśli nie ma mechanizmu "odpychającego".

D. Run all in-scope Pods in the namespace in-scope-pci.
Dlaczego jest niepoprawna: Ta opcja jest błędna, ponieważ Namespaces (przestrzenie nazw) zapewniają izolację logiczną wewnątrz API Kubernetes, ale nie gwarantują izolacji fizycznej na poziomie węzłów (maszyn wirtualnych). Pody z różnych przestrzeni nazw (np. in-scope-pci i default) mogą swobodnie działać na tym samym węźle fizycznym, jeśli scheduler Kubernetes uzna ten węzeł za odpowiedni. Namespaces służą do logicznego grupowania zasobów, zarządzania dostępem za pomocą Role-Based Access Control (RBAC) w obrębie danego projektu oraz do organizacji klastra, ale nie do fizycznej separacji obciążeń. Wymóg "Nodes can only contain the in-scope Pods" oznacza fizyczną izolację, której Namespaces nie są w stanie zapewnić.

4. Wskazówki, hinty, tips and tricks:
*   Kluczowe słowa w pytaniu: Zawsze szukaj w pytaniu słów kluczowych wskazujących na konkretne wymagania. W tym przypadku frazy "only on X" (tylko na węzłach X) i "X can only contain Y" (węzły X mogą zawierać tylko Pody Y) są absolutnie krytyczne. Oznaczają one dwukierunkową, wzajemną ekskluzywność.
*   "Only on X" vs. "X can only contain Y":
    *   Jeśli pytanie mówi tylko "Pody A mają być na węzłach X" (ale nie ma wymogu, że na węzłach X mogą być *tylko* Pody A), to nodeSelector lub Node Affinity może być wystarczający.
    *   Jeśli pytanie zawiera oba warunki – "Pody A mają być na węzłach X" ORAZ "Na węzłach X mogą być *tylko* Pody A" – to jest to niemal pewny znak, że potrzebujesz Taints i Tolerations. Taints są mechanizmem "odpychającym", który gwarantuje, że nikt niepożądany nie trafi na węzeł.
*   PCI DSS i inne wymogi compliance: Wymogi zgodności, takie jak PCI DSS, HIPAA, SOC 2, często narzucają ścisłe zasady izolacji danych i przetwarzania. W Kubernetes, Taints i Tolerations są podstawowym narzędziem do fizycznej izolacji obciążeń na poziomie węzłów, co jest często interpretowane jako sposób na spełnienie tych wymogów.
*   Rozróżnienie izolacji:
    *   Izolacja logiczna (namespaces, RBAC, Network Policies)
    *   Izolacja fizyczna/na poziomie węzłów (Taints/Tolerations, Node Affinity, dedykowane Node Pools)
    *   Izolacja bezpieczeństwa Podów (Pod Security Admission/Policies)
*   Deprecated Features: Zwróć uwagę na funkcje, które są przestarzałe lub usunięte (np. Pod Security Policy). Egzaminy GCP starają się testować wiedzę na temat aktualnych i zalecanych rozwiązań.
*   Czytaj pytanie uważnie: Pułapki językowe często polegają na subtelnych różnicach w słowach "może", "musi", "tylko". Dokładna analiza tych słów jest kluczowa.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
*   Jeśli pytanie wspomina o "izolacji obciążeń na poziomie węzłów" lub "dedykowanych węzłach dla konkretnych Podów" ORAZ o "zapobieganiu uruchamianiu innych Podów na tych samych węzłach", szukaj odpowiedzi zawierającej "Taint" i "Toleration".
*   Gdy celem jest ścisła "zgodność z normami bezpieczeństwa" (np. PCI DSS) wymagająca "separacji fizycznej" środowisk w Kubernetes, rozwiązanie oparte na Taints i Tolerations jest najczęściej prawidłową odpowiedzią.
*   Jeśli wymagane jest, aby "tylko specyficzne Pody" mogły być planowane na "specyficznych węzłach" ORAZ, że "żadne inne Pody" nie mogły na tych węzłach być uruchamiane, Taints z efektem NoSchedule są niezbędne. nodeSelector jest niewystarczający w takim scenariuszu.
*   Gdy w pytaniu pojawiają się frazy takie jak "Nodes can *only* contain X Pods", natychmiast rozważ Taints jako mechanizm aktywnego odpychania niepożądanych Podów.
*   Jeśli pytanie odnosi się do "kontroli kontekstu bezpieczeństwa Podu" lub "ograniczeń uprawnień Podu", szukaj odpowiedzi związanych z Pod Security Admission (lub Pod Security Policy, jeśli pytanie jest starsze). Jeśli pytanie dotyczy "gdzie Pod jest planowany", te opcje są zazwyczaj błędne.
