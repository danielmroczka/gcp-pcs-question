Question 63 / 361

For compliance reasons, an organization needs to ensure that in-scope PCI Kubernetes Pods reside on `in-scope` Nodes only. These Nodes can only contain the `in-scope` Pods. How should the organization achieve this objective?

  • A. Add a nodeSelector field to the pod configuration to only use the Nodes labeled inscope: true.
  • B. Create a node pool with the label inscope: true and a Pod Security Policy that only allows the Pods to run on Nodes with that label.
  • C. Place a taint on the Nodes with the label inscope: true and effect NoSchedule and a toleration to match in the Pod configuration.
  • D. Run all in-scope Pods in the namespace in-scope-pci.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C (Place a taint on the Nodes with the label inscope: true and effect NoSchedule and a toleration to match in the Pod configuration.)

Wyjaśnienie:
To pytanie dotyczy izolacji obciążeń (workload isolation) w klastrze GKE. Aby zapewnić, że konkretne pody (PCI) działają TYLKO na konkretnych węzłach ORAZ że żadne inne pody nie trafią na te węzły, należy użyć mechanizmu Taints i Tolerations.
1. Taint (Skażenie): Nakładasz "skażenie" na węzły z efektem `NoSchedule`. Powoduje to, że żaden pod nie zostanie na nich uruchomiony, chyba że posiada odpowiednią "tolerancję". To załatwia wymóg: "These Nodes can only contain the in-scope Pods".
2. Toleration (Tolerancja): Dodajesz tolerancję do konfiguracji podów PCI. Pozwala im to "zignorować" skażenie i zostać uruchomionym na tych konkretnych węzłach.
3. Node Affinity / nodeSelector: Często stosuje się je razem z taints, aby upewnić się, że pody PCI trafią WŁAŚNIE tam (przyciąganie), a taints zapewniają, że inne pody tam NIE trafią (odpychanie).

Dlaczego pozostałe są błędne:
A. nodeSelector: Pozwala podom wybrać konkretne węzły, ale NIE zapobiega sytuacji, w której inne pody (bez nodeSelector) również zostaną tam zaplanowane przez scheduler. Nie spełnia więc drugiej części wymogu.
B. Pod Security Policy: PSP (obecnie deprecated na rzecz Pod Security Admission) służy do kontroli uprawnień wewnątrz kontenera (np. czy może działać jako root), a nie do sterowania tym, na których węzłach fizycznych pod ma się znaleźć.
D. Namespaces: Przestrzenie nazw zapewniają izolację logiczną wewnątrz API Kubernetes, ale nie gwarantują izolacji fizycznej na poziomie węzłów (maszyn wirtualnych). Pody z różnych przestrzeni nazw mogą działać na tym samym węźle.

Tips & Tricks:
- "Nodes can only contain specific Pods" = Taints and Tolerations.
- NodeSelector = "Pod chce tam być" (ale inni też mogą).
- Taint = "Nikt tu nie wejdzie bez przepustki (tolerancji)".
- Na egzaminie PCI DSS często wymaga fizycznej separacji danych lub procesów – Taints są standardowym sposobem na jej osiągnięcie w Kubernetes.
