Question 311 / 361

Your organization is worried about recent news headlines regarding application vulnerabilities in production applications that have led to security breaches. You want to automatically scan your deployment pipeline for vulnerabilities and ensure only scanned and verified containers can run in the environment. What should you do?

  • A. Use Kubernetes role-based access control (RBAC) as the source of truth for cluster access by granting "container.clusters.get" to limited users. Restrict deployment access by allowing these users to generate a kubeconfig file containing the configuration access to the GKE cluster.
  • B. Use gcloud artifacts docker images describe LOCATION-docker.pkg.dev/PROJECT_ID/REPOSITORY/IMAGE_ID@sha256:HASH --show-package-vulnerability in your CI/CD pipeline, and trigger a pipeline failure for critical vulnerabilities.
  • C. Enforce the use of Cloud Code for development so users receive real-time security feedback on vulnerable libraries and dependencies before they check in their code.
  • D. Enable Binary Authorization and create attestations of scans.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
W pytaniach typu 'Security in GCP', zawsze priorytetyzuj rozwiązania natywne (SCC, Cloud KMS, Secret Manager, VPC SC) nad rozwiązaniami typu 'third-party' lub 'self-managed', chyba że scenariusz wymaga specyficznej integracji hybrydowej.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka 'Least Privilege': Egzamin często podpowiada role o szerokim zakresie (np. 'Editor' lub 'Owner') – zawsze odrzucaj je na rzecz ról predefiniowanych o najmniejszym zakresie uprawnień.
- Pułapka 'Logging vs Monitoring': Pamiętaj: Audit Logs służą do badania aktywności (Who/What/When), a Monitoring do zbierania metryk wydajnościowych.

Głębokie wyjaśnienie techniczne:
Każda architektura bezpieczeństwa w GCP powinna być projektowana w oparciu o 'Security by Default'. Oznacza to m.in. szyfrowanie w spoczynku (domyślne), tożsamość opartą na rolach (IAM) oraz pełną widoczność zapewnianą przez scentralizowane logowanie (Cloud Logging/SCC).

Wyjaśnienie

Potwierdzona odpowiedź: D (Enable Binary Authorization and create attestations of scans.)

Wyjaśnienie:
Binary Authorization to usługa bezpieczeństwa łańcucha dostaw (supply chain security) w Google Cloud, która zapewnia, że tylko zaufane obrazy kontenerów są wdrażane w Google Kubernetes Engine (GKE) lub Cloud Run. Działa ona jako brama (admission controller), która sprawdza, czy obraz posiada wymagane atestacje (podpisy cyfrowe) przed zezwoleniem na jego uruchomienie. W opisanym scenariuszu, automatyczne skanowanie w potoku CI/CD powinno kończyć się utworzeniem atestacji dla obrazów, które przeszły weryfikację. Polityka Binary Authorization w klastrze GKE zostanie następnie skonfigurowana tak, aby wymagała tej konkretnej atestacji, co gwarantuje, że tylko "zeskanowane i zweryfikowane" kontenery będą mogły zostać uruchomione.

Dlaczego pozostałe odpowiedzi są niepoprawne:
- A. RBAC (Role-Based Access Control) służy do zarządzania uprawnieniami użytkowników i kont serwisowych wewnątrz klastra (kto co może robić), ale nie posiada mechanizmów weryfikacji integralności ani bezpieczeństwa samych obrazów kontenerów przed ich wdrożeniem.
- B. Użycie komendy gcloud do sprawdzenia podatności w potoku CI/CD i przerwanie budowania jest dobrą praktyką, ale samo w sobie nie daje gwarancji, że ktoś nie spróbuje wdrożyć innego, niezweryfikowanego obrazu bezpośrednio do klastra, omijając potok. Brakuje tutaj mechanizmu wymuszania (enforcement) na poziomie klastra, który zapewnia Binary Authorization.
- C. Cloud Code oferuje funkcje skanowania podatności w IDE, co pomaga deweloperom na wczesnym etapie ("shift left"), ale nie stanowi mechanizmu kontroli wdrożeń produkcyjnych. Użytkownicy nadal mogliby wdrażać niebezpieczne kontenery ręcznie lub przez inne narzędzia.

Wskazówki i triki (Tips & Tricks):
- Słowa kluczowe "ensure only scanned and verified containers can run" niemal zawsze wskazują na Binary Authorization.
- Pamiętaj o koncepcji "Attestors" (atestatorów) – są to byty, które poświadczają, że dany krok (np. skanowanie, testy QA) został wykonany pomyślnie.
- Binary Authorization integruje się z Container Analysis, które automatycznie skanuje obrazy w Artifact Registry.

Praktyczne informacje na egzamin:
- Binary Authorization działa na poziomie Admission Controller w Kubernetes.
- Może blokować wdrożenia na podstawie wielu atestacji (np. musi być skanowanie bezpieczeństwa ORAZ zatwierdzenie przez zespół QA).
- Tryb "Dry run" pozwala testować polityki bez faktycznego blokowania ruchu, co jest przydatne przy wdrażaniu usługi w istniejącym środowisku.
