Question 17 / 361

An employer wants to track how bonus compensations have changed over time to identify employee outliers and correct earning disparities. This task must be performed without exposing the sensitive compensation data for any individual and must be reversible to identify the outlier. Which Cloud Data Loss Prevention API technique should you use to accomplish this?

  • A. Generalization
  • B. Redaction
  • C. CryptoHashConfig
  • D. CryptoReplaceFfxFpeConfig
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

Potwierdzona odpowiedź: D (CryptoReplaceFfxFpeConfig)

Wyjaśnienie: 
Aby umożliwić analizę danych bez ujawniania wrażliwych informacji, przy zachowaniu możliwości odwrócenia tego procesu (de-identyfikacja odwracalna), należy zastosować tokenizację. `CryptoReplaceFfxFpeConfig` w Cloud DLP implementuje szyfrowanie zachowujące format (Format-Preserving Encryption - FPE). Pozwala ono zastąpić np. identyfikator pracownika tokenem o identycznym formacie. Dzięki użyciu klucza kryptograficznego, proces ten jest odwracalny – po znalezieniu anomalii (outlier), administrator może odszyfrować token, aby dowiedzieć się, o którego konkretnego pracownika chodzi.

Dlaczego pozostałe są błędne:
A. Generalization (Generalizacja): Zastępuje dokładne wartości przedziałami (np. zarobki 5000 -> 4000-6000). Jest to proces nieodwracalny, co uniemożliwiłoby późniejszą identyfikację pracownika.
B. Redaction (Redagowanie): Całkowicie usuwa lub zasłania dane (np. czarny pasek). Jest to proces definitywnie nieodwracalny.
C. CryptoHashConfig (Haszowanie): Haszowanie jest funkcją jednostronną. Chociaż pozwala na zliczanie wystąpień tej samej wartości, nie pozwala na bezpośrednie odkodowanie hasza z powrotem do tekstu jawnego bez posiadania bazy wszystkich możliwych wartości (brute-force).

Wskazówki egzaminacyjne (Tips & Tricks):
- Słowa klucze: "Without exposing sensitive data" + "Reversible" = Tokenization / FPE.
- W Google Cloud DLP, jeśli widzisz "FPE" (Format-Preserving Encryption), jest to klucz do odwracalnej anonimizacji.
- Pamiętaj: Haszowanie jest bezpieczne, ale nieodwracalne (jednostronne).

**Reguła Egzaminacyjna (Exam Rule):**
Zawsze identyfikuj warstwę modelu OSI, na której operuje atak oraz rozwiązanie. DNSSEC działa na poziomie warstwy aplikacji dla DNS, zapobiegając zatruwaniu pamięci podręcznej (Cache Poisoning).

**Haczyki egzaminacyjne (Exam Traps):**
- Mylenie Cloud Armor (WAF - L7) z zabezpieczeniami DNS (DNSSEC - integralność danych DNS).
- Zakładanie, że TLS/SSL wystarczy do ochrony przed przekierowaniem całego ruchu DNS (DNSSEC zabezpiecza sam proces rezolucji, zanim nawiążesz bezpieczne połączenie TLS).

**Głębokie wyjaśnienie techniczne:**
DNSSEC wykorzystuje kryptografię klucza publicznego (RRSIG, DNSKEY, DS) do cyfrowego podpisywania rekordów DNS w strefach (Zone Signing). Dzięki temu resolver DNS może zweryfikować łańcuch zaufania aż do punktu głównego (root zone) bez konieczności polegania wyłącznie na adresie IP serwera autorytatywnego, co drastycznie ogranicza skuteczność ataków typu MITM i cache poisoning.

Analiza i Podsumowanie Dyskusji (AI)

Analiza i Wyjaśnienie

Sugerowana odpowiedź: D

Analiza spornych kwestii (AI): Głównym punktem analizy jest wymóg 'odwracalności'. Wiele osób wybiera haszowanie (C), myśląc, że jest to standard. Jednak w kryptografii hasz jest z definicji jednostronny. FPE (D) pozwala na zachowanie struktury danych, co jest kluczowe przy analizie w bazach danych, i daje administratorowi posiadającemu klucz drogę powrotną do danych osobowych.
