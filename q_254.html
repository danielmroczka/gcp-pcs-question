Question 254 / 361

Your organization has applications that run in multiple clouds. The applications require access to a Google Cloud resource running in your project. You must use short-lived access credentials to maintain security across the clouds. What should you do?

  • A. Create a managed workload identity. Bind an attested identity to the Compute Engine workload.
  • B. Create a service account key. Download the key to each application that requires access to the Google Cloud resource.
  • C. Create a workload identity pool with a workload identity provider for each external cloud. Set up a service account and add an IAM binding for impersonation.
  • D. Create a VPC firewall rule for ingress traffic with an allowlist of the IP ranges of the external cloud applications.
Show Suggested Answer
Suggested Answer: C

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Create a workload identity pool with a workload identity provider for each external cloud. Set up a service account and add an IAM binding for impersonation.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź C jest prawidłowa, ponieważ Workload Identity Federation (Federacja Tożsamości Obciążeń) jest standardowym i najbardziej bezpiecznym mechanizmem Google Cloud umożliwiającym aplikacjom działającym w innych chmurach (np. AWS, Azure) bezpieczne odpytywanie API GCP przy użyciu tożsamości krótkotrwałych.

Zalety i mechanizm działania:
a. **Pule i dostawcy (Pools & Providers):** Tworzymy dedykowaną pulę tożsamości oraz dostawców dla poszczególnych chmur zewnętrznych (np. provider AWS korzystający z ról IAM AWS, provider Azure z OIDC).
b. **Wymiana tożsamości:** Aplikacja w innej chmurze pobiera swój natywny token tożsamości (np. AWS STS token) i wysyła go do Google STS w celu wymiany na krótkotrwały token dostępu GCP.
c. **Impersonacja (Impersonation):** Konto serwisowe w GCP posiada przypisane powiązanie IAM (`roles/iam.workloadIdentityUser`), które zezwala tożsamościom z zewnętrznej puli chmurowej na podszywanie się pod nie. Zapewnia to pełne bezpieczeństwo bez konieczności generowania i dystrybucji kluczy prywatnych.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Create a managed workload identity. Bind an attested identity to the Compute Engine workload.
   * Dlaczego nieprawidłowa: "Managed workload identity" w tym kontekście brzmi podobnie do Workload Identity w GKE lub Managed Identities w Active Directory, ale samo sformułowanie nie opisuje poprawnej procedury integracji dla aplikacji działających w zewnętrznych chmurach (multi-cloud). Ponadto Compute Engine dotyczy maszyn w GCP, a nie w innych chmurach.
B. Create a service account key. Download the key to each application...
   * Dlaczego nieprawidłowa: Pobieranie i zapisywanie kluczy prywatnych (JSON keys) konta serwisowego na maszynach w innych chmurach jest rażącym naruszeniem zasad bezpieczeństwa. W przypadku skompromitowania maszyny w chmurze zewnętrznej, klucz zostaje ujawniony, dając stały dostęp do zasobów GCP.
D. Create a VPC firewall rule for ingress traffic with an allowlist...
   * Dlaczego nieprawidłowa: Reguły zapory sieciowej (firewall rules) filtrują ruch sieciowy, ale nie uwierzytelniają aplikacji i nie wydają tokenów dostępu (credentials) wymaganych do autoryzacji zapytań do usług GCP (np. BigQuery czy GCS).

4. Wskazówki, hinty, tips and tricks:
* Uwierzytelnianie aplikacji z innych chmur (AWS, Azure, multi-cloud) w GCP bez kluczy -> Zawsze **Workload Identity Federation** (WIF).
* WIF obsługuje natywnie uwierzytelnianie oparte na kontach AWS IAM oraz Azure Active Directory OIDC.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Applications in multiple clouds + access GCP + short-lived credentials -> Workload Identity Federation (workload identity pool).
