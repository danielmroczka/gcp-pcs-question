Question 209 / 361

Your organization is transitioning to Google Cloud. You want to ensure that only trusted container images are deployed on Google Kubernetes Engine (GKE) clusters in a project. The containers must be deployed from a centrally managed Container Registry and signed by a trusted authority.

  • A. Enable Container Threat Detection in the Security Command Center (SCC) for the project.
  • B. Configure the trusted image organization policy constraint for the project.
  • C. Create a custom organization policy constraint to enforce Binary Authorization for Google Kubernetes Engine (GKE).
  • E. Configure the Binary Authorization policy with respective attestations for the project.
  • D. Enable PodSecurity standards, and set them to Restricted.
Show Suggested Answer Hide Answer
Suggested Answer: CE

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Create a custom organization policy constraint to enforce Binary Authorization for Google Kubernetes Engine (GKE).
E. Configure the Binary Authorization policy with respective attestations for the project.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedzi C i E są prawidłowe, ponieważ Binary Authorization (Autoryzacja Binarna) jest flagową usługą bezpieczeństwa Google Cloud służącą do egzekwowania wdrażania wyłącznie podpisanych i zaufanych obrazów kontenerowych na klastrach GKE.

Szczegóły wdrożenia:
a. **Polityka organizacji (C):** Aby upewnić się, że żadne klastry GKE w projektach nie ominą tego zabezpieczenia, administrator może utworzyć lub włączyć politykę organizacji wymuszającą aktywację usługi Binary Authorization na każdym nowo tworzonym klastrze GKE.
b. **Reguły i atestatory (Attestators) (E):** Konfiguracja samej polityki Binary Authorization polega na zdefiniowaniu reguł (np. blokowanie wszystkich obrazów poza określonymi wyjątkami) oraz zdefiniowaniu Atestatorów. Atestatory to tożsamości, które muszą kryptograficznie podpisać (attest) obraz kontenera (np. po pomyślnym przejściu skanowania podatności w potoku CI/CD), aby GKE zezwoliło na jego uruchomienie.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Enable Container Threat Detection in the Security Command Center (SCC) for the project.
   * Dlaczego nieprawidłowa: Container Threat Detection wykrywa zagrożenia w czasie rzeczywistym w już uruchomionych kontenerach (np. próby wykonania exploitów). Jest to kontrola reaktywna (detective), a nie prewencyjna blokada wdrożenia niepodpisanych obrazów.
B. Configure the trusted image organization policy constraint for the project.
   * Dlaczego nieprawjednoczesna: Polityka `constraints/compute.trustedImageProjects` dotyczy obrazów maszyn wirtualnych Compute Engine (GCE), a nie obrazów kontenerów (Docker/OCI) wdrażanych w klastrach Kubernetes.
D. Enable PodSecurity standards, and set them to Restricted.
   * Dlaczego nieprawidłowa: Standardy bezpieczeństwa Podów (Pod Security Standards) w Kubernetes kontrolują uprawnienia kontenerów wewnątrz systemu (np. zakaz uruchamiania jako root, dostęp do sieci hosta), ale nie weryfikują podpisów kryptograficznych samych obrazów przed wdrożeniem.

4. Wskazówki, hinty, tips and tricks:
* Weryfikacja podpisów kontenerów / dopuszczenie tylko zaufanych obrazów do uruchomienia na GKE -> Zawsze **Binary Authorization**.
* Atestacja (attestation) to proces podpisywania obrazu przez zaufany podmiot (np. potok Jenkins/GitHub Actions lub skaner podatności Cloud Build).

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Trusted container images on GKE / Signed images -> Binary Authorization.

Głęboka analiza: To pytanie testuje Twoją zdolność do budowania wielowarstwowej obrony (Defense in Depth) dla kontenerów. Sama technologia (BinAuthz) to połowa sukcesu – druga połowa to zarządzanie (Organization Policy), które gwarantuje, że technologia ta jest faktycznie używana we wszystkich klastrach w projekcie, uniemożliwiając "ludzkie błędy" przy konfiguracji klastra.
