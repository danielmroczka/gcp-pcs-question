Question 175 / 361

You are consulting with a client that requires end-to-end encryption of application data (including data in transit, data in use, and data at rest) within Google Cloud. Which options should you utilize to accomplish this? (Choose two.)

  • A. External Key Manager
  • B. Customer-supplied encryption keys
  • C. Hardware Security Module
  • D. Confidential Computing and Istio
  • E. Client-side encryption
Show Suggested Answer Hide Answer
Suggested Answer: DE

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
Jeśli scenariusz dotyczy zabezpieczania zasobów chmurowych (GCP), zawsze wybieraj rozwiązanie typu Managed (SCC, Secret Manager, Cloud KMS), a unikaj rozwiązań self-managed, chyba że pytanie wyraźnie wymaga dostosowania niskopoziomowego.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka IAM: Pytania o uprawnienia często sugerują 'Project Owner' – zawsze szukaj 'Least Privilege' (np. 'Role: Secret Manager Secret Accessor').
- Pułapka Sieciowa: Często mylone są VPC Peering (wydajność) oraz VPN (szyfrowanie/on-premise).

Głębokie wyjaśnienie techniczne:
Rozwiązanie bazuje na GCP Shared Responsibility Model. Google zarządza bezpieczeństwem infrastruktury (Physical, Network, Host), podczas gdy administrator zarządza tożsamością (IAM), danymi (Encryption, Cloud KMS) i regułami dostępu (VPC Firewall).

Wyjaśnienie

Poprawna odpowiedź: DE (D: Confidential Computing and Istio, E: Client-side encryption)

Dlaczego te odpowiedzi są poprawne:
- Kluczowe wymaganie: Szyfrowanie danych w trzech stanach: "in transit" (w ruchu), "in use" (podczas przetwarzania) oraz "at rest" (podczas przechowywania).
- D. Confidential Computing i Istio:
    - Confidential Computing: Rozwiązuje problem szyfrowania danych "in use". Dzięki technologii TEE (Trusted Execution Environment) dane są szyfrowane bezpośrednio w pamięci RAM, co chroni je nawet przed administratorem hosta lub samym Google.
    - Istio: Jest to service mesh, który automatycznie zapewnia szyfrowanie "in transit" między mikroserwisami za pomocą Mutual TLS (mTLS). Szyfrowanie "at rest" w GCP jest domyślne dla wszystkich usług.
- E. Client-side encryption: Jest to alternatywne podejście, w którym dane są szyfrowane jeszcze zanim trafią do Google Cloud. Dzięki temu są one zaszyfrowane "at rest" (na dyskach Google), "in transit" (podczas przesyłania) oraz "in use" (z punktu widzenia Google, ponieważ platforma widzi tylko zaszyfrowane bloki danych i nie może ich przetworzyć bez klucza klienta).

Analiza niepoprawnych odpowiedzi:
- A. External Key Manager (EKM): EKM pomaga zarządzać kluczami do szyfrowania danych "at rest" poza infrastrukturą Google, ale sam w sobie nie zapewnia szyfrowania danych "in use".
- B. Customer-supplied encryption keys (CSEK): Podobnie jak EKM i CMEK, CSEK służy głównie do ochrony danych "at rest". Dane muszą zostać odszyfrowane w pamięci RAM, aby procesor mógł na nich operować, więc nie chroni to stanu "in use".
- C. Hardware Security Module (HSM): HSM to urządzenie sprzętowe do bezpiecznego przechowywania kluczy i wykonywania operacji kryptograficznych. Nie jest to technologia służąca do szyfrowania danych aplikacyjnych "in use" czy "in transit" w skali całej platformy.

Wskazówki i triki (Tips & Tricks):
- "Data in use" = Confidential Computing (AMD SEV / Intel TDX).
- "Data in transit" (Internal) = Istio / Anthos Service Mesh.
- "Data at rest" = CMEK / CSEK / Default encryption.
- Jeśli widzisz "End-to-end" i masz opcję Client-side encryption – zazwyczaj jest ona poprawna, bo daje największą kontrolę.

Praktyczne informacje na egzamin:
- Zapamiętaj, że domyślnie Google szyfruje dane "at rest" (AES-256) oraz "in transit" (TLS) na swoich łączach, ale klient może chcieć dodatkowych warstw kontroli.
- Confidential Computing jest dostępne na instancjach N2D oraz C3 (z AMD SEV).

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: DE

Analiza strategiczna: To pytanie sprawdza holistyczne podejście do bezpieczeństwa danych. Tradycyjne chmury skupiały się na ochronie dysków i transmisji. Google Cloud idzie krok dalej z "Confidential Computing", eliminując ostatnią lukę - dane w pamięci RAM procesora. Połączenie tego z mTLS (Istio) daje pełny stos ochrony "Zero Trust" wewnątrz chmury.

Dodatkowe wskazówki

  • Szyfrowanie po stronie klienta (Client-side) jest najbezpieczniejsze, ale uniemożliwia korzystanie z wielu funkcji chmurowych (np. przeszukiwanie danych w BigQuery, transkodowanie wideo).
  • Confidential GKE nodes pozwalają na uruchamianie całych klastrów Kubernetes w trybie poufnym.
