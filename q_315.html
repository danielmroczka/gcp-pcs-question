Question 315 / 361

Your organization is building a real-time recommendation engine using ML models that process live user activity data stored in BigQuery and Cloud Storage. Each new model developed is saved to Artifact Registry. This new system deploys models to Google Kubernetes Engine, and uses Pub/Sub for message queues. Recent industry news have been reporting attacks exploiting ML model supply chains. You need to enhance the security in this serverless architecture, specifically against risks to the development and deployment pipeline. What should you do?

  • A. Enable container image vulnerability scanning during development and pre-deployment. Enforce Binary Authorization on images deployed from Artifact Registry to your continuous integration and continuous deployment (CI/CD) pipeline.
  • B. Thoroughly sanitize all training data prior to model development to reduce risk of poisoning attacks. Use IAM for authorization, and apply role-based restrictions to code repositories and cloud services.
  • C. Limit external libraries and dependencies that are used for the ML models as much as possible. Continuously rotate encryption keys that are used to access the user data from BigQuery and Cloud Storage.
  • D. Develop strict firewall rules to limit external traffic to Cloud Run instances. Integrate intrusion detection systems (IDS) for real-time anomaly detection on Pub/Sub message flows.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
W pytaniach typu 'Security in GCP', zawsze priorytetyzuj rozwiązania natywne (SCC, Cloud KMS, Secret Manager, VPC SC) nad rozwiązaniami typu 'third-party' lub 'self-managed', chyba że scenariusz wymaga specyficznej integracji hybrydowej.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka 'Least Privilege': Egzamin często podpowiada role o szerokim zakresie (np. 'Editor' lub 'Owner') – zawsze odrzucaj je na rzecz ról predefiniowanych o najmniejszym zakresie uprawnień.
- Pułapka 'Logging vs Monitoring': Pamiętaj: Audit Logs służą do badania aktywności (Who/What/When), a Monitoring do zbierania metryk wydajnościowych.

Głębokie wyjaśnienie techniczne:
Każda architektura bezpieczeństwa w GCP powinna być projektowana w oparciu o 'Security by Default'. Oznacza to m.in. szyfrowanie w spoczynku (domyślne), tożsamość opartą na rolach (IAM) oraz pełną widoczność zapewnianą przez scentralizowane logowanie (Cloud Logging/SCC).

Wyjaśnienie

Potwierdzona odpowiedź: A (Enable container image vulnerability scanning during development and pre-deployment. Enforce Binary Authorization on images deployed from Artifact Registry to your continuous integration and continuous deployment (CI/CD) pipeline.)

Wyjaśnienie:
Aby zabezpieczyć łańcuch dostaw modeli ML (ML model supply chain) przed atakami, kluczowe jest zapewnienie integralności i bezpieczeństwa artefaktów (obrazów kontenerów) od momentu ich utworzenia do momentu wdrożenia. Włączenie automatycznego skanowania podatności (Vulnerability Scanning) w Artifact Registry pozwala na wczesne wykrycie zagrożeń w obrazach. Wymuszenie Binary Authorization na klastrach GKE gwarantuje, że tylko te obrazy, które przeszły pomyślnie proces weryfikacji i posiadają odpowiednie atestacje (np. brak krytycznych podatności, zatwierdzenie przez potok CI/CD), będą mogły zostać uruchomione w środowisku produkcyjnym.

Dlaczego pozostałe odpowiedzi są niepoprawne:
- B. Sanityzacja danych treningowych (data sanitization) i restrykcje IAM są ważnymi elementami bezpieczeństwa ML (ochrona przed poisoning attacks), ale nie adresują bezpośrednio ryzyka związanego z potokiem wdrożeniowym (deployment pipeline), o który pyta scenariusz. Binary Authorization jest bardziej specyficznym rozwiązaniem dla bezpieczeństwa "supply chain".
- C. Ograniczanie zewnętrznych bibliotek i rotacja kluczy szyfrujących to ogólne dobre praktyki bezpieczeństwa, ale nie stanowią kompleksowego rozwiązania dla ochrony łańcucha dostaw kontenerów w środowisku GKE.
- D. Reguły zapory ogniowej (firewall rules) i systemy IDS chronią infrastrukturę przed atakami sieciowymi i anomaliami w przepływie wiadomości, ale nie weryfikują, czy kod/model wewnątrz kontenera jest bezpieczny i pochodzi z zaufanego źródła.

Wskazówki i triki (Tips & Tricks):
- "Supply chain attacks" + "pipeline" + "containers" = Skanowanie podatności + Binary Authorization.
- Pamiętaj, że w Google Cloud atestacje są przechowywane jako metadane w Container Analysis.
- Model ML w kontenerze traktujemy tak samo jak każdą inną aplikację kontenerową z punktu widzenia bezpieczeństwa potoku.

Praktyczne informacje na egzamin:
- Binary Authorization integruje się z Cloud Build, umożliwiając automatyczne podpisywanie obrazów (atestację) po pomyślnym zbudowaniu i przetestowaniu.
- Vulnerability scanning w Artifact Registry może być skanowaniem przy przesyłaniu (on-upload) lub ciągłym (continuous).
- Zwróć uwagę na "Binary Authorization" jako kluczowy mechanizm wymuszania (enforcement).

- https://cloud.google.com/architecture/software-supply-chain-security

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: A

Analiza strategiczna: To pytanie skupia się na bezpieczeństwie nowoczesnych potoków ML Ops. Kluczem jest zrozumienie, że model ML dostarczany jako kontener musi podlegać tym samym rygorystycznym kontrolom łańcucha dostaw (supply chain), co tradycyjny kod aplikacji.
