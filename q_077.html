Question 77 / 361

Last week, a company deployed a new App Engine application that writes logs to BigQuery. No other workloads are running in the project. You need to validate that all data written to BigQuery was done using the App Engine Default Service Account. What should you do?

  • A. 1. Use Cloud Logging and filter on BigQuery Insert Jobs. 2. Click on the email address in line with the App Engine Default Service Account in the authentication field. 3. Click Hide Matching Entries. 4. Make sure the resulting list is empty.
  • B. 1. Use Cloud Logging and filter on BigQuery Insert Jobs. 2. Click on the email address in line with the App Engine Default Service Account in the authentication field. 3. Click Show Matching Entries. 4. Make sure the resulting list is empty.
  • C. 1. In BigQuery, select the related dataset. 2. Make sure that the App Engine Default Service Account is the only account that can write to the dataset.
  • D. 1. Go to the Identity and Access Management (IAM) section of the project. 2. Validate that the App Engine Default Service Account is the only account that has a role that can write to BigQuery.
Show Suggested Answer Hide Answer
Suggested Answer: A

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
A.1. Use Cloud Logging and filter on BigQuery Insert Jobs. 2. Click on the email address in line with the App Engine Default Service Account in the authentication field. 3. Click Hide Matching Entries. 4. Make sure the resulting list is empty.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Prawidłowa odpowiedź opiera się na zasadniczym wykorzystaniu Google Cloud Logging jako centralnego narzędzia do audytu i monitorowania aktywności w projekcie GCP. Scenariusz wymaga weryfikacji, że WSZYSTKIE operacje zapisu danych do BigQuery zostały wykonane WYŁĄCZNIE przez konkretny Service Account – App Engine Default Service Account. Oznacza to, że musimy udowodnić brak jakichkolwiek innych źródeł zapisu.

Cloud Logging automatycznie gromadzi logi audytu dla większości usług GCP, w tym BigQuery. Te logi zawierają kluczowe informacje, takie jak:
  Kto wykonał akcję (pole authenticationInfo.principalEmail).
  Co zostało wykonane (pole protoPayload.methodName lub protoPayload.serviceName).
  Kiedy akcja miała miejsce.
  Na jakim zasobie (np. BigQuery dataset, table).

Kroki opisane w opcji A są logiczną i skuteczną metodą osiągnięcia celu:
1.  Use Cloud Logging and filter on BigQuery Insert Jobs: Pierwszym krokiem jest zawężenie zakresu logów do istotnych operacji. Operacje zapisu danych do BigQuery są zazwyczaj rejestrowane pod metodami takimi jak tabledata.insertAll, jobs.insert (dla zadań ładowania), lub podobnymi. Filtrowanie po "BigQuery Insert Jobs" jest ogólnym określeniem obejmującym te typy zdarzeń w logach audytu BigQuery.
2.  Click on the email address in line with the App Engine Default Service Account in the authentication field: Po uzyskaniu listy wszystkich operacji zapisu do BigQuery, następnym krokiem jest identyfikacja tych, które zostały wykonane przez App Engine Default Service Account. W interfejsie Cloud Logging można łatwo filtrować logi według pola authenticationInfo.principalEmail, które zawiera adres e-mail Service Account lub użytkownika wykonującego akcję.
3.  Click Hide Matching Entries: To jest kluczowy element tej odpowiedzi. Zamiast pokazywać wpisy wykonane przez App Engine Default Service Account, ukrywamy je. Logika polega na tym, że jeśli App Engine Default Service Account jest jedynym podmiotem wykonującym zapisy, to po ukryciu wszystkich wpisów, które zostały przez niego wykonane, w rezultacie nie powinno zostać NIC.
4.  Make sure the resulting list is empty: Jeśli po ukryciu wszystkich BigQuery Insert Jobs wykonanych przez App Engine Default Service Account lista jest pusta, oznacza to, że absolutnie wszystkie operacje zapisu do BigQuery w badanym okresie zostały wykonane przez ten konkretny Service Account. To bezpośrednio potwierdza wymaganie pytania, że "all data written to BigQuery was done using the App Engine Default Service Account".
Jest to najlepsza praktyka w audycie bezpieczeństwa, ponieważ bezpośrednio weryfikuje historyczne działania (a nie tylko uprawnienia) i wykorzystuje domyślne możliwości monitorowania GCP.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
B.1. Use Cloud Logging and filter on BigQuery Insert Jobs. 2. Click on the email address in line with the App Engine Default Service Account in the authentication field. 3. Click Show Matching Entries. 4. Make sure the resulting list is empty.
  Ta opcja jest błędna z powodu użycia "Show Matching Entries" w połączeniu z oczekiwaniem pustej listy.
  Jeśli po filtrowaniu na BigQuery Insert Jobs i wybraniu App Engine Default Service Account klikniemy "Show Matching Entries" i otrzymamy pustą listę, oznaczałoby to, że App Engine Default Service Account NIE wykonał ŻADNYCH operacji zapisu do BigQuery. To bezpośrednio zaprzeczałoby postawionemu w pytaniu warunkowi, że "new App Engine application that writes logs to BigQuery". Celem jest udowodnienie, że TYLKO ten Service Account pisał, a nie, że w ogóle nie pisał. "Show Matching Entries" miałoby sens, gdybyśmy chcieli zobaczyć WSZYSTKIE wpisy danego SA, a potem ręcznie sprawdzić, czy nie ma tam niczego od innych SA, ale to nie jest tak efektywne jak metoda z ukrywaniem.

C.1. In BigQuery, select the related dataset. 2. Make sure that the App Engine Default Service Account is the only account that can write to the dataset.
  Ta opcja skupia się na zarządzaniu tożsamością i dostępem (Identity and Access Management – IAM), a nie na audycie historycznych działań. Sprawdzenie, kto "can write" (ma uprawnienia do zapisu) jest kluczowe dla prewencji i zarządzania bezpieczeństwem, ale nie potwierdza, kto "did write" (wykonał zapis) w przeszłości. Uprawnienia mogły zostać zmienione w dowolnym momencie. Innymi słowy, nawet jeśli w danej chwili tylko App Engine Default Service Account ma uprawnienia do zapisu, nie ma to żadnego wpływu na to, kto mógł mieć takie uprawnienia i z nich skorzystać w zeszłym tygodniu (czyli w okresie, w którym aplikacja została wdrożona i zaczęła pisać logi). Pytanie wyraźnie dotyczy walidacji historycznej aktywności ("all data written [...] was done").

D.1. Go to the Identity and Access Management (IAM) section of the project. 2. Validate that the App Engine Default Service Account is the only account that has a role that can write to BigQuery.
  Podobnie jak opcja C, ta odpowiedź błędnie koncentruje się na konfiguracji IAM, a nie na logach audytu. IAM kontroluje "kto może" (permissions), a nie "kto faktycznie wykonał" (audit trail). Sprawdzenie ról w sekcji IAM projektu pokaże aktualny stan uprawnień, ale nie dostarczy dowodu, że wszystkie zapisy zostały wykonane przez konkretny Service Account w przeszłości. Co więcej, uprawnienia mogą być nadawane na różnych poziomach hierarchii (projekt, folder, organizacja, zasób), a także poprzez przypisanie ról do grup, co komplikuje prostą weryfikację. Audyt logów jest jedynym niezawodnym sposobem potwierdzenia faktycznych działań.

4. Wskazówki, hinty, tips and tricks:
  Rozróżnienie na egzaminie: Zawsze zwracaj uwagę na kluczowe słowa w pytaniu, które wskazują, czy chodzi o konfigurację (IAM, Network Policies, Storage Classes) czy o audyt/monitorowanie (Cloud Logging, Cloud Monitoring, Security Command Center). Frazy typu "validate that all data was done", "ensure only X performed Y", "investigate an incident" niemal zawsze kierują w stronę Cloud Logging.
  Logika "Show/Hide Matching Entries": Zrozumienie, jak działają filtry w Cloud Logging, jest kluczowe. "Hide Matching Entries" jest często używane do wyszukiwania anomalii lub sprawdzania, czy nic poza oczekiwanym nie wystąpiło. Jeśli szukamy, czy tylko jeden podmiot wykonał daną akcję, filtrujemy wszystkie akcje, a następnie "ukrywamy" te wykonane przez oczekiwany podmiot. Jeśli coś zostanie, to znaczy, że ktoś inny to zrobił. Jeśli lista jest pusta, to nikt inny tego nie zrobił.
  IAM vs. Auditing: To częsta pułapka egzaminacyjna. IAM określa potencjalny zakres działania użytkownika lub Service Account. Cloud Logging rejestruje faktyczne, wykonane akcje. Pytania o "kto zrobił" lub "czy na pewno tylko X zrobił" zawsze wymagają audytu, a nie sprawdzenia konfiguracji uprawnień.
  Default Service Account: Pamiętaj, że wiele usług GCP (takich jak App Engine, Cloud Functions, Cloud Run, Compute Engine) ma domyślne Service Accounts. Na egzaminie często pojawiają się pytania dotyczące ich uprawnień lub aktywności. Domyślne Service Accounts posiadają szerokie uprawnienia domyślnie, co jest często celem analizy bezpieczeństwa.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
  Jeśli pytanie wspomina o "validate that all data was done by [specific entity]" lub "ensure only [specific entity] performed [action]", szukaj odpowiedzi zawierającej "Cloud Logging" i logiczne kroki filtrowania i weryfikacji logów, często z wykorzystaniem logiki "Hide Matching Entries" lub porównywania dwóch zestawów logów.
  Gdy celem jest audytowanie historycznych działań lub weryfikacja, kto faktycznie wykonał daną operację, wybierz opcję, która wykorzystuje "Cloud Logging" lub inne narzędzia do analizy logów audytu (np. BigQuery Export logów).
  Jeśli pytanie dotyczy "who can perform [action]" lub "controlling access", szukaj odpowiedzi odnoszących się do "Identity and Access Management (IAM)", "roles", "permissions" lub "Access Control Lists (ACLs)". Pamiętaj, że to dotyczy uprawnień, a nie wykonanych akcji.
  Kiedy w pytaniu pojawiają się frazy takie jak "anomalies", "unexpected activity" lub "non-compliant actions", odpowiedzi często będą odwoływać się do Cloud Logging w celu wyszukiwania nietypowych wpisów, a także do Security Command Center dla kompleksowej oceny bezpieczeństwa.
  Dla potwierdzenia wyłączności (np. "only this account did X"), należy zawsze szukać metod, które eliminują wszystkie inne możliwości. W Cloud Logging często oznacza to filtrowanie po wszystkich interesujących zdarzeniach, a następnie odrzucenie (ukrycie) tych, które pochodzą od oczekiwanego podmiotu – jeśli nic nie pozostanie, oznacza to wyłączność.
