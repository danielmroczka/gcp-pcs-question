Question 331 / 361

Your organization uses a microservices architecture based on Google Kubernetes Engine (GKE). Recent security reviews recommend tighter controls around deployed container images to reduce potential vulnerabilities and maintain compliance. You need to implement an automated system by using managed services to ensure that only approved container images are deployed to the GKE clusters. What should you do?

  • A. Develop custom organization policies that restrict GKE cluster deployments to container images hosted within a specific Artifact Registry project where your approved images reside.
  • B. Enforce Binary Authorization in your GKE clusters. Integrate container image vulnerability scanning into the CI/CD pipeline and require vulnerability scan results to be used for Binary Authorization policy decisions.
  • C. Automatically deploy new container images upon successful CI/CD builds by using Cloud Build triggers. Set up firewall rules to limit and control access to instances to mitigate malware injection.
  • D. Build a system using third-party vulnerability databases and custom scripts to identify potential Common Vulnerabilities and Exposures (CVEs) in your container images. Prevent image deployment if the CVE impact score is beyond a specified threshold.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

✅ PRAWIDŁOWA ODPOWIEDŹ: B

Prawidłowa odpowiedź: B – Enforce Binary Authorization in your GKE clusters. Integrate container image vulnerability scanning with Artifact Registry and create attestations of successful scans.

DLACZEGO B JEST PRAWIDŁOWE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
To kompleksowe rozwiązanie supply chain security dla GKE:
1. Binary Authorization = wymuszenie że tylko attested obrazy mogą być deployed.
2. Artifact Registry vulnerability scanning = automatyczne skanowanie przy push.
3. Attestations = kryptograficzne potwierdzenia ze skanowania, wymagane przez Binary Authorization.
Razem tworzą automatyczny, niezawodny pipeline bezpieczeństwa kontenerów.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
DLACZEGO INNE OPCJE SĄ BŁĘDNE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
A. ❌ Custom org policies dla "hosted in Artifact Registry" = ogranicza source rejestru, ale nie weryfikuje czy obraz był skanowany. Brak attestation enforcement.
C. ❌ Auto-deploy po CI/CD build = brak weryfikacji bezpieczeństwa obrazu przed deploymentem. "Successful build" ≠ "secure image".
D. ❌ Third-party databases + custom scripts = niespójne, trudne do utrzymania, nie natywne GCP rozwiązanie. Opcja B jest wbudowana.

WSKAZÓWKI EGZAMINACYJNE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• Container image security GKE = Binary Authorization + Artifact Registry + Attestations.
• Attestations = "dowód" że skan się odbył i był pomyślny.
• Binary Authorization bez attestations = tylko weryfikacja źródła, nie bezpieczeństwa.
