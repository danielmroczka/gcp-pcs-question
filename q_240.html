Question 240 / 361

Your customer has an on-premises Public Key Infrastructure (PKI) with a certificate authority (CA). You need to issue certificates for many HTTP load balancer frontends. The on-premises PKI should be minimally affected due to many manual processes, and the solution needs to scale. What should you do?

  • A. Use Certificate Manager to issue Google managed public certificates and configure it at HTTP the load balancers in your infrastructure as code (IaC).
  • B. Use a subordinate CA in the Google Certificate Authority Service from the on-premises PKI system to issue certificates for the load balancers.
  • C. Use Certificate Manager to import certificates issued from on-premises PKI and for the frontends. Leverage the gcloud tool for importing.
  • D. Use the web applications with PKCS12 certificates issued from subordinate CA based on OpenSSL on-premises. Use the gcloud tool for importing. Use the External TCP/UDP Network load balancer instead of an external HTTP Load Balancer.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
B. Use a subordinate CA in the Google Certificate Authority Service from the on-premises PKI system to issue certificates for the load balancers.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź B jest prawidłowa, ponieważ wykorzystanie podrzędnego urzędu certyfikacji (Subordinate CA) w ramach usługi Google Certificate Authority Service (CAS), który jest podpisany przez lokalny (on-premises) główny urząd certyfikacji (Root CA), pozwala na automatyczne, bezpieczne i wysoce skalowalne wystawianie certyfikatów w chmurze bez obciążania lokalnego zespołu PKI.

Zalety tego rozwiązania:
a. **Skalowalność i automatyzacja:** Google CAS jest w pełni zarządzaną, wysoce dostępną usługą. Po skonfigurowaniu podrzędnego CA w CAS, certyfikaty dla Load Balancerów mogą być wystawiane automatycznie (np. przy użyciu integracji z Certificate Managerem) w kilka sekund, bez konieczności ręcznego generowania żądań i podpisywania ich on-premises.
b. **Zachowanie zaufania (Chain of Trust):** Ponieważ podrzędny CA w chmurze jest podpisany przez lokalny Root CA firmy, wszystkie systemy wewnątrz organizacji (które domyślnie ufają lokalnemu Root CA) będą automatycznie ufać certyfikatom wystawionym w GCP.
c. **Minimalizacja wpływu na on-premises PKI:** Lokalny zespół PKI musi uczestniczyć w procesie tylko raz – podczas jednorazowego podpisania certyfikatu podrzędnego urzędu (subordinate CA) dla chmury.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Use Certificate Manager to issue Google managed public certificates...
   * Dlaczego nieprawidłowa: Zautomatyzowane publiczne certyfikaty zarządzane przez Google są wystawiane przez publiczne urzędy certyfikacji (np. Let's Encrypt). Nie są one powiązane z wewnętrzną, lokalną infrastrukturą PKI firmy (on-premises PKI) i nie mogą być używane dla zasobów wewnętrznych wymagających zaufania do lokalnego Root CA.
C. Use Certificate Manager to import certificates issued from on-premises PKI...
   * Dlaczego nieprawidłowa: Ręczne lub skryptowe importowanie certyfikatów wygenerowanych on-premises wymaga ciągłego zaangażowania lokalnego zespołu PKI przy każdym nowym certyfikacie oraz przy ich odnawianiu (renewals). Nie jest to rozwiązanie skalowalne i znacznie obciąża lokalną PKI.
D. Use the web applications with PKCS12 certificates... External TCP/UDP Network load balancer...
   * Dlaczego nieprawidłowa: PKCS12 to format kontenera (często zawierający klucz prywatny i certyfikat), który nie jest bezpośrednio używany na load balancerach HTTP w ten sposób. Ponadto przejście na External TCP/UDP Network Load Balancer (który działa w warstwie 4) uniemożliwia terminowanie połączeń SSL na poziomie Load Balancera (brak funkcji warstwy 7, takich jak routing URL czy IAP), co zmusza do zarządzania certyfikatami na samych maszynach wirtualnych (ogromny narzut operacyjny).

4. Wskazówki, hinty, tips and tricks:
* Jeśli firma posiada własne PKI on-premises i chce zintegrować je z GCP w celu skalowalnego wystawiania certyfikatów -> Zawsze używaj **Certificate Authority Service (CAS)** w trybie **Subordinate CA** (podrzędny urząd certyfikacji).
* Pozwala to na zachowanie łańcucha zaufania (Chain of Trust) przy jednoczesnym przeniesieniu ciężaru wystawiania certyfikatów do chmury.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* On-premises PKI + scale + issue certificates for load balancers -> Subordinate CA in Google Certificate Authority Service (CAS).
