Question 257 / 361

You are running code in Google Kubernetes Engine (GKE) containers in Google Cloud that require access to objects stored in a Cloud Storage bucket. You need to securely grant the Pods access to the bucket while minimizing management overhead. What should you do?

  • A. Create a service account. Grant bucket access to the Pods by using Workload Identity Federation for GKE.
  • B. Create a service account with keys. Store the keys in Secret Manager with a 30-day rotation schedule. Reference the keys in the Pods.
  • C. Create a service account with keys. Store the keys as a Kubernetes secret. Reference the keys in the Pods.
  • D. Create a service account with keys. Store the keys in Secret Manager. Reference the keys in the Pods.
Show Suggested Answer
Suggested Answer: A

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
A. Create a service account. Grant bucket access to the Pods by using Workload Identity Federation for GKE.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź A jest prawidłowa, ponieważ Workload Identity Federation for GKE (dawniej znane jako GKE Workload Identity) jest zalecaną i najbezpieczniejszą metodą nadawania uprawnień IAM aplikacjom działającym w kontenerach na klastrach GKE.

Mechanizm działania i zalety:
a. **Mapowanie tożsamości Kubernetes na IAM:** Łączymy konto serwisowe Kubernetes (KSA - używane wewnątrz klastra przez Pod) z kontem serwisowym Google Cloud (GSA).
b. **Brak kluczy:** Pod pobiera krótkotrwałe tokeny dostępu bezpośrednio z serwera metadanych GKE w locie. Całkowicie eliminuje to potrzebę generowania, zapisywania, rotowania i zabezpieczania fizycznych kluczy prywatnych kont serwisowych (plików JSON) wewnątrz klastra.
c. **Minimalizacja narzutu (least management overhead):** Zarządzanie uprawnieniami odbywa się w pełni deklaratywnie przez pliki YAML w Kubernetes, a tokeny są odnawiane automatycznie przez platformę GCP.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
B. ...Store the keys in Secret Manager with a 30-day rotation schedule...
   * Dlaczego nieprawidłowa: Zapisywanie kluczy w Secret Managerze i wdrażanie ich rotacji co 30 dni wymaga napisania i utrzymywania własnych skryptów rotujących klucze i aktualizujących je w Podach. Generuje to duży narzut administracyjny (management overhead) w porównaniu do bezkluczowego Workload Identity.
C. ...Store the keys as a Kubernetes secret. Reference the keys in the Pods.
   * Dlaczego nieprawidłowa: Przechowywanie kluczy prywatnych jako Kubernetes Secrets jest mniej bezpieczne (są one jedynie zakodowane w Base64 i mogą zostać odczytane przez każdego z dostępem do namespace) oraz wymaga ręcznego odnawiania kluczy przed ich wygaśnięciem.
D. ...Store the keys in Secret Manager. Reference the keys...
   * Dlaczego nieprawidłowa: Podobnie jak opcja B, ta metoda wymaga zarządzania sekretami i integracji z Secret Managerem z poziomu kodu aplikacji w Podach, co zwiększa złożoność kodu i narzut operacyjny w porównaniu z automatycznym i natywnym Workload Identity.

4. Wskazówki, hinty, tips and tricks:
* Nadawanie uprawnień Podom w GKE do usług GCP (GCS, BigQuery itp.) -> Zawsze wybieraj **Workload Identity Federation for GKE** (Workload Identity).
* Jest to złoty standard bezpieczeństwa GKE eliminujący pliki kluczy kont serwisowych.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* GKE containers/Pods + access Cloud Storage bucket + minimize management overhead -> Workload Identity Federation for GKE.
