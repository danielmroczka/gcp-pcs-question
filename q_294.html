Question 294 / 361

Your organization has an internet-facing application behind a load balancer. Your regulators require end-to-end encryption of user login credentials. You must implement this requirement. What should you do?

  • A. Generate a symmetric key with Cloud KMS. Encrypt client-side user credentials by using the symmetric key.
  • B. Concatenate the credential with a timestamp. Submit the timestamp and hashed value of credentials to the network.
  • C. Deploy the TLS certificate at Google Cloud Global HTTPs Load Balancer, and submit the user credentials through HTTPs.
  • D. Generate an asymmetric key with Cloud KMS. Encrypt client-side user credentials using the public key.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Deploy the TLS certificate at Google Cloud Global HTTPs Load Balancer, and submit the user credentials through HTTPs.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź C jest prawidłowa, ponieważ przesłanie poświadczeń użytkownika (credentials) przez bezpieczny protokół HTTPS (zabezpieczony certyfikatem TLS terminowanym na globalnym Load Balancerze HTTPS) jest standardowym, bezpiecznym i powszechnie akceptowanym przez audytorów sposobem na zapewnienie szyfrowania danych logowania w transporcie.

Dlaczego to poprawne podejście:
a. **Szyfrowanie w transporcie (Transit Encryption):** Protokół TLS szyfruje całą sesję HTTP, w tym nagłówki, ciasteczka sesyjne oraz treść żądania (payload zawierający login i hasło) przed opuszczeniem przeglądarki użytkownika.
b. **Globalny Load Balancer:** Terminowanie połączeń TLS na poziomie Global HTTPS Load Balancera (GFE) chroni aplikację przed atakami DDoS i pozwala na centralne zarządzanie certyfikatami SSL za pomocą Certificate Managera. Po deszyfrowaniu, ruch do maszyn backendowych w sieci VPC również może być szyfrowany (end-to-end), jeśli skonfigurujemy HTTPS na backendzie.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Generate a symmetric key with Cloud KMS. Encrypt client-side user credentials by using the symmetric key.
   * Dlaczego nieprawidłowa: Szyfrowanie symetryczne wymaga posiadania tego samego klucza po stronie klienta (przeglądarki) i serwera. Przekazanie klucza symetrycznego do kodu JavaScript w przeglądarce użytkownika oznacza, że klucz ten stałby się publicznie dostępny dla każdego (w tym dla napastników), co całkowicie kompromituje bezpieczeństwo szyfrowania.
B. Concatenate the credential with a timestamp. Submit the timestamp and hashed value...
   * Dlaczego nieprawidłowa: Samo haszowanie hasła z solą/timestampem bez szyfrowania kanału komunikacji (TLS) chroni przed niektórymi atakami typu replay, ale nie zapewnia pełnej ochrony w transporcie i nie stanowi standardowego mechanizmu end-to-end encryption wymaganego przez współczesne regulacje bezpieczeństwa.
D. Generate an asymmetric key with Cloud KMS. Encrypt client-side user credentials using the public key.
   * Dlaczego nieprawidłowa: Choć szyfrowanie kluczem publicznym (asymetrycznym) w przeglądarce jest kryptograficznie bezpieczne (tylko serwer posiadający klucz prywatny w KMS może odszyfrować dane), to wdrażanie własnego szyfrowania aplikacyjnego w przeglądarce bez TLS jest niezwykle skomplikowane, podatne na błędy implementacji i niepotrzebne, ponieważ standardowy protokół HTTPS (TLS) realizuje to zadanie automatycznie i bezpiecznie na poziomie przeglądarki i serwera web.

4. Wskazówki, hinty, tips and tricks:
* Bezpieczne przesyłanie poświadczeń w internecie (encryption of credentials in transit) -> Zawsze używaj **HTTPS / TLS** z certyfikatem zainstalowanym na **Load Balancerze**.
* Unikaj własnych systemów szyfrowania haseł w kodzie JavaScript przeglądarki.

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* End-to-end encryption of user credentials / secure transport -> Deploy TLS certificate on HTTPs Load Balancer + submit via HTTPs.
