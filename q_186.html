Question 186 / 361

You have stored company approved compute images in a single Google Cloud project that is used as an image repository. This project is protected with VPC Service Controls and exists in the perimeter along with other projects in your organization. This lets other projects deploy images from the image repository project. A team requires deploying a third-party disk image that is stored in an external Google Cloud organization. You need to grant read access to the disk image so that it can be deployed into the perimeter.
What should you do?

  • A. Allow the external project by using the organizational policy, constraints/compute.trustedImageProjects.
  • B. 1. Update the perimeter. 2. Configure the egressTo field to include the external Google Cloud project number as an allowed resource and the serviceName to compute.googleapis.com. 3. Configure the egressFrom field to set identityType to ANY_IDENTITY.
  • C. 1. Update the perimeter. 2. Configure the ingressFrom field to set identityType to ANY_IDENTITY. 3. Configure the ingressTo field to include the external Google Cloud project number as an allowed resource and the serviceName to compute.googleapis.com.
  • D. 1. Update the perimeter. 2. Configure the egressTo field to set identityType to ANY_IDENTITY. 3. Configure the egressFrom field to include the external Google Cloud project number as an allowed resource and the serviceName to compute.googleapis.com.

Suggested Answer: B

Wyjaśnienie

Potwierdzona odpowiedź: B (1. Update the perimeter. 2. Configure the egressTo field to include the external Google Cloud project number as an allowed resource and the serviceName to compute.googleapis.com. 3. Configure the egressFrom field to set identityType to ANY_IDENTITY).

Wyjaśnienie:
VPC Service Controls (VPC SC) domyślnie blokuje komunikację z usługami Google Cloud (API) znajdującymi się poza perymetrem. W tej sytuacji żądanie pobrania obrazu wychodzi Z Twojego perymetru DO zewnętrznego projektu. Jest to ruch typu "Egress". Aby go umożliwić, należy:
1. Skonfigurować `egressTo`, wskazując numer zewnętrznego projektu jako zasób (resource) oraz usługę `compute.googleapis.com`.
2. Skonfigurować `egressFrom`, określając, kto może wykonać to połączenie (ustawienie `ANY_IDENTITY` pozwala każdemu uwierzytelnionemu użytkownikowi wewnątrz perymetru na taką próbę, pod warunkiem posiadania odpowiednich uprawnień IAM).
To rozwiązanie precyzyjnie "wycina otwór" w perymetrze tylko dla konkretnego celu, zachowując ochronę przed ogólną eksfiltracją danych.

Dlaczego pozostałe są błędne:
- A. Organization policy (trustedImageProjects): Ta polityka ogranicza to, co można zrobić wewnątrz projektu, ale nie znosi blokady sieciowej na poziomie API nałożonej przez VPC SC. Żądanie do zewnętrznego API wciąż zostałoby zablokowane.
- C. Ingress rule: Reguły Ingress służą do wpuszczania ruchu Z ZEWNĄTRZ perymetru do Twoich chronionych zasobów. Tutaj to Ty chcesz sięgnąć "na zewnątrz" do zasobów zewnętrznych.
- D. Egress swap: Ta opcja błędnie przypisuje parametry – `egressTo` powinno zawierać cel (projekt/usługa), a `egressFrom` tożsamość źródłową.

Wskazówki egzaminacyjne (Tips & Tricks):
- Pamiętaj: Egress = wyjście z perymetru do zewnętrznego projektu Google Cloud. Ingress = wejście do perymetru.
- Reguły VPC SC działają na poziomie API Google Cloud, a nie na poziomie adresów IP.

Kluczowe zagadnienia do powtórzenia:
- Zasada działania Ingress i Egress w VPC Service Controls.
- Różnica między Perimeter Bridge (wewnątrz jednej organizacji) a regułami Egress (między organizacjami).
- Debugowanie blokad VPC SC w logach audytowych.

Analiza i Wyjaśnienie

Sugerowana odpowiedź: B

Głęboka analiza: Zadanie dotyczy zaawansowanej ochrony przed eksfiltracją danych. VPC SC jest "najtwardszą" warstwą ochrony w GCP. Zrozumienie, że pobranie obrazu z zewnętrznej organizacji wymaga reguły wyjścia (Egress), jest kluczowe. Ustawienie `ANY_IDENTITY` w `egressFrom` jest bezpieczne, ponieważ i tak wymagane są odpowiednie uprawnienia IAM, aby operacja się udała.
