Question 125 / 361

You are setting up a CI/CD pipeline to deploy containerized applications to your production clusters on Google Kubernetes Engine (GKE). You need to prevent containers with known vulnerabilities from being deployed. You have the following requirements for your solution: Must be cloud-native. Must be cost-efficient. Minimize operational overhead. How should you accomplish this? (Choose two.)

  • A. Create a Cloud Build pipeline that will monitor changes to your container templates in a Cloud Source Repositories repository. Add a step to analyze Container Analysis results before allowing the build to continue.
  • B. Use a Cloud Function triggered by log events in Google Cloud's operations suite to automatically scan your container images in Container Registry.
  • C. Use a cron job on a Compute Engine instance to scan your existing repositories for known vulnerabilities and raise an alert if a non-compliant container image is found.
  • D. Deploy Jenkins on GKE and configure a CI/CD pipeline to deploy your containers to Container Registry. Add a step to validate your container images before deploying your container to the cluster.
  • E. In your CI/CD pipeline, add an attestation on your container image when no vulnerabilities have been found. Use a Binary Authorization policy to block deployments of containers with no attestation in your cluster.
Show Suggested Answer Hide Answer
Suggested Answer: AE

Wyjaśnienie

Potwierdzona odpowiedź: AE (A. Create a Cloud Build pipeline... analyze Container Analysis results, E. In your CI/CD pipeline, add an attestation... Use a Binary Authorization policy)

Wyjaśnienie:
- Container Analysis (A): Jest to natywna usługa Google Cloud, która automatycznie skanuje obrazy kontenerów w poszukiwaniu znanych luk w zabezpieczeniach (CVE) w momencie ich przesyłania do Artifact Registry lub Container Registry. Integracja z Cloud Build pozwala na przerwanie procesu budowania, jeśli zostaną wykryte krytyczne podatności.
- Binary Authorization (E): To mechanizm kontroli wdrożeń (deployment-time security). GKE sprawdza politykę Binary Authorization przed uruchomieniem kontenera. Jeśli obraz nie posiada "atestacji" (cyfrowego podpisu) potwierdzającego, że przeszedł pomyślnie skanowanie w pipeline CI/CD, wdrożenie zostanie zablokowane.
- Synergia: Połączenie skanowania (Analysis) z egzekwowaniem (Authorization) tworzy bezpieczny łańcuch dostaw oprogramowania (Secure Software Supply Chain) przy minimalnym nakładzie operacyjnym, ponieważ obie usługi są w pełni zarządzane (serverless).

Dlaczego pozostałe są błędne:
- B: Cloud Functions wyzwalane logami to rozwiązanie "reaktywne" (skanowanie po fakcie), które jest trudniejsze do wdrożenia i zarządzania niż wbudowana Container Analysis.
- C: Użycie instancji Compute Engine i zadań cron wprowadza niepotrzebny "operational overhead" (zarządzanie systemem operacyjnym, patchowanie samej VM) i nie jest rozwiązaniem natywnym dla chmury (cloud-native).
- D: Jenkins wymaga samodzielnego hostowania, zarządzania i skalowania. Cloud Build (A) jako usługa zarządzana znacznie lepiej spełnia wymóg minimalizacji narzutu operacyjnego.

Wskazówki egzaminacyjne (Tips & Tricks):
- Bezpieczeństwo kontenerów w GCP = Container Analysis (Skanowanie) + Binary Authorization (Blokowanie).
- Słowo klucz "prevent containers from being deployed" zawsze wskazuje na Binary Authorization.

Kluczowe zagadnienia do powtórzenia:
- Jak działa Binary Authorization (Attestors, Attestations, Policy).
- Automatyczne skanowanie podatności w Artifact Registry.
- Budowanie bezpiecznych rurociągów CI/CD w Cloud Build.
