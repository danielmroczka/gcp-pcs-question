Question 92 / 361

You are on your company's development team. You noticed that your web application hosted in staging on GKE dynamically includes user data in web pages without first properly validating the inputted data. This could allow an attacker to execute gibberish commands and display arbitrary content in a victim user's browser in a production environment.
How should you prevent and fix this vulnerability?

  • A. Use Cloud IAP based on IP address or end-user device attributes to prevent and fix the vulnerability.
  • B. Set up an HTTPS load balancer, and then use Cloud Armor for the production environment to prevent the potential XSS attack.
  • C. Use Web Security Scanner to validate the usage of an outdated library in the code, and then use a secured version of the included library.
  • D. Use Web Security Scanner in staging to simulate an XSS injection attack, and then use a templating system that supports contextual auto-escaping.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

**Poprawna odpowiedź: D**

**1. Kompleksowe wyjaśnienie poprawnej odpowiedzi:**
W aplikacji wykryto lukę typu Cross-Site Scripting (XSS), polegającą na dynamicznym wstrzykiwaniu niezweryfikowanych danych użytkownika do przeglądarki. Należy zapobiec i trwale naprawić tę podatność w środowisku staging:
- **Użycie Web Security Scanner w staging do symulacji ataków XSS oraz wdrożenie systemu szablonów obsługującego automatyczne uciekanie znaków (contextual auto-escaping) (D):** Web Security Scanner (część Security Command Center) pozwala na automatyczne testowanie aplikacji w środowisku staging pod kątem podatności takich jak XSS czy SQL injection. Aby trwale wyeliminować podatność w kodzie źródłowym, należy użyć silnika szablonów (templating engine), który automatycznie koduje (escape) znaki specjalne HTML (np. `<`, >, `&`) w zależności od kontekstu (HTML, atrybut, JavaScript), co uniemożliwia przeglądarce wykonanie wstrzykniętego kodu jako skryptu.

**2. Wyjaśnienie niepoprawnych odpowiedzi:**
- **A. Użycie Cloud IAP na podstawie IP lub urządzenia:** IAP kontroluje dostęp do aplikacji (uwierzytelnianie i autoryzacja), ale nie modyfikuje kodu aplikacji ani nie chroni przed lukami XSS wewnątrz samej aplikacji po zalogowaniu się użytkownika.
- **B. Użycie Cloud Armor w produkcji:** Cloud Armor może pomóc zablokować niektóre próby ataków XSS na brzegu sieci, ale nie naprawia samej luki w kodzie aplikacji. Zadanie pyta o zapobieżenie i *naprawienie* podatności (prevent and fix).
- **C. Web Security Scanner do sprawdzania nieaktualnych bibliotek:** Web Security Scanner wykrywa podatności aplikacyjne (np. XSS), ale nie służy głównie do analizy składników oprogramowania (Software Component Analysis / dependency scanning) pod kątem wersji bibliotek (od tego są inne narzędzia, np. Artifact Registry scanning). Ponadto zmiana wersji biblioteki nie naprawi luki, jeśli tkwi ona w autorskim kodzie renderującym dane wejściowe.

**3. Wskazówki i pułapki egzaminacyjne (Tips & Tricks):**
- **XSS (Cross-Site Scripting):** Najlepszym sposobem na trwałą naprawę w kodzie jest **contextual auto-escaping** w silnikach szablonów.
- **Web Security Scanner:** Narzędzie GCP dedykowane do automatycznego skanowania aplikacji webowych pod kątem luk bezpieczeństwa (takich jak XSS) w środowiskach deweloperskich i staging.

**4. Reguły wyboru odpowiedzi:**
- Wykrywanie luk webowych w staging (XSS, SQLi) -> Web Security Scanner.
- Naprawa XSS w kodzie -> Contextual auto-escaping.

**5. Dodatkowe źródła:**
- Web Security Scanner overview: https://cloud.google.com/security-command-center/docs/concepts-web-security-scanner-overview
