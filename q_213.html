Question 213 / 361

Your organization is using GitHub Actions as a continuous integration and delivery (CI/CD) platform. You must enable access to Google Cloud resources from the CI/CD pipelines in the most secure way. What should you do?

  • A. Create a service account key, and add it to the GitHub pipeline configuration file.
  • B. Create a service account key, and add it to the GitHub repository content.
  • C. Configure a Google Kubernetes Engine cluster that uses Workload Identity to supply credentials to GitHub.
  • D. Configure workload identity federation to use GitHub as an identity pool provider.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

Potwierdzona odpowiedź: D (Configure workload identity federation to use GitHub as an identity pool provider)

Wyjaśnienie:
- Workload Identity Federation (WIF): Jest to najbezpieczniejszy i obecnie rekomendowany sposób uwierzytelniania zewnętrznych obciążeń (takich jak GitHub Actions) do Google Cloud. 
- Eliminacja kluczy: WIF całkowicie eliminuje potrzebę tworzenia, pobierania i rotowania statycznych kluczy JSON kont serwisowych (Service Account Keys). Klucze te są najczęstszą przyczyną wycieków danych (np. poprzez przypadkowe wypchnięcie ich do repozytorium).
- Mechanizm działania: GitHub Actions generuje krótkotrwały token OIDC (OpenID Connect). Google Cloud weryfikuje ten token i na jego podstawie wydaje krótkotrwały, bezpieczny token dostępu do GCP. Po zakończeniu pipeline'u token wygasa automatycznie.
- Audytowalność: Każde użycie WIF jest logowane, a dostęp może być precyzyjnie ograniczony do konkretnego repozytorium, a nawet konkretnej gałęzi (branch) lub środowiska w GitHubie.

Dlaczego pozostałe odpowiedzi są niepoprawne:
- A i B. Service account keys: Przechowywanie kluczy JSON w plikach konfiguracyjnych lub w repozytorium (nawet jako GitHub Secrets) wiąże się z ryzykiem ich kradzieży. Są to poświadczenia długotrwałe, które wymagają ręcznego zarządzania i rotacji. WIF (D) jest metodą "keyless", czyli bezkluczową.
- C. GKE cluster with Workload Identity: Choć Workload Identity wewnątrz GKE jest świetnym rozwiązaniem dla podów działających W CHMURZE, nie służy ono do dostarczania poświadczeń dla zewnętrznych systemów takich jak GitHub. To GitHub potrzebuje tożsamości, aby "pukać" do Google Cloud, a nie odwrotnie.

Wskazówki i triki (Tips & Tricks):
- "GitHub Actions" / "External CI/CD" + "Securely" = Workload Identity Federation.
- Pamiętaj: WIF jest zawsze lepsze niż Service Account Keys.
- Zapamiętaj frazę: "Keyless authentication".

Praktyczne informacje na egzamin:
- Zrozum terminologię: **Identity Pool** (grupa zewnętrznych tożsamości), **Provider** (konkretny system, np. GitHub).
- WIF wspiera standardy OIDC i SAML 2.0.

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
Jeśli scenariusz dotyczy zabezpieczania zasobów chmurowych (GCP), zawsze wybieraj rozwiązanie typu Managed (SCC, Secret Manager, Cloud KMS), a unikaj rozwiązań self-managed, chyba że pytanie wyraźnie wymaga dostosowania niskopoziomowego.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka IAM: Pytania o uprawnienia często sugerują 'Project Owner' – zawsze szukaj 'Least Privilege' (np. 'Role: Secret Manager Secret Accessor').
- Pułapka Sieciowa: Często mylone są VPC Peering (wydajność) oraz VPN (szyfrowanie/on-premise).

Głębokie wyjaśnienie techniczne:
Rozwiązanie bazuje na GCP Shared Responsibility Model. Google zarządza bezpieczeństwem infrastruktury (Physical, Network, Host), podczas gdy administrator zarządza tożsamością (IAM), danymi (Encryption, Cloud KMS) i regułami dostępu (VPC Firewall).

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: D

Analiza strategiczna: To pytanie uderza w kluczowy trend "modern security" – odejście od haseł i kluczy na rzecz federacji tożsamości. W nowoczesnym DevSecOps klucze JSON są traktowane jako dług techniczny i zagrożenie. WIF przekształca zaufanie z "pliku na dysku" w "relację między systemami", co jest znacznie bezpieczniejsze i łatwiejsze w audytowaniu.

Dodatkowe wskazówki

  • Możesz użyć warunków (conditions), aby upewnić się, że tylko konkretne repozytorium GitHub (np. my-org/my-repo) może pobrać token GCP.
  • Google udostępnia gotową akcję google-github-actions/auth, która automatyzuje proces wymiany tokenów WIF.
