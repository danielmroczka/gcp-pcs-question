Question 213 / 361

Your organization is using GitHub Actions as a continuous integration and delivery (CI/CD) platform. You must enable access to Google Cloud resources from the CI/CD pipelines in the most secure way. What should you do?

  • A. Create a service account key, and add it to the GitHub pipeline configuration file.
  • B. Create a service account key, and add it to the GitHub repository content.
  • C. Configure a Google Kubernetes Engine cluster that uses Workload Identity to supply credentials to GitHub.
  • D. Configure workload identity federation to use GitHub as an identity pool provider.
Show Suggested Answer Hide Answer
Suggested Answer: D

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
D. Configure workload identity federation to use GitHub as an identity pool provider.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź D jest prawidłowa, ponieważ Workload Identity Federation (Federacja Tożsamości Obciążeń) jest najbezpieczniejszą metodą uwierzytelniania zewnętrznych potoków CI/CD (np. GitHub Actions) w Google Cloud.

Dlaczego to najbezpieczniejsze rozwiązanie:
a. **Brak kluczy długoterminowych:** Eliminuje potrzebę generowania plików kluczy JSON dla kont serwisowych GCP. Przechowywanie takich kluczy w zewnętrznych systemach (np. jako GitHub Secrets) niesie ogromne ryzyko ich wycieku lub kompromitacji.
b. **Klucze krótkoterminowe (Short-lived tokens):** GitHub Actions uwierzytelnia się u swojego dostawcy OIDC, uzyskując token tożsamości. Następnie GCP Security Token Service (STS) weryfikuje ten token i wymienia go na tymczasowy (ważny np. przez godzinę) token dostępu OAuth 2.0 konta serwisowego GCP.
c. **Precyzyjne mapowanie:** Możemy ograniczyć dostęp tylko do konkretnego repozytorium GitHub, a nawet konkretnej gałęzi (branch), za pomocą warunków atrybutów (attribute conditions).

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. Create a service account key, and add it to the GitHub pipeline configuration file.
   * Dlaczego nieprawidłowa: Umieszczenie klucza prywatnego (pliku JSON) bezpośrednio w pliku konfiguracyjnym w repozytorium kodu to krytyczny błąd bezpieczeństwa. Każdy, kto ma dostęp do kodu, uzyska pełne uprawnienia do Twojej chmury.
B. Create a service account key, and add it to the GitHub repository content.
   * Dlaczego nieprawidłowa: Podobnie jak w opcji A, przechowywanie klucza konta serwisowego w zawartości repozytorium (nawet prywatnego) jest niezgodne z najlepszymi praktykami i grozi wyciekiem danych.
C. Configure a Google Kubernetes Engine cluster that uses Workload Identity to supply credentials to GitHub.
   * Dlaczego nieprawidłowa: Workload Identity w GKE służy do nadawania tożsamości podom (pods) uruchomionym wewnątrz klastra Kubernetes w GCP. Nie rozwiązuje to problemu uwierzytelniania zewnętrznego systemu CI/CD (GitHub Actions), który działa poza GCP.

4. Wskazówki, hinty, tips and tricks:
* Uwierzytelnianie systemów CI/CD działających poza GCP (GitHub Actions, GitLab, Terraform Cloud) w Google Cloud -> Zawsze wybieraj **Workload Identity Federation**.
* Unikaj generowania kluczy kont serwisowych (Service Account Keys) – Google uznaje je za ryzyko bezpieczeństwa (compromised credentials).

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* GitHub Actions / CI/CD external access without keys -> Workload Identity Federation.

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
Jeśli scenariusz dotyczy zabezpieczania zasobów chmurowych (GCP), zawsze wybieraj rozwiązanie typu Managed (SCC, Secret Manager, Cloud KMS), a unikaj rozwiązań self-managed, chyba że pytanie wyraźnie wymaga dostosowania niskopoziomowego.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka IAM: Pytania o uprawnienia często sugerują 'Project Owner' – zawsze szukaj 'Least Privilege' (np. 'Role: Secret Manager Secret Accessor').
- Pułapka Sieciowa: Często mylone są VPC Peering (wydajność) oraz VPN (szyfrowanie/on-premise).

Głębokie wyjaśnienie techniczne:
Rozwiązanie bazuje na GCP Shared Responsibility Model. Google zarządza bezpieczeństwem infrastruktury (Physical, Network, Host), podczas gdy administrator zarządza tożsamością (IAM), danymi (Encryption, Cloud KMS) i regułami dostępu (VPC Firewall).

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: D

Analiza strategiczna: To pytanie uderza w kluczowy trend "modern security" – odejście od haseł i kluczy na rzecz federacji tożsamości. W nowoczesnym DevSecOps klucze JSON są traktowane jako dług techniczny i zagrożenie. WIF przekształca zaufanie z "pliku na dysku" w "relację między systemami", co jest znacznie bezpieczniejsze i łatwiejsze w audytowaniu.

Dodatkowe wskazówki

  • Możesz użyć warunków (conditions), aby upewnić się, że tylko konkretne repozytorium GitHub (np. my-org/my-repo) może pobrać token GCP.
  • Google udostępnia gotową akcję google-github-actions/auth, która automatyzuje proces wymiany tokenów WIF.
