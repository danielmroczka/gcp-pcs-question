Question 320 / 361

You are developing an application that runs on a Compute Engine VM. The application needs to access data stored in Cloud Storage buckets in other Google Cloud projects. The required access to the buckets is variable. You need to provide access to these resources while following Google-recommended practices. What should you do?

  • A. Limit the VMs access to the Cloud Storage buckets by setting the relevant access scope of the VM.
  • B. Create IAM bindings for the VM's service account and the required buckets that allow appropriate access to the data stored in the buckets.
  • C. Grant the VM's service account access to the required buckets by using domain-wide delegation.
  • D. Create a group and assign IAM bindings to the group for each bucket that the application needs to access. Assign the VM's service account to the group.
Show Suggested Answer Hide Answer
Suggested Answer: B

Wyjaśnienie

✅ PRAWIDŁOWA ODPOWIEDŹ: B

Prawidłowa odpowiedź: B – Create IAM bindings for the VM's service account and the required buckets that allow appropriate access to the data stored in the buckets.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
DLACZEGO B JEST PRAWIDŁOWE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Google-recommended best practice: przypisuj uprawnienia do service account (SA) na poziomie konkretnego zasobu (bucket), nie do VM. IAM bindings dla SA pozwalają na:
- Granularne uprawnienia (różne dla każdego bucketu).
- Zasada least privilege (tylko niezbędne role, np. roles/storage.objectViewer).
- Cross-project access (działa między różnymi projektami GCP).
- Brak konieczności zarządzania kluczami ani tokenami.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
DLACZEGO INNE OPCJE SĄ BŁĘDNE?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
A. ❌ Access scopes na poziomie VM = przestarzały mechanizm, używany z legacy APIs. Nie zapewnia granularności i jest mniej elastyczny niż IAM.
C. ❌ Domain-wide delegation = mechanizm dla G Suite/Workspace do działania w imieniu użytkowników. Nie jest przeznaczony do dostępu do zasobów GCP między projektami.
D. ❌ Grupy dla service accounts = nieobsługiwane. GCP Groups są przeznaczone dla użytkowników, nie SA. SA nie można dodać do grupy Google jako elementu grupy.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WSKAZÓWKI EGZAMINACYJNE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• VM potrzebuje dostępu do zewnętrznych zasobów = IAM binding dla SA VM.
• Access scopes są przestarzałe – unikaj w odpowiedziach egzaminacyjnych.
• Domain-wide delegation = tylko Workspace/G Suite scenarios.
• Cross-project access = IAM binding na zasobie docelowym.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
REGUŁY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
• Dostęp aplikacji do zasobów GCP = IAM binding dla Service Account.
• Granularny dostęp = binding na poziomie zasobu, nie projektu.

Analiza i Podsumowanie (AI)

Kluczowe zagadnienia

Sugerowana odpowiedź: B

Analiza strategiczna: Pytanie sprawdza fundamentalną wiedzę o tożsamościach i dostępach (IAM) w chmurze. Kluczem jest zrozumienie, że aplikacja na VM powinna posiadać własną tożsamość (Service Account) i otrzymywać tylko te uprawnienia, które są jej niezbędne do działania.

Praktyczny przykład

Zamiast nadawać maszynie VM rolę `roles/storage.admin` na poziomie projektu (co dałoby dostęp do wszystkich bucketów), nadajemy jej tożsamość `my-app-sa@project-id.iam.gserviceaccount.com` i przypisujemy jej rolę `roles/storage.objectViewer` tylko na buckecie `my-data-bucket` w innym projekcie.
