Question 24 / 361

A company's application is deployed with a user-managed Service Account key. You want to use Google-recommended practices to rotate the key.
What should you do?

  • A. Open Cloud Shell and run gcloud iam service-accounts enable-auto-rotate --iam-account=IAM_ACCOUNT.
  • B. Open Cloud Shell and run gcloud iam service-accounts keys rotate --iam-account=IAM_ACCOUNT --key=NEW_KEY.
  • C. Create a new key, and use the new key in the application. Delete the old key from the Service Account.
  • D. Create a new key, and use the new key in the application. Store the old key on the system as a backup key.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C (Create a new key, and use the new key in the application. Delete the old key from the Service Account.)

Wyjaśnienie: 
Google Cloud nie oferuje automatycznej rotacji dla kluczy serwisowych zarządzanych przez użytkownika (user-managed Service Account keys) w formacie JSON. Zalecaną i najbezpieczniejszą praktyką rotacji, która minimalizuje ryzyko przestojów, jest procedura manualna:
1. Utworzenie nowego klucza (nowa para publiczny/prywatny).
2. Zaktualizowanie konfiguracji aplikacji tak, aby korzystała z nowego klucza.
3. Zweryfikowanie poprawności działania aplikacji (test).
4. Usunięcie starego klucza z konta serwisowego w IAM, co trwale unieważnia go w całym systemie Google Cloud.

Dlaczego pozostałe są błędne:
A, B. gcloud commands: Komendy takie jak `enable-auto-rotate` czy `keys rotate` dla kluczy typu "user-managed" (JSON pobrany na dysk) po prostu nie istnieją w narzędziu `gcloud`. Automatyczna rotacja dotyczy wyłącznie kluczy zarządzanych przez Google (Google-managed keys), do których użytkownik nigdy nie ma dostępu.
D. Store old key as backup: Przechowywanie starych kluczy "na zapas" jest poważnym błędem bezpieczeństwa. Ideą rotacji jest właśnie to, aby stary klucz przestał działać, ograniczając okno czasowe, w którym ewentualnie przejęty przez napastnika klucz mógłby zostać użyty.

Wskazówki egzaminacyjne (Tips & Tricks):
- "User-managed key" + "Rotate" = Zawsze oznacza procedurę: Nowy klucz -> Update aplikacji -> Usunięcie starego.
- Pamiętaj: Jeśli możesz pobrać klucz JSON, jest on "user-managed". Google nigdy nie rotuje takich kluczy automatycznie.

Kluczowe zagadnienia do powtórzenia:
- Zarządzanie kluczami kont serwisowych (Service Account Keys)
- Najlepsze praktyki rotacji (Zero Downtime Rotation)
- Google-managed vs User-managed keys

Dokumentacja:

**Reguła Egzaminacyjna (Exam Rule):**
Zawsze identyfikuj warstwę modelu OSI, na której operuje atak oraz rozwiązanie. DNSSEC działa na poziomie warstwy aplikacji dla DNS, zapobiegając zatruwaniu pamięci podręcznej (Cache Poisoning).

**Haczyki egzaminacyjne (Exam Traps):**
- Mylenie Cloud Armor (WAF - L7) z zabezpieczeniami DNS (DNSSEC - integralność danych DNS).
- Zakładanie, że TLS/SSL wystarczy do ochrony przed przekierowaniem całego ruchu DNS (DNSSEC zabezpiecza sam proces rezolucji, zanim nawiążesz bezpieczne połączenie TLS).

**Głębokie wyjaśnienie techniczne:**
DNSSEC wykorzystuje kryptografię klucza publicznego (RRSIG, DNSKEY, DS) do cyfrowego podpisywania rekordów DNS w strefach (Zone Signing). Dzięki temu resolver DNS może zweryfikować łańcuch zaufania aż do punktu głównego (root zone) bez konieczności polegania wyłącznie na adresie IP serwera autorytatywnego, co drastycznie ogranicza skuteczność ataków typu MITM i cache poisoning.

Analiza i Wyjaśnienie

Sugerowana odpowiedź: C

Analiza spornych kwestii (AI): Współczesne zalecenia bezpieczeństwa Google sugerują całkowite unikanie kluczy JSON (Service Account Keys) na rzecz tożsamości instancji lub Workload Identity Federation, co eliminuje problem rotacji. Jeśli jednak musisz ich używać, procedura opisana w punkcie C jest jedynym poprawnym i wspieranym sposobem na ich odświeżenie.
