Question 258 / 361

Your organization is adopting Google Cloud and wants to ensure sensitive resources are only accessible from devices within the internal on-premises corporate network. You must configure Access Context Manager to enforce this requirement. These considerations apply: • The internal network uses IP ranges 10.100.0.0/16 and 192.168.0.0/16. • Some employees work remotely but connect securely through a company-managed virtual private network (VPN). The VPN dynamically allocates IP addresses from the pool 172.16.0.0/20. • Access should be restricted to a specific Google Cloud project that is contained within an existing service perimeter. What should you do?

  • A. Create an access level named "Authorized Devices." Utilize the Device Policy attribute to require corporate-managed devices. Apply the access level to the Google Cloud project and instruct all employees to enroll their devices in the organization's management system.
  • B. Create an access level titled "Internal Network Only." Add a condition with these attributes: IP Subnetworks: 10.100.0.0/16, 192.168.0.0/16. Device Policy: Require OS as Windows or macOS. Apply this access level to the sensitive Google Cloud project.
  • C. Create an access level titled "Corporate Access." Add a condition with the IP Subnetworks attribute, including the ranges: 10.100.0.

Wyjaśnienie

1. Prawidłowa odpowiedź lub odpowiedzi:
C. Create an access level titled "Corporate Access." Add a condition with the IP Subnetworks attribute, including the ranges: 10.100.0.0/16, 192.168.0.0/16, and 172.16.0.0/20. Apply this access level to the sensitive Google Cloud project.

2. Kompleksowe wyjaśnienie dlaczego dana odpowiedź jest prawidłowa (Analiza):
Odpowiedź C jest prawidłowa, ponieważ pozwala na zdefiniowanie poziomu dostępu (Access Level) w Access Context Managerze na podstawie atrybutu sieciowego (IP Subnetworks), co precyzyjnie dopuszcza ruch wyłącznie z zaufanych adresów IP (zarówno z fizycznej sieci biurowej, jak i z puli przydzielanej przez korporacyjny VPN).

Szczegóły konfiguracji:
a. **Dopuszczenie sieci on-premises:** Zakresy `10.100.0.0/16` oraz `192.168.0.0/16` odpowiadają lokalnej sieci firmowej.
b. **Dopuszczenie ruchu VPN:** Ponieważ pracownicy zdalni łączą się przez VPN firmy, ich ruch sieciowy dociera do zasobów GCP z adresów przypisanych z puli VPN, czyli `172.16.0.0/20`. Dodanie tego zakresu do poziomu dostępu umożliwia im bezpieczną pracę z domu.
c. **Powiązanie z perymetrem:** Poziom dostępu (Access Level) zostaje przypisany do perymetru chroniącego projekt, co gwarantuje, że zapytania z innych adresów IP w internecie będą blokowane.

3. Wyjaśnienie z osobna każdej niepoprawnej odpowiedzi:
A. ...Utilize the Device Policy attribute to require corporate-managed devices...
   * Dlaczego nieprawidłowa: Wymaganie polityki urządzeń (Device Policy) weryfikuje stan systemu operacyjnego (np. szyfrowanie dysku, hasło), ale samo w sobie nie ogranicza dostępu wyłącznie do adresów IP sieci firmowej i VPN, co było głównym wymaganiem bezpieczeństwa. Ponadto rejestracja wszystkich urządzeń generuje duży narzut operacyjny.
B. ...Add a condition with these attributes: IP Subnetworks: 10.100.0.0/16, 192.168.0.0/16. Device Policy: Require OS as Windows or macOS.
   * Dlaczego nieprawidłowa: Ta opcja pomija zakres IP dla pracowników zdalnych łączących się przez VPN (`172.16.0.0/20`). W rezultacie wszyscy pracownicy zdalni zostaliby odcięci od dostępu do projektu, co uniemożliwiłoby im pracę.

4. Wskazówki, hinty, tips and tricks:
* Access Context Manager (ACM) pozwala na definiowanie reguł dostępu opartych na: adresach IP (subnetworks), tożsamościach (principals), regionach geograficznych oraz stanie urządzenia (device policy).
* Aby dopuścić ruch VPN w regułach IP, należy zawsze uwzględnić pulę adresów przydzielanych przez serwer VPN klientom (VPN pool).

5. Reguły wyboru odpowiedzi (Słowa kluczowe):
* Access only from internal corporate network + VPN remote employees -> Access level with all IP Subnetworks (including VPN pool).
