Question 316 / 361

You want to set up a secure, internal network within Google Cloud for database servers. The servers must not have any direct communication with the public internet. What should you do?

  • A. Assign a private IP address to each database server. Use a NAT gateway to provide internet connectivity to the database servers.
  • B. Assign a static public IP address to each database server. Use firewall rules to restrict external access.
  • C. Create a VPC with a private subnet. Assign a private IP address to each database server.
  • D. Assign both a private IP address and a public IP address to each database server.
Show Suggested Answer Hide Answer
Suggested Answer: C

Wyjaśnienie

Potwierdzona odpowiedź: C (Create a VPC with a private subnet. Assign a private IP address to each database server.)

Wyjaśnienie:
Najbardziej podstawową i skuteczną metodą zabezpieczenia serwerów baz danych w Google Cloud przed bezpośrednim dostępem z internetu jest umieszczenie ich w podsieci prywatnej (private subnet) i przypisanie im wyłącznie prywatnych adresów IP (RFC 1918). W takim modelu serwery te nie posiadają publicznych adresów IP, co fizycznie uniemożliwia bezpośrednią komunikację przychodzącą z internetu. Dostęp do nich powinien odbywać się wyłącznie za pośrednictwem innych zasobów wewnątrz VPC (np. frontendu aplikacji) lub przez bezpieczne bramy (np. Bastion Host z IAP).

Dlaczego pozostałe odpowiedzi są niepoprawne:
- A. Chociaż serwery mają prywatne IP, użycie NAT Gateway (Cloud NAT) służy właśnie do zapewnienia łączności z internetem (dla ruchu wychodzącego). Scenariusz wyraźnie mówi, że serwery nie mogą mieć żadnej bezpośredniej komunikacji z publicznym internetem, więc Cloud NAT jest tu niepożądany lub zbędny.
- B. Przypisanie publicznego adresu IP (nawet statycznego) i poleganie wyłącznie na regułach firewalla jest mniej bezpieczne. Publiczny adres IP wystawia zasób na potencjalne ataki, a błąd w konfiguracji firewalla może doprowadzić do natychmiastowej ekspozycji bazy danych.
- D. Przypisanie obu adresów IP (prywatnego i publicznego) wprost narusza wymóg braku komunikacji z internetem, ponieważ publiczny adres IP służy właśnie do takiej komunikacji.

Wskazówki i triki (Tips & Tricks):
- "No direct communication with public internet" = Brak publicznego IP + brak trasy 0.0.0.0/0 do bramy internetowej (Internet Gateway).
- W GCP "prywatna podsieć" to po prostu podsieć, w której instancje nie mają publicznych adresów IP.

Praktyczne informacje na egzamin:
- Zawsze stosuj zasadę najmniejszych uprawnień również w sieci: jeśli serwer nie musi być w internecie, nie dawaj mu publicznego IP.
- Cloud NAT jest użyteczny tylko wtedy, gdy serwery w prywatnej podsieci muszą np. pobierać aktualizacje z internetu (ruch inicjowany przez serwer).
- Private Google Access pozwala instancjom z tylko prywatnym IP na dostęp do API Google (np. Cloud Storage) bez wychodzenia do internetu.

Dokumentacja i linki:

- https://cloud.google.com/vpc/docs/configure-private-google-access

Wskazówki egzaminacyjne (Tips & Tricks)

Reguła Egzaminacyjna (Exam Rule): 
W pytaniach typu 'Security in GCP', zawsze priorytetyzuj rozwiązania natywne (SCC, Cloud KMS, Secret Manager, VPC SC) nad rozwiązaniami typu 'third-party' lub 'self-managed', chyba że scenariusz wymaga specyficznej integracji hybrydowej.

Haczyki egzaminacyjne (Exam Traps):
- Pułapka 'Least Privilege': Egzamin często podpowiada role o szerokim zakresie (np. 'Editor' lub 'Owner') – zawsze odrzucaj je na rzecz ról predefiniowanych o najmniejszym zakresie uprawnień.
- Pułapka 'Logging vs Monitoring': Pamiętaj: Audit Logs służą do badania aktywności (Who/What/When), a Monitoring do zbierania metryk wydajnościowych.

Głębokie wyjaśnienie techniczne:
Każda architektura bezpieczeństwa w GCP powinna być projektowana w oparciu o 'Security by Default'. Oznacza to m.in. szyfrowanie w spoczynku (domyślne), tożsamość opartą na rolach (IAM) oraz pełną widoczność zapewnianą przez scentralizowane logowanie (Cloud Logging/SCC).
